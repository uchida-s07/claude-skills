# データ構造・ファイルレイアウト設計のレビュー（詳細設計）

対象は **`04-db.md` 1本**。**新規に書き直さない。**既にあるものに観点を当て、**不足だけを埋める。**

作成は `db-doc` スキルの仕事。まだ文書が無いならそちらへ回す。

**仕様書（03）と要件定義書（02）は照合用に必ず読む。**
04は02の機能・03の画面が扱うデータを器に落とした文書なので、上流を見ずに過不足は判定できない。
とくに**03は必須**（画面に出る項目・並び順・絞り込みが、器とインデックスの唯一の根拠になる）。
ただし**直すのは04だけ。**02側の不足は `requirement-doc-review`、
03側の不足は `spec-doc-review` へ回す。

**04は3つの形態がある。**どれなのかを最初に見極めてから観点を当てる
（章タイトルと点検内容が変わる）。

| 形態 | 見分け方 |
|---|---|
| RDB | テーブル一覧 / ER図 / テーブル定義 / インデックス方針 |
| ドキュメントDB | コレクション一覧 / ドキュメント定義 / 複合インデックス・クエリ制約 |
| DBなし | データストア一覧 / データ構造定義 / ファイルレイアウト |

## 大原則

1. **全部読んでから判断する。**一部だけ見て「足りている」と言わない。
   **02・03・04**を通しで読む（01はデータの分離単位を見るときだけ）。
2. **既存スキーマがあるなら、実物と照らす。**04は実装が直接参照する文書なので、
   **文書と現物がずれていること自体が最大の不足。**
   `migrations/` / `schema.sql` / `firestore.rules` / `firestore.indexes.json` /
   データアクセス層のコードを読み、04と食い違っていないか確かめる。
   **ただし直すのは文書側だけ。**コードやスキーマには手を入れない
   （実装を直すべきだと判断したら、そう報告してユーザーに委ねる）。
3. **勝手に書き足さない。**不足を埋めるには判断が要る。
   ただし**02・03から一意に導ける記述**は、聞く前に案を書いて見せてよい
   （そのとき02・03のどこから起こしたかを必ず示す）。
   導けないもの（保持期間・削除の方針・非正規化の可否）は案を添えて聞く。
4. **決めるのは人間。**推奨案は出してよいが、承認なしに決定として書かない。
5. **指摘は場所と一緒に出す。**「`inquiries.answered_by` の `ON DELETE` が未定義」のように、
   **どのテーブル・どのカラムの何が足りないかを名前で言う。**
6. **設計の好みでは指摘しない。**「自分ならこう切る」は不足ではない。
   指摘するのは、**02・03の要求を満たせない**か、**実装者が判断に迷う**か、
   **現物と食い違う**場合だけ。
7. **05以降（API・テスト）とBuildの内容を要求しない。**
   エンドポイント定義が無いのは不足ではなく正しい状態。
   **動くCREATE文・マイグレーション・モデル実装コードが無いのも正しい**
   （あったらむしろ混入。観点J）。
8. **02の内容を蒸し返さない。**機能の切り方やスコープへの異議はこのレビューの範囲外。
   04が02と食い違っているかどうかだけを見る。

## 手順

### 1. 対象を特定する

`docs/requirements/04-db.md` など、設計書の場所を確認する。
複数あるなら、どれを見るのかユーザーに聞く。見つからなければ、
**まだ作成の段階なので `db-doc` を使うよう案内して終了する。**

あわせて次も特定する。

- **形態**（RDB / ドキュメントDB / DBなし）。冒頭の前提と章タイトルから判定する。
  判定できないなら、それ自体が不足（観点A）。
- **対になる仕様書（03）と要件定義書（02）。**照合の土台なので、無ければ観点B・Cを当てられない。
  見つからない場合は、そのことを伝えたうえで、残りの観点だけで点検するか、
  先に上流（`spec-doc` / `requirement-doc`）を作るかを**ユーザーに選んでもらう。**
  片方だけ欠けている場合も同じ（欠けた側の観点を飛ばしたことは必ず伝える）。
- **モック**（`mocks/mockup.html`）。あれば、本文に無い項目が画面に出ていないかを見る材料になる。
- **既存スキーマの実物**（観点I）。無ければその観点を飛ばす。

### 2. 全部読む

飛ばし読みしない。04を冒頭の前提から「次のステップ」まで通し、**02・03も通しで読む。**
03は画面ごとの仕様（表示項目・一覧の並び順・絞り込み・状態表示）まで読む。

### 3. 観点を当てる

下の「点検の観点」を全部当てる。
**B（トレーサビリティ）・C（画面項目の器）・E（キーと参照の整合）は漏れが最も出るので必ず見る。**

機械的に確かめられるものは、目視より先にコマンドで潰す（「機械的に潰せるもの」）。

### 4. 結果を提示する

- **不足がある場合** → 見つかった不足を**一覧でユーザーに提示してから**直しに入る（手順5へ）。
  一覧は**構造に波及するもの（項目の追加・分割・キーの変更）と、
  記述の不足（説明・理由・制約の書き漏れ）を分けて**出す。
  **前者を先に直す**（後者は前者の結果で変わるため）。
- **不足がない場合** → 何も書き換えない。
  **「不足のない設計書が既にある」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのかも一緒に伝える（当てた観点と、その結果を示す）。

### 5. 不足を埋める

1件ずつ「（必要なら質問 →）ドラフト → 赤入れ → 確定 → ファイルへ書く」で進める。

- **02・03から一意に導ける不足は、先に案を書いて見せる**（原則3）。
  「SCR-02の一覧が更新日時の降順なので、`{table}.updated_at` にインデックスを足す案です」の形。
- 導けない事実（保持期間・削除の方針・想定件数・運用）は**推測で埋めず聞く。**
  「まだ決まっていない」と言われたら、選択肢を2〜3案に絞り、推す案に `（推奨）` と
  理由を添えて聞き直す。それでも決まらないなら、持ち帰るか暫定で決めるかを
  **ユーザーに選んでもらう。**
- **項目やテーブルを増減させたら、波及を必ず追う。**1章の一覧・2章のER図・3章の定義・
  4章のインデックス（またはファイルレイアウト）・5章の方針 — この5箇所が
  そろって直っているかを毎回確認する。**ここが最も取りこぼす。**
- 一度に聞くのは2件まで。まとめて並べない。
- **直した箇所はその都度ファイルへ書く。**まとめて最後に書かない。

### 6. ユーザーの承認をもって完了とする

直した内容を報告し、承認を得て終わる。自分の判断で締めない。

- 何が足りず、どう直したかを短く一覧で見せる（構造の変更 / 記述の追加を分ける）
- 決着させた未確定事項があれば、何をどう決めたかも見せる
- **02・03側に見つけた不足があれば、直さずに報告する**（どちらのスキルへ回すかも添える）
- **既存スキーマと食い違っていた箇所は、文書と実装のどちらが正なのかを確認する**
- 「これで05（API設計）／実装へ進んでよいか」を確認する
- 進んでよいと言われたら、**次の工程を案内する**（走らせるかはユーザーが決める）

> 次は **`api-ipo-doc` スキルで 05（API・IPO一覧）を作成できます。**
> 04で決めた器を、どのインターフェースがどう読み書きするかを確定させる文書です。
> **05が既にあるなら `api-ipo-doc-review`**（05単体の点検）、
> **04と05の食い違いを見たいなら `db-api-crossreview`**（横断レビュー）。

## 点検の観点

### A. 章と項目が揃っているか

形態によって章タイトルが変わる。**中身の役割が揃っているか**を見る（名前の一致は問わない）。

| # | RDB | ドキュメントDB | DBなし |
|---|---|---|---|
| 冒頭 | Vモデル上の位置（詳細設計 / 単体テスト）＋前提（DBエンジン・既存スキーマの扱い） | 同左 | 同左＋**DBを持たない理由と将来の逃げ道** |
| 1 | テーブル一覧 | コレクション一覧 | データストア一覧 |
| 2 | ER図 | データモデル関連図 | データモデル関連図 |
| 3 | テーブル定義 | ドキュメント定義 | データ構造定義 |
| 4 | インデックス方針 | インデックス・クエリ方針 | ファイルレイアウト |
| 5 | 正規化・整合性の方針 | 非正規化・整合性の方針 | 正規化・永続化の方針 |
| 末尾 | 設計書の範囲を切る一文 ＋ 次のステップ | 同左 | 同左 |

- **1章の全行に「関連機能(②)」欄があるか。**空欄は不足。
- **3章の各定義に「目的」が1〜2文あるか。**表だけ置いて目的が無いのは不足
  （何のために持つ器なのかが分からないと、実装者が使い方を誤る）。
- **DBを持たない設計なのに、持たない理由が書かれていない**のは不足。
  「将来必要になったときの移行先」も同じ。
- **行数や箇条書きの数は問わない。**「項目があるか」だけを見る。

### B. 要件（02）とのトレーサビリティ（最も漏れが出る）

**両方向で照合する。**片方向だけだと必ず抜ける。

**02 → 04（器の不足）**

- 02の機能一覧の**機能IDが1つ残らず**、1章のどこかの「関連機能(②)」欄に現れているか
- 現れない機能があるなら、**なぜデータを持たないかが書かれているか**
  （その場で計算する / 外部システムが持つ / Out of Scope）。無言で消えているのは不足
- 02の各機能の**受入基準**が、この構造で満たせるか。
  「〜順に表示されること」「重複を登録できないこと」のような基準に、
  **対応する並び順のキー・UNIQUE制約があるか**
- 02の各機能の**例外・バリデーション**のうち、データで表現するもの
  （状態の遷移・重複の検知・失敗の記録）に**器があるか**

**04 → 02（出どころ不明）**

- 1章の全データストアに対応する機能IDがあるか（空欄が無いか）
- そこに書かれたIDが**02に実在するか**（`FUNC-09` と書いてあるのに02は08までで終わっている、など）
- 02のどこにも根拠が無いテーブル・項目が紛れていないか。
  あるならそれは**新規要件**。02を直すのか（→ `requirement-doc-review`）
  04から落とすのかをユーザーに聞く
- **Out of Scope から器を起こしていないか**（作らないと決めた機能のテーブルがある）。
  Scope 2/3 のための器なら、**`（Scope2）` の注記があるか**

### C. 仕様書（03）の画面項目に器があるか（最も漏れが出る）

**画面を1つずつ指で追って**照合する。

- 画面が**表示する項目**が、すべてどこかの定義にあるか。
  「一覧に投稿者名を出す」のに、投稿側が投稿者IDしか持っていない、が起きやすい
- 画面の**入力フォームの項目**が、すべて器を持っているか。必須／任意が制約と一致しているか
- 画面の**一覧の並び順・絞り込み・検索条件**が、器とインデックスで実現できるか（観点Hへ繋がる）
- 画面の**状態表示**（未対応／対応済み・下書き／公開）に対応する列挙値が定義されているか。
  **画面に出る状態の数と、定義の列挙値の数が合っているか**
- 画面の**エラー・例外表示**のうち、データの状態から出るもの
  （重複エラー・0件・権限なし）を、この構造で判定できるか

**03は04の前提なので、通常この観点は必ず当たる。**
例外的に03が見つからない場合だけ飛ばし、**飛ばしたことをユーザーに伝える。**

### D. 定義そのものが実装に足りるか

3章の表を1行ずつ見る。**実装者が判断に迷う行が残っていないか**が基準。

- **型が具体的か。**`string` で済ませていて長さ・用途が読み取れない、
  日時が `string` になっている、金額が浮動小数になっている
- **制約が空欄でないか。**PK / NOT NULL / UNIQUE / DEFAULT が書かれているか
- **NULLを許す列に、許す理由が説明列にあるか。**
  「未回答の間はNULL」のように、**いつNULLになるか**が書かれているか
- **列挙値が全部書かれているか。**`status: string` だけで、取りうる値が無いのは不足。
  値と意味の対応（`unanswered`=未対応）まであるか。**既定値はどれか**
- **未知の値が来たときの扱い**が決まっているか（特にドキュメントDB・外部由来のデータ）
- `created_at` / `updated_at` の有無が対象ごとに決まっているか
  （全部に機械的に付いている／全部に無い、はどちらも一度疑う）
- **命名が全体で揃っているか。**単数形と複数形、スネークとキャメル、
  `is_` 接頭辞の有無が混在していないか
- 実装キーと**利用者に見えるラベル**が別なら、対応表があり、**写像する場所**が書かれているか
- 説明列が「作成日時」で終わっていないか。**何のためにあるかが書ける項目は書かれているか**

### E. キー・参照・一意性の整合（最も漏れが出る）

- **FKの参照先が実在するか。**`FK(admins.id)` と書いてあるのに `admins` が1章に無い、
  カラム名が違う（`admin_id` を指しているのに参照先は `user_id`）
- **`ON DELETE` の挙動が決まっているか。**参照先が消えたとき、
  CASCADE / SET NULL / RESTRICT のどれか。**決まっていない行が1つでもあれば不足**
  （実装者が握りつぶす、または本番でエラーになる）
- **多対多に中間テーブルがあるか。**あるなら**複合UNIQUE**（重複登録を防ぐ）が書かれているか
- **主キーの決め方が書かれているか。**自動採番か、業務キーをそのまま使うか。
  ドキュメントDBなら**ドキュメントIDが何から来るか**（自動ID / 業務ID）
- **一意であるべきものにUNIQUEが付いているか。**
  ログインID・トークン・外部システムの識別子・「1ユーザー1件」の関係
- **ER図の線と、3章のFK定義が一致するか。**図では繋がっているのに列が無い（逆も）
- ドキュメントDB・DBなしなら、**入れ子と参照の使い分けに理由があるか**
  （なぜサブコレクションに切ったか／なぜ埋め込んだか）

### F. 章をまたいだ整合

- **1章 → 2章 → 3章で数が合うか。**一覧に7つあるなら、ER図に7つ、定義も7つ。
  **どれか1つにしか出てこないものが最も見つかりにくい不足**
- 名前が章をまたいで揃っているか（1章は `faqs`、3章は `faq` になっていないか）
- 4章のインデックス表に出てくるテーブル・カラムが、**3章に実在するか**
- 5章の方針が、3章の定義と矛盾していないか
  （「論理削除する」と書いてあるのに削除フラグの列が無い、
  「非正規化していない」と書いてあるのに同じ項目が2か所にある）
- 冒頭の前提で宣言したDBエンジンと、本文で使っている型・構文が一致しているか

### G. mermaidが壊れていないか

- **エンティティ名に `/` `-` 空白が入っているのにクォートされていない**
  （Firestoreのパスをそのまま書くと**パースに失敗して図が出ない**。
  `"festival/27/events"` のようにクォートする、または `FESTIVAL_EVENTS` のような別名にする）
- **属性の型に `<` `>` `(` `)` が入っている**（`array<string>` は erDiagram で壊れる。
  `array_string` や `list` に置き換え、詳細は説明のクォート内に書く）
- **属性のコメントがクォートされているか**（`string id "説明"` の形。裸の日本語コメントは壊れる）
- リレーションの記号が正しいか（`||--o{` `}o--||` `||--|{`）。
  **カーディナリティが本文と一致しているか**（3章では0件可なのに図は `||--|{` になっている）
- 未定義エンティティ・閉じ忘れ
- 図に出てくるエンティティが、**すべて1章の一覧に実在するか**
- ドキュメントDB・DBなしで入れ子を `||--o{` で表しているなら、
  **図の直前にその読み方の断りがあるか**（リレーションと誤読される）

**図は壊れていても本文だけ読むと気づけない。**ここは必ず目で追う。

### H. 4章が実際のクエリ・出力に対応しているか

**RDB / ドキュメントDB（インデックス方針）**

- **UNIQUE制約で自動的に張られるものと、明示的に足すものが区別されているか**
- 03の画面が使う**絞り込み・並び順が、すべてインデックスで拾えているか。**
  逆に、どのクエリのためか説明できないインデックスが無いか
- **理由が「どのクエリのためか」まで書かれているか。**「検索が速くなるため」は理由ではない
- FKにインデックスを付けるかがエンジン差込みで書かれているか
  （PostgreSQLは自動で張らない / MySQL(InnoDB)は張る）
- ドキュメントDBなら、**等価条件＋並び順の組み合わせに複合インデックスが挙がっているか。**
  クエリ制約（複合クエリの可否・`array-contains` の個数制限）に構造が合っているか。
  **全文検索のように、そのDBでは解けないものに代替が書かれているか**
- **セキュリティルールで絞れる形になっているか**（パスの切り方が権限の境界と一致しているか）

**DBなし（ファイルレイアウト）**

- ディレクトリツリーがあり、**各ディレクトリの役割が書かれているか**
- **読取専用の場所と、書込を許す場所が明示されているか**（入力の原本を改変しない、が守られる形か）
- **生成物のファイル名規則があるか。**どの入力に対応する出力かが名前で辿れるか
- 中間ファイルの位置づけ（実行状態か、捨ててよいキャッシュか）が書かれているか
- 1章の「実体」列に書かれたパスと、ツリーが一致しているか

### I. 実物（既存スキーマ・実装）と食い違っていないか

**既存スキーマがある場合だけ当てる。**無ければ飛ばし、飛ばしたことを伝える。

- `migrations/` / `schema.sql` / `prisma/schema.prisma` / `models.py` にあるテーブル・列が、
  04の定義と**名前・型・制約まで一致するか**
- ドキュメントDBなら、**データアクセス層のコードが実際に読み書きしているパス**と
  1章のパスが一致するか（`firestore.rules` と `firestore.indexes.json` も見る）
- 04にあって実物に無いもの、実物にあって04に無いものを**両方向で洗う**
- 移行途中なら、**新旧2系統あることが04に書かれているか。**
  どちらが正で、いつどちらへ寄せるかが書かれているか（黙って片方だけ載っているのは不足）

**食い違いを見つけても、コードやスキーマは直さない**（原則2）。
文書が古いのか実装が先走ったのかをユーザーに確認し、**文書側だけ**直す。

### J. 書いてはいけないものが混ざっていないか

- **動く CREATE 文（DDL）の全文・マイグレーションファイルの中身** → Buildフェーズの成果物。
  **04に載せるのは定義表・ER図・制約まで**
- **モデル実装コード（Pydantic / Dartのクラス・ORMの定義）** → 同上
- APIエンドポイント・リクエスト/レスポンス定義・IPO → 05の内容
- テストケース・テスト手順・テストデータ → 06以降の内容
- 画面構成・UI要素・モック → 03の内容
- DBエンジンやクラウド構成の**選定理由・比較検討** → インフラ設計（07）。
  04に書くのは「何を使うか」の前提までで、なぜそれを選んだかの検討過程ではない

見つかったら「不足」ではなく**削除の提案**として出す。消す判断もユーザーに仰ぐ。

> **型・制約・列挙値を書くのは正しい。**混入として扱うのは、
> **そのままコピーすれば動いてしまう成果物**（DDL全文・実装クラス）が置かれている場合。
> 短い例示（`ON DELETE SET NULL` の書き方など）まで削らせない。

### K. 非機能要件（02）が構造に反映されているか

- **秘密情報の持ち方。**パスワードが平文の列になっていないか（`password_hash` になっているか）。
  APIキー・トークンの置き場が決まっているか
- **個人情報の置き場**が、02のセキュリティ要件と噛み合っているか
- **保持期間**が決まっている（ログ・履歴を消す運用がある）なら、
  消す単位で器が切れているか（消せない形に埋め込まれていないか）
- **データの分離単位**（テナント・物件・ユーザー）が、全テーブルで一貫しているか。
  1つだけ分離キーを持たないテーブルが混ざっていないか — **横断で見えてしまう事故になる**
- 02の性能要件（件数・応答時間）に対して、構造とインデックスが無理をしていないか

### L. 未確定が残っていないか

- **「未定」「未確認」「TBD」「要検討」「{}」が1つも無いか。**
  04は実装が直接参照する文書で、ここが宙ぶらりんだとAPI設計・実装が止まる。
  残っていたら、そこを決めるところまでやって閉じる
- テンプレートの `{プレースホルダ}` が埋まらないまま残っていないか
- **`<!-- ASK: ... -->` のコメントが残っていないか**（`db-doc` が完了前の確認用に置く印。
  残っている＝聞かずに暫定案のまま出ている。**本文だけ読んでも見えないので必ずgrepする**）
- 「〜かもしれない」「必要に応じて」で逃げている箇所が無いか。**決め切る**

## 機械的に潰せるもの（目視の前に）

**ここで出た差分が、そのままB・E・F・L観点の指摘になる。**

| 確かめること | 見かた |
|---|---|
| 1章と3章の数が合うか | 1章の表の行数と、3章の小見出しの数を数えて突き合わせる |
| ER図に全部出ているか | `erDiagram` ブロック内のエンティティ名を列挙し、1章と**差集合を取る** |
| 02の機能IDの拾い漏れ | 02から `FUNC-\d+` を全部拾い、04の本文にあるものと差集合を取る |
| 存在しない機能IDの参照 | 逆向きの差集合（04にあって02に無いID） |
| FKの参照先 | `FK\(([a-z_]+)\.` を拾い、テーブル名が1章に実在するか |
| `ON DELETE` の抜け | `FK(` を含む行のうち `ON DELETE` を含まない行を数える |
| 未確定の残り | `未定` `TBD` `要検討` `要確認` `{` `ASK:` を検索 |
| DDL・実装の混入 | `CREATE TABLE` `ALTER TABLE` `class ` `@Entity` `BaseModel` を検索 |
| 実物との差 | `migrations/` `schema.sql` `firestore.rules` からテーブル名・パスを拾い、04と突き合わせる |

## やらないこと

- **新規に書き起こす** → `db-doc`
- **要件定義書（02）の点検・不足埋め** → `requirement-doc-review`。
  02側の不足はここでは直さず、そちらへ回す
- **仕様書（03）の点検・不足埋め** → `spec-doc-review`
- **05以降の内容（API・テストケース）を要求する**
- **動くDDL・マイグレーション・モデル実装コードを書く／要求する** → Buildフェーズ
- **コードや既存スキーマを直す。**観点Iで食い違いを見つけても、**直すのは文書だけ**
- **設計の作り直し・好みによる作り替え。**不足を埋めるだけにとどめる
- **DBエンジンの選び直し** → インフラ設計（07）の範囲

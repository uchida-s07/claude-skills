# docs-review（常設文書のレビュー）

あなたは文書のレビュー担当です。**文書を書いた人とは別の立場で**、常設文書（vision・常設要件）と、範囲が `all` のときはコード・設計・spec の状態まで横断して、意味の上での矛盾・ずれ・放置を洗い出します。
呼び出し元の会話は見えません。必要な情報は引数とファイルから得てください。

- 引数：`$ARGUMENTS`
  - 1つ目：範囲。`vision` / `requirements`（続けて領域コードがあればその領域）/ `all`。**無ければ `all`。**
  - 最後の要素が ①〜⑨ の丸数字ならタイミング番号。無ければ「手動（⑨）」とみなす。
  - 引数が読み取れなければ `all` で進め、そう判断したことをレポートの冒頭に書く。
- 共通ルール（要件の書き方・重大度・指摘の状態・書式・除外）：`${CLAUDE_SKILL_DIR}/../product-requirements/rules.md`。**最初に全文を読む。**
- vision の書き方の基準：`${CLAUDE_SKILL_DIR}/../product-vision/SKILL.md` の「大原則」と「各章に必要な項目」。

## 守ること

1. **読み取り専用。** ファイルを作らない・書き換えない・消さない。直すのは呼び出し元。実行してよいコマンドは、読み取り（`git log` / `ls` / `grep` など）と、下の `spec_check.py` だけ。
2. **全文を読んでから判断する。** 範囲の文書は飛ばし読みしない。
3. **両方向で見る。** 片方向だけでは必ず抜ける（vision → 要件、要件 → vision。要件 → コード、コード → 要件）。
4. **どちらを直すべきかまで書く。** 判断できないときは両方の案と、それぞれを採ると何が起きるかを1行ずつ書く。「上流が正」を機械的に当てない（コードのほうが新しい実態を映していることは普通にある）。
5. **指摘は場所と ID で言う。** 両方の記述を引用する。
6. **機械点検で分かることは繰り返さない。** 手順1の結果に出た指摘は「機械点検の結果」に載せるだけにする。
7. **除外済みの指摘は出さない。** `docs/review-notes.md` の表に同じ対象・同じ要旨の行があれば出さず、件数だけ書く。ただし除外の日付より後に対象のファイルが変わっていれば、改めて判断する。
8. **照合不能を「問題なし」に混ぜない。** 材料が無くて確かめられなかった観点は「照合不能」として分ける。
9. **書いてはいけないものの混入は「削除の提案」として出す。**
10. **範囲外の不備は直さず「別のレビューへ回す指摘」として分ける。**
11. 設計の好みでは指摘しない。指摘するのは、記述どうしが成り立たないか、必要なものが無いか、成り立つが危ういときだけ。
12. **プロジェクトのルートを取り違えない。** 引数に `--root <パス>` があればそこを、無ければ作業ディレクトリをルートとする。そこに `docs/` が無ければ、**ほかの場所を探さずに**「対象のプロジェクトが分からない（`--root` で指定してほしい）」とだけ書いて終える。以下のコマンドの `--root .` は、このルートに読み替える。

## 手順

### 1. 機械点検を実行する

プロジェクトのルート（`docs/` のあるディレクトリ）で実行する。`python3` が無ければ `python`。

| 範囲 | コマンド |
|---|---|
| vision / all | `python3 "${CLAUDE_SKILL_DIR}/../spec-check/scripts/spec_check.py" all --root .` |
| requirements <領域> | `python3 "${CLAUDE_SKILL_DIR}/../spec-check/scripts/spec_check.py" area <領域> --root .` |
| requirements（領域の指定なし） | `all` と同じ |

vision の範囲では、出力のうち vision.md と、vision を参照している要件に関わる指摘だけを「機械点検の結果」に載せる。

### 2. 読む

| 範囲 | 読むもの |
|---|---|
| vision | `docs/product/vision.md`。vision を参照している要件（`docs/product/requirements/` を `G-` `P-` `J-` で grep）と、進行中の spec の「関連する要求」 |
| requirements [領域] | `docs/product/vision.md`、`requirements/README.md`、`common.md`、対象の領域ファイル（指定が無ければ全部）、対象の要件を事前条件で参照している・参照される他の領域の要件、`docs/product/glossary.md` |
| all | 上の全部に加えて、`docs/architecture.md`、`docs/adr/`、`docs/specs/` のすべての spec の冒頭と「対象の要件」、コードの入口（画面・API のルーティング・コマンド・バッチ）とスキーマ、旧フローの文書（`01-request.md` 〜 `06-scenario-test.md` を探す）、`CLAUDE.md` |

どの範囲でも `docs/review-notes.md` を読む。
規模が大きいときは、観点ごとに読む範囲を分けて進めてよい（ただし当てた観点の結果はすべて書く）。

### 3. 観点を当てる

範囲ごとに ○ の観点を当てる。

| 観点 | 見ること | vision | requirements | all |
|---|---|---|---|---|
| V1. vision の章と項目 | 背景・課題 / ゴール（成功指標）/ 非目標 / ペルソナ / ジャーニー / 利害関係者 / 変更履歴 が揃い、中身があるか | ○ | | ○ |
| V2. vision の一貫性 | 課題 → ゴール → ジャーニーがつながっているか。どこでも解決されない課題が無いか。ペルソナのペインと課題一覧が一致しているか。ペルソナの技術スキル・頻度とジャーニーの行動が噛み合うか | ○ | | ○ |
| V3. ジャーニー | 各行の終わりが次の始まりになっているか。始まりと終わりがあるか。書かれている以外の入口が無いか。図と表と感情の変化が対応し、スコアが満足度として一貫しているか。登場人物が複数なら相手側の行動もあるか。（画面単位の操作が無いことは不足ではない） | ○ | | ○ |
| V4. vision への混入 | 機能・データモデル・画面・API・技術選定・工数 | ○ | | ○ |
| V5. 言葉の具体性 | 「使いやすく」「スムーズに」などの抽象語が具体的な場面に置き換わっているか | ○ | | ○ |
| V6. 非目標との矛盾 | 非目標に書いたことを、ゴールやジャーニーが前提にしていないか | ○ | | ○ |
| R1. 要件の中身 | 5項目が中身を持つか（「特になし」の事前条件が本当に前提を持たないか、正常フローに分岐が混ざっていないか、粒度が揃っているか） | | ○ | ○ |
| R2. 受入基準 | 検証可能か。rules.md 第6章の禁止語が無いか。Given に具体的な値、Then に観察できる結果があるか | | ○ | ○ |
| R3. 例外 | 3方向（rules.md 第5章）が検討され、止める / 飛ばすが読み取れるか。「止める」ものが AC になっているか | | ○ | ○ |
| R4. 非機能 | common.md の5カテゴリに中身があるか（該当なしは理由付きか）。測り方があるか。ユーザビリティがペルソナの技術スキルと合うか | | ○ | ○ |
| R5. 要件への混入 | 画面構成・テーブル定義・API・予定（まだ作っていないこと） | | ○ | ○ |
| R6. 要件どうしの矛盾 | 同じ条件に対して違う振る舞いを定めていないか。ある要件の例外処理が、別の要件の正常フローを否定していないか。事前条件が循環していないか。共通の非機能要件と領域固有の非機能要件がぶつかっていないか | | ○ | ○ |
| R7. 重複 | 同じ振る舞いを別の ID で二重に定めていないか | | ○ | ○ |
| R8. 要求との対応の妥当性 | 「対応する要求」の参照が、中身として本当にそのゴール・課題・ジャーニーに効いているか。vision の非目標に当たる要件が無いか。（vision の範囲では、変更・廃止した vision 項目を参照している要件への影響として見る） | ○ | ○ | ○ |
| X1. 要件とコード | 要件にある振る舞いの入口（画面・API・コマンド）がコードにあるか。要件に無い API・テーブル・画面が増えていないか（書かれていない振る舞い） | | | ○ |
| X2. 用語 | glossary・文書・コードで、同じものを別の名前で呼んでいないか。コード上の名前が用語集と一致しているか（requirements の範囲では文書だけ） | | ○ | ○ |
| X3. 設計判断 | 実際の構成が architecture.md と一致しているか。採用中の ADR の決定に反する実装、置き換えられた ADR を前提にした記述 | | | ○ |
| X4. spec の状態 | 進行中の spec どうしの衝突（同じ要件・テーブル・API を変えようとしている）。done なのに常設要件に移されていない spec。approved のまま手が付いていない spec。スコープ外の「後回し」のうち、どの spec にも拾われていない項目 | | | ○ |
| X5. 旧文書の残骸 | 旧 01〜06 の文書が残っていて、新構成と食い違っていないか（残すか消すかはユーザーに聞くよう提案する） | | | ○ |

要件とテストの対応の有無は機械点検が見る。テストの中身が AC と一致しているかは `spec-verify` が spec ごとに見るので、ここでは見ない。

重大度は rules.md 第12章：2つの記述が同時に成り立たない → 矛盾 / 必要な項目・対応が無い → 欠落 / 成り立つが危うい → 注意。

### 4. レポートを返す

次の形で返す（これが最終出力。呼び出し元がそのまま使う）。

```
# docs-review 結果: <範囲>

- タイミング: ①（引数に無ければ「手動 ⑨」）
- 読んだファイル: …
- 当てた観点: …
- 除外済み: n 件（docs/review-notes.md）

## 機械点検の結果
（spec_check.py の件数と、指摘の一覧をそのまま。vision の範囲では関係する分だけ）

## 指摘
| ID | 重大度 | 観点 | 場所 | 何がどうぶつかっているか（両方の記述を引用） | 直し方の案 | 直す先 |
|---|---|---|---|---|---|---|
| R-1 | 矛盾 | R6 | MEAL-F-003 例外 / MEAL-F-005 正常フロー | … | 案1: … / 案2: … | 常設要件（/product-requirements update） |

## 確認した観点と結果
| 観点 | 結果 | 確認したこと |
|---|---|---|
（照合できなかった観点は「照合不能」と書き、何が足りないかを書く）

## 別のレビューへ回す指摘
（範囲外の不備。例：requirements の範囲で vision の不備 → docs-review vision）

## 直す先の振り分け
| 指摘 | 直す先 | 使う Skill |
|---|---|---|
| R-1 | 常設要件（文言の修正で済む） | /product-requirements update |
| R-2 | vision | /product-vision update |
| R-3 | 振る舞いの変更が要る | 新しい spec（/spec-new） |
| R-4 | 進行中の spec 002 | /spec-new で 002 を直す |
（直す順番も書く：vision → 常設要件 → spec の順が基本）

## 判定
合格 / 不合格（未解決の矛盾 n 件・欠落 n 件。機械点検の分を含む）
```

- 指摘が無い場合も「確認した観点と結果」を必ず書く（「問題なし」とだけ言わない）。
- 判定は、機械点検と LLM の指摘を合わせて、**矛盾・欠落が0件なら合格**。注意は判定に含めない。

# spec-close（spec を閉じて常設要件へ移す）

実装が済んだ spec を検証し、要件を常設ドキュメントへ移して完了にする。対象の spec：$ARGUMENTS

- 共通ルール：`${CLAUDE_SKILL_DIR}/../product-requirements/rules.md`（必ず全文を読んでから始める）
- 領域ファイルの雛形：`${CLAUDE_SKILL_DIR}/../product-requirements/template-area.md`、全体共通：`template-common.md`、索引：`template-readme.md`

## 手順

### 1. 完了を確かめる

- `docs/specs/NNN-*/spec.md` と `tasks.md` を読む（番号は3桁ゼロ埋め）。
- `status` が `approved` でなければ止める。
- tasks.md に未完了（`- [ ]`）のタスクがあれば、一覧で見せて**中止する**。

### 2. 実装を検証する（タイミング⑥）

`spec-verify` を呼ぶ（Skill ツールで `spec-verify`、引数 `NNN`）。fork したサブエージェントが、実装に関与していない立場で、AC とテストの対応・テストの中身・テスト全体の回帰・差分の一致・スコープ外の実装を見て、レポートを返す。

- **未解決の矛盾・欠落があれば、一覧で見せて中止する。** 直すのは実装側（またはユーザーの判断で spec 側）。直したら `/spec-close NNN` をやり直す。
- ユーザーが「誤検知」「承知で進める」と判断した指摘は、理由を聞いて `docs/review-notes.md` に書く（rules.md 第12章）。
- 「実行方法が不明」で判定不能なら、CLAUDE.md の「テストの実行」を埋めるようユーザーに頼み、中止する。

### 3. 常設要件へ移す

spec の「2. 要件」を常設要件に反映する。**spec に書いたとおりに移す。** 移すときに中身を書き換えない（直す必要に気づいたら、止めてユーザーに聞く）。

| spec の区分 | 常設要件でやること |
|---|---|
| 新規 | 「変更後の姿」の5項目を、該当する領域ファイルの「機能要件」へ見出しごと移す。「要件一覧」の表にも1行足す |
| 変更 | 領域ファイルの該当ブロックを、spec の「変更後の姿」で置き換える。「（変更）」の印と「変更前との差」の行は外す。「要件一覧」の行も合わせる |
| 廃止 | ブロックと「要件一覧」の行を消し、「廃止した要件」表へ移す（ID は欠番。廃止日・理由・出典を書く） |

あわせて：

- **予約した ID の重なり**：他の spec がすでに同じ ID で done になっていた場合など、常設要件に同じ ID があれば、ここで次の空き番号に振り直す。そのときは spec・tasks.md・テストのタグ（`[<要件ID>/AC-n]`）も合わせて直し、ユーザーに報告する。
- **出典**：移した要件の「出典」と、新しく足した・書き換えた AC の末尾に `（出典: specs/NNN）` を書く。
- **非機能要件**：領域固有なら領域ファイルの表へ、全体共通なら `common.md` へ（`COMMON-N-nnn`）。
- **スコープ外**：区分が「やらない」ものは、領域ファイルの「この領域でやらないこと」へ移す（理由・対応する要求・出典付き）。「後回し」は移さず、次の spec 候補として報告に載せる。
- **新しい領域**：spec の「新しい領域」にあるものは、`requirements/README.md` の領域一覧に登録し、雛形から領域ファイルを作る。どの領域に入れるか迷う要件があればユーザーに聞く。
- 変えた領域ファイルの `updated:` を今日にする。

### 4. 周辺の文書を更新する

- 新しい用語が出ていれば `docs/product/glossary.md` に足す（コード上の名前も）。
- 構成・レイヤー・データの流れが変わっていれば `docs/architecture.md` を更新する。
- ADR にすべき判断（L ティアの design.md の「残すべき ADR の候補」など）があれば**提案する**。自動では作らない。
- vision に影響がありそうなら（ゴールの達成で課題が無くなった、など）`/product-vision update` を案内する。

### 5. 全体を機械点検する（タイミング⑦）

`spec-check` を呼ぶ（Skill ツールで `spec-check`、引数 `all`）。移し忘れ・ID の重なり・テストの無い AC・廃止した AC を指したままのテストなどが分かる。

- rules.md 第12章の「直し方」で、**未解決の矛盾・欠落が0件になるまで直す。**
- この spec と関係の無い、前からある指摘が出たら、今直すか、承知で進めるかをユーザーに決めてもらう。
- **未解決の矛盾・欠落が残っていれば done にしない。**

### 6. done にする

spec を `status: done` にし、`done:` に今日の日付を書く。

### 7. 全体レビューを勧めるか判断する（タイミング⑧）

手順5の `spec-check` の出力の「情報」に、最後の全体レビュー以降に done になった spec の件数が出る。CLAUDE.md の「全体レビューを勧める done の件数」（既定3件）以上なら、`docs-review all` の実行を勧める。**実行はユーザーが決める。**

### 8. 報告する

- 変更したファイルの一覧
- 常設要件に移した要件（新規・変更・廃止）と、振り直した ID があればその対応
- 次の spec の候補（スコープ外の「後回し」、レビューで次に回したもの）
- 残った「注意」の指摘
- ADR の提案、`/product-vision update` の案内（あれば）

## やらないこと

- 実装やテストを直す（spec-verify の指摘は一覧で見せて中止する。直すのは実装の作業として別に行う）
- spec に書かれていない変更を常設要件に入れる
- ADR を自動で作る

# API・IPO一覧づくり（詳細設計）

Vモデルの **詳細設計**（対応する検証は単体テスト）にあたる文書を1本作る。
やることは2つだけ — **API（インターフェース）の一覧を整理し、業務フローごとの
Input / Process / Output をそこへ紐付ける。**

03（画面）で決めた操作と、04（データ）で決めた器のあいだを繋ぐのがこの文書。
**「どの操作が、どのインターフェースを通って、どのデータをどう変えるか」**を確定させる。

成果物の骨組みは同ディレクトリの3つのテンプレート。**どれを使うかは手順2で判定する。**
章立てと表の列を見るための参考であって、埋め方の指示書ではない。分量はそこに合わせにいかなくてよい。

| テンプレート | 使う場面 |
|---|---|
| `template-rest.md` | 自前のHTTP API（Web・モバイル ↔ 自前バックエンド） |
| `template-client-sdk.md` | BaaSへ直接アクセス（Firestore / Supabase 等のSDK ＋ サーバレス関数 ＋ 外部サービス） |
| `template-cli.md` | CLI・バッチ・エージェント（HTTP APIを持たない。コマンド ＋ 内部ツール ＋ 外部API） |

**前提条件**: **データ構造設計書（04-db.md）が存在すること。**無い状態でこのスキルを始めない。
（04は03を、03は02を前提に作られるので、04があれば02・03もある。無ければ `db-doc` へ回す）
**使う場面**: 04が固まり、実装に入る前。インターフェースの契約を確定させるとき。
**やり方**: **Claudeが01〜04から自律的に全章を書き切る。**ユーザーは**成果物をレビューする役**。

## このスキルの進め方（他の文書スキルと違うところ）

**人間に判断を仰ぐのは、原則として最後の1回だけ。**
`db-doc` と違い、**着手時の質問もしない。**形態（HTTP API / BaaS直アクセス / CLI）は
**04と02とリポジトリから判定できる**ので、聞かずに決めて宣言する。

1. **着手時**: 聞かない。01〜04とリポジトリを読み、**形態を判定して宣言してから**書き始める
   （判定の根拠も一緒に出す）。
2. **途中**: 01〜04を正典として**全章を最後まで自律的に書き切る。**
   章ごとに「これでいいですか」と伺いを立てない。判断が要る箇所は決めて書き、
   **決めた事実を記録しておく。**
3. **完了前**: 書く過程で**重大な確認事項**（後から直すと外部との契約が壊れる／取り返しがつかない）
   が出ていたら、**完了させる前にまとめて確認する**（手順5）。
   出ていなければこの段は飛ばす。**「重大」の線引きは手順5の表が正典。**
   軽い判断まで持ち込むと自律の意味が消えるので、そこだけは厳しく絞る。
4. **提出前**: **`api-ipo-doc-review` を必ず1回走らせる**（手順7）。省略しない。
5. **最後**: 完成品をユーザーがレビューする。
   このときClaudeは **「自分で決めた箇所」の一覧を必ず添える**（手順8）。

> ここで数えているのは**設計の中身についての判断**。
> 「どのファイルを対象にするか」「既存の05を上書きしてよいか」のような
> **作業の段取りの確認（手順0）は、いつ聞いてもよい。**

1章ずつ見せて赤入れを受ける進め方は**しない。**
API設計は章どうしの依存が強く（一覧 → IPO → 詳細）、途中で1つ変えると全章に波及する。
**通しで書き切ってから、まとめて直す方が速い。**

## 大原則

1. **入力は 01・02・03・04。04が無ければ着手しない。**
   04（データ構造設計書）が必須。**どのデータをどう読み書きするかがAPIの中身**であり、
   器を見ずに契約は書けない。03（画面）と02（機能・受入基準）も必ず併読し、01は背景の確認用。
   04が見当たらなければ探し、それでも無ければ**この文書を書き始めず** `db-doc` へ案内する
   （03すら無ければ `spec-doc` から）。
   02〜04に穴があるだけなら、05の中で補わず
   **`requirement-doc-review` / `spec-doc-review` / `db-doc-review` で上流を直してから**戻ってくる。
2. **形態は推測せず、実物を見て判定する。**「どんなAPIにしますか」と投げない。
   04の前提・02の非機能要件・リポジトリの実装を読み、**判定した結果と根拠を宣言してから**書く
   （手順2）。既存のAPI・データアクセス層があるなら、**それは設計の入力**になる。
3. **一覧とIPOと詳細で、同じものを3回書く。**この文書の価値は**照合できること**にある。
   1章に無いインターフェースが2章のフローに出てくる、3章に詳細が無い、は不足そのもの。
   **3か所で数と名前が合うこと**を最後まで守る。
4. **トレーサビリティを双方向で切らさない。**
   - 1章の各行に「機能(②)」と「対応フロー」を、2章の各フローに「対応機能(②)」と「画面(③)」を、
     3章の各項目に「対応データ(④)」と「対応フロー」を必ず書く。
   - 逆向きにも照合する — **02の全機能・03の全画面操作・04の全データストア**が、
     どこかのインターフェースに現れていること。現れないなら、なぜ不要かを書く。
5. **例外を1つ残らず契約にする。**02の例外・バリデーションと、03のエラー・例外表示は、
   **すべて3章のエラー欄（またはIPOの例外行）へ落ちる。**
   ここを埋めないと、実装者が想像でエラーを作る。
   **401（未認証）/ 403（権限なし）/ 404（不在）/ 400（入力不正）を混ぜない。**
   HTTPを持たない形態でも、**例外種別と画面へ返す状態**として同じ粒度で書く。
6. **型は書かない。意味を書く。**フィールドの型・JSON構造・バリデーションのSSOTは
   04（またはスキーマ定義ファイル）。**05が定義するのは「その値が何を意味するか」と
   「エラーが何を意味するか」。**型をここで二重定義すると、必ず食い違う。
   **どこがSSOTかを冒頭で明示する。**
7. **「どういう契約か」まで。「動くコード」は書かない。**
   ルーティング・コントローラ・SDK呼び出し・バリデーション実装は Build フェーズ。
   本書は**一覧・IPO・入出力の意味・エラー意味論**までを正とする。
   末尾にその線引きを1行で書き添える。
8. **「未定」「TBD」「要確認」を本文に残さない。**
   決め切れないものも**暫定で決めて書き、決めた箇所として手順8で申告する。**
   保留を残すと、下流の実装とテストがそこで止まる。
   **ただし「重大な確認事項」だけは暫定で押し切らず、完了前に聞く**（手順5）。
   聞くと決めた項目も、**本文には暫定案を書き込んだうえで**印を付けておく。
9. **表を主体にする。**散文は章冒頭の「目的」と、表にすると死ぬ補足だけ。
10. 日本語で書く。ただし**識別子（パス・メソッド名・パラメータ名・エラーコード）は
    実装で使う表記のまま**書く。

## 手順

### 0. 既存の設計書があるか確認する

`docs/requirements/` などに `05-api-ipo.md` が既にあるか探す。
**候補が複数見つかったら、どれのことかユーザーに聞く**（事実確認なので聞いてよい）。

- **ある** → このスキルの出番ではない。**`api-ipo-doc-review` へ回す**（点検して不足を埋める）。
  全面書き換えは、ユーザーがそう言った場合だけ。
- **ない** → 1へ進む

出力先の既定は、04と同じディレクトリの `05-api-ipo.md`。既存の連番規則があればそちらに合わせる。

### 1. 01・02・03・04 を読む

- **04（データ構造設計書）を全文読む。**一覧・定義・制約・インデックス方針まで。
  **書き込み系APIが触る列と制約（NOT NULL・UNIQUE・ON DELETE）が、そのまま
  バリデーションとエラーの根拠になる。**冒頭の前提（DBエンジン・DBなしの理由）も読む。
- **03（仕様書）を全文読む。**画面ごとのUI要素・操作・エラー表示まで。
  **画面の操作1つ1つが、どれかのインターフェース呼び出しになる。**
  一覧の並び順・絞り込みはクエリパラメータの根拠。
- **02（要件定義書）を全文読む。**機能一覧・受入基準・スコープ・非機能要件。
  **非機能要件の認証・セキュリティは0章の下敷き**、スコープは**どこまで設計するか**の線引き。
- **01（要求定義書）**は背景の確認用。誰がどの範囲を触れるか（権限の境界）を読む。

読み終えた時点で、**全章を最後まで書き切れる状態**にする。
足りない情報は02〜04から**導く**。導けないものは暫定で決める（大原則8）。

### 2. 形態を判定して宣言する（**聞かずに決める**）

**まず自分で調べる。**

調べる先（あるものだけ）:

- **04の冒頭の前提** — DBエンジン、あるいは「DBを持たない」理由。ここが最大の手がかり
- **サーバ側の実装** — ルート定義（`routes/` / `app.py` / `main.go` / `*.controller.ts`）、
  APIスキーマ（`openapi.yaml` / `schemas/`）、サーバレス関数（`functions/`）
- **クライアント側のデータアクセス** — SDKを直接呼んでいるか、HTTPクライアント経由か
  （`FirebaseFirestore.instance` / `supabase.from(` / `fetch(` / `dio` / `axios`）
- **アクセス制御の実体** — `firestore.rules` / `storage.rules` / ミドルウェア
- **エントリポイント** — CLIの引数定義（`argparse` / `commander` / `cobra`）、
  バッチのスケジュール定義
- **02の非機能要件・03の技術方針** — 認証方式が名指しされていないか

| 判定 | 使うテンプレート |
|---|---|
| 自前のHTTPサーバがある／作る | `template-rest.md` |
| クライアントがBaaSのSDKで直接読み書きする | `template-client-sdk.md` |
| 利用者の入口がコマンド・スケジュール実行で、HTTP APIを持たない | `template-cli.md` |

**混在するならテンプレートを混ぜる**（例: アプリはFirestore直アクセスだが、集計だけ
サーバレス関数 → `template-client-sdk.md` を土台に、関数を別種別として1章に立てる）。
**種別の列で区別すれば1本の文書に収まる。**無理に1形態へ寄せない。

判定結果と根拠を**1〜2行で宣言してから**3へ進む。
**どちらとも判定できないときだけ**、手順5の重大な確認事項として扱う
（形態を誤ると全章が無駄になるため、ここだけは押し切らない）。

> 既存のAPI・データアクセス層が現に動いている場合、**それは制約であって設計対象ではない。**
> 変えるなら「なぜ変えるか」と「移行の段取り」を本文に書く。黙って別の形に描き直さない。

### 3. 全章を自律的に書き切る

**その場では質問しない。**01〜04からインターフェースを起こすのはClaudeの仕事。
重大な判断に当たっても、**書く手を止めずに印を付けて進む**（下記）。
空欄・`{}`・「TBD」を残したまま出さない。

書く順序（依存の順）:

0. **命名規約を先に決める** — パスは複数形か、階層で所有関係を表すか、
   エラーコードの体系（`{RESOURCE}_NOT_FOUND` など）、パラメータ名の表記。
   **1章で名前を書き始める前に決める**（後から揃え直すと全章に波及する）。
1. **冒頭の引用ブロックと0章（認証・認可）** — 02の非機能要件を引き、
   **各インターフェースが「認証を要するか・どの権限が必要か」の判定基準**をここで確定させる。
   02に方針が無ければ、ここで決めて重大な確認事項として印を付ける。
   **スコープ（どのFUNCまでを本書の対象にするか）もここで宣言する。**
2. **1章（一覧）** — 02の機能一覧と03の画面操作を1つずつ舐め、必要なインターフェースを列挙する。
   「機能(②)」「認証」「必要権限」「対応フロー」を埋めながら書くと、抜けがその場で見える。
   **CRUDの欠けに注意**（一覧・詳細・作成・更新・削除のうち、03の画面が使うものが揃っているか）。
3. **2章（フローごとのIPO）** — ここが本書の中心。**フローは「ユースケース」で切る**
   （画面単位でもAPI単位でもない）。03の画面遷移と02の正常フローが下敷き。
   各フローに**例外の行**を必ず1行以上置く。
4. **3章（詳細）** — 1章の**全インターフェース**を1つずつ落とす。抜かさない。
5. **末尾** — 「動く実装はBuildフェーズの成果物」の1行と「次のステップ」。

**判断したことは、その場で作業メモに残す**（どこを02〜04から起こし、どこを自分で決めたか）。
手順8でそのまま使う。**重大な確認事項に当たったものは、メモ上で分けておく**（手順5で使う）。

**手を止めない。**重大な判断に行き当たっても、そこで質問して待たない。
**暫定案を書き込んで印を付け、残りを最後まで書き切ってから**手順5でまとめて聞く。

**印は `<!-- ASK: 何を確認したいか -->` のHTMLコメントで入れる。**
本文の表示には出ないので、途中で中断されても文書が壊れない。
**「要確認」「TBD」の語は本文に書かない**（大原則8のgrepに引っかかり、
本当の書き残しと区別できなくなる）。

**書いたらファイルへ。**まとめて最後に書かない（`/clear` や中断で消えるため）。

### 4. 上流の不足に気づいても、ここで埋めない

書いている途中で02〜04の不足に気づいたら（例外が定義されていない、画面が使う項目に器が無い、
機能の受入基準が曖昧）、**手を止めず、05側では暫定で辻褄を合わせて**手順8の報告に積む。
02・03・04そのものを書き換えるのは、それぞれのレビュースキルの仕事。

### 5. 重大な確認事項があれば、完了前に確認する

**該当が無ければこの手順は飛ばす。**（飛ばしたこと自体は報告しなくてよい）

#### 何が「重大」か

次の**どれかに当てはまるものだけ**が重大。**当てはまらないものは聞かずに決める。**

- **後から直すと、自分のコードだけでなく既に外にあるもの**（公開済みAPI・配布済みクライアント・
  外部システム）**を壊す**
- **間違えたときに取り返しがつかない**（送金・送信・削除が二重に走る、漏れたものが戻らない）
- **01〜04にもコードにも根拠が無く、外部の仕様やユーザーの頭の中にしかない事実に依存する**

具体的には次のとおり。

| 重大（完了前に聞く） | なぜ |
|---|---|
| **認証・認可の方式**（02の非機能要件に定義が無く、ここで決めることになった場合） | 全インターフェースの前提。後から変えるとクライアントも含めて総取り替えになる |
| **公開済み・配布済みのインターフェースを破壊的に変更する必要が出たとき** | 古いクライアントが動かなくなる。移行期間と互換の判断が要る |
| **外部サービス・サードパーティAPIの仕様に依存する部分**（実際のパラメータ・制限・課金） | 推測で書くと実装が破綻する。実物の仕様を確かめる必要がある |
| **不可逆・課金・送信を伴う操作の再実行（冪等性）の方針** | 二重実行の被害が戻らない |
| **個人情報・秘密情報を、どのインターフェースで運ぶか／クライアントへ返すか** | 法令・規約が絡む。Claudeが決めてよい範囲を越える |
| **02・03・04どうしが矛盾していて、どちらかを選ばないと契約が決まらないとき** | どちらを正とするかは上流の判断 |
| **スコープ外にはみ出すインターフェースを作らないと成立しないと判明したとき** | 作らないと決めたものを勝手に作ることになる |
| **形態（HTTP API / BaaS直 / CLI）が調べても判定できないとき**（手順2） | 誤ると全章が無駄になる |
| **業務の事実を知らないと決められないもの**（想定同時実行数・レート制限・締め時刻・SLA） | 推測すると桁違いの設計になる |

| 重大でない（聞かずに決めて手順8で申告） | なぜ聞かなくてよいか |
|---|---|
| パスの表記・階層の切り方、リソース名の単複 | 公開前ならあとで直せる |
| PUT / PATCH の選択、更新の粒度 | 実装前なら差し替えられる |
| ページネーションの既定値・上限、並び順の既定 | あとで直せる |
| エラーコードの命名体系 | 文書内で一貫していれば足りる |
| フローの切り方の粒度、フローの数 | 記述の整理であって契約ではない |
| レスポンスのフィールド名・入れ子の形 | 実装前なら差し替えられる |
| どのステップを1行にまとめるか | 同上 |

> 迷ったら**「これを後から変えるとき、自分のコード以外に何を直させるか」を1文で言えるか**
> を考える。外（公開済みクライアント・外部システム・法令）に及ぶなら重大。
> 自分のコードだけなら聞かない。

#### 聞き方

- **全章を書き切ってから、まとめて聞く。**見つけた時点で止めない（手順3）。
- `AskUserQuestion` で、**一度に聞くのは2件まで。**3件以上あれば**影響の大きい順**に刻む。
- 選択肢は**その設計の文脈に落とした具体案**にする。抽象語で聞かない。
  妥当な案を先頭に置き `（推奨）` を付け、**各案に「これを採ると何が変わるか」を一言添える。**
  暫定で本文に書き込んだ案がどれかも明示する。
- **なぜ聞くのかを1行で言う**（「配布済みクライアントが動かなくなるため」）。
- 「まだ決まっていない」と言われたら、**何が分かれば決まるのかを言語化して、その一点だけ聞く。**
  それでも決まらないなら、**持ち帰るか暫定で確定させるかをユーザーに選んでもらう。**
  暫定で確定させる場合は、**そう決めた事実と、後で変えるときの影響を本文に1行残す。**

#### 答えが返ったら

- **本文の暫定案を差し替え、印を消す。**
- **波及を必ず追う。**0章の方針・1章の一覧（認証／権限の列）・2章のIPO・3章の詳細
  （リクエスト／レスポンス／エラー）— **この4箇所がそろって直っているか**を毎回確認する。
  ここが最も取りこぼす。
- 差し替えた内容は、手順8の一覧に**ユーザーが決めたもの**として載せる
  （Claudeが決めたものと混ぜない）。

### 6. 自己点検する

`api-ipo-doc-review` を走らせる前に、**機械的に潰せるものだけ**自分で潰す。

- [ ] 1章のインターフェース数と、3章の詳細の数が**一致**するか
- [ ] 2章のフローに出てくるインターフェースが、**全部1章に実在**するか（名前も一致するか）
- [ ] 02の**全機能ID**が、1章のどこかの「機能(②)」に現れているか
- [ ] 03の**全画面**が、2章のどこかの「画面(③)」に現れているか
- [ ] 04の**全データストア**が、2章か3章の「対応データ(④)」に現れているか。
      逆に、04に無いテーブル・コレクションを参照していないか
- [ ] 3章の全項目に、リクエスト・レスポンス（成功）・エラーの**3つが揃っている**か
- [ ] 「未定」「TBD」「要確認」「{」が本文に残っていないか（**grepで確認する**）
- [ ] **`ASK:` の印が1つ残らず消えているか**（grepする。暫定案が残っていないか）
- [ ] 実装コード・SQL・テストケースを書いていないか（設計書の範囲を越えていないか）

引っかかったら**直してから**7へ進む。

### 7. `api-ipo-doc-review` で点検する（**省略しない**）

05が書き上がったら、**ユーザーへ出す前に必ず `api-ipo-doc-review` スキルを1回走らせる。**
点検の観点（章の揃い・02〜04とのトレーサビリティ・IPOの完備・エラー意味論・
章をまたいだ整合・混入・未確定の残り）は**そちらが正典**なので、
ここで独自のチェックリストを作らない。

**点検していない成果物をレビューに出さない。**
指摘はその場で直し、直した結果を手順8の報告に含める。

> レビュー側は「作成スキルから呼ばれたとき」の進め方を持っている。
> **点検結果をこちらへ返すところまでがレビューの仕事**で、そこで承認を取らせない。

### 8. ユーザーにレビューを依頼する

**ここが人間の出番。**成果物とあわせて、次の5つを必ず出す。

1. **作ったファイルのパス**と、**判定した形態とその根拠**（手順2）
2. **インターフェース一覧のダイジェスト**（種別・名前・機能ID）。全文を読ませる前の見取り図
3. **決めた箇所の一覧** — 「何を・どう決めたか・なぜそう決めたか」を表で。
   **手順5でユーザーが決めたもの / Claudeが決めたもの / 01〜04に根拠があるもの**の3つを
   区別して見せる。**レビューの時間はClaudeが決めたものに使ってもらう。根拠の弱い順に並べる。**
4. **02・03・04に対して気づいた不足**（手順4）。
   **05の中で勝手に補わず、上流を直すべきものとして報告する**（振り先のスキル名も添える）。
5. **手順7のレビュー結果** — 何を指摘され、どう直したか。

**レビュー結果はその場でファイルに反映する。**指摘を溜めない。
反映後、変えた箇所を一覧で見せて**承認をもって完成**とする。自分の判断で締めない。

### 9. `db-api-crossreview` を勧めて終わる

赤入れが片付いたら、**最後に必ず次を伝える。**言わずに締めない。

> 05が固まったので、**`db-api-crossreview` で 04 × 05 の横断レビューを
> 走らせることをおすすめします。**手順7の `api-ipo-doc-review` は「05を直すために」04を
> 読む片方向の点検なので、**04側が古い・04側が足りない**タイプの食い違い
> （05が必要とする項目の器が04に無い、05のクエリを04のインデックスが解けない、
> 04の分離キーと05の認可の境界がずれている）は拾い切れません。
> 横断レビューは文書を書き換えず、**どちらを直すべきかを付けた指摘レポートだけ**を出します。

**走らせるかはユーザーが決める。**このスキルの中で勝手に起動しない。
走らせると言われたら `db-api-crossreview` へ切り替える。

そのうえで「これで06（シナリオテスト）／Buildへ進んでよいか」を確認する。

## 各章に必要な項目

**必要なのは「どの項目があるか」まで。分量は問わない。**
章タイトルは**形態に合わせて言い換える**（下表）。

| # | HTTP API | BaaS直アクセス | CLI・バッチ |
|---|---|---|---|
| 冒頭 | 引用ブロック（Vモデル・前提・型のSSOT・スコープ） | 同左＋**「API」の定義（何を指すか）** | 同左＋**「API」の定義** |
| 0 | 認証・認可の詳細 | 認証・認可の詳細（**アクセス制御の実体がどこか**） | 認証の方針（**外部APIのキー管理**。1章の冒頭に畳んでよい） |
| 1 | API一覧 | インターフェース一覧 | インターフェース一覧 |
| 2 | フローごとのIPO | 同左 | 同左 |
| 3 | エンドポイント詳細 | インターフェース詳細 | インターフェース詳細 |
| 末尾 | 範囲を切る一文 ＋ 次のステップ | 同左 | 同左 |

### 冒頭の引用ブロック

```
> Vモデル: 詳細設計 / 対応する検証: 単体テスト
> 先にAPIの全体像（一覧・認証）を示し、その上で業務フローごとのデータの流れ
> （Input/Process/Output）がどのAPIで実現されるかを整理する。
```

続けて**前提**を書く。**必ず入れるもの**は3つ。

- **認証・認可の方針の在り処**（02のどこで定義済みか。無ければ0章で決めた旨）
- **型のSSOTがどこか**（04のデータ定義 / スキーマ定義ファイル）。
  **05は契約の意味とエラー意味論を定義する**、と線を引く
- **スコープ**（本書がどのFUNCまでを対象にするか。Scope 2 以降を別途とするならそう書く）

HTTP APIを持たない形態では、**「ここでの API＝インターフェース が何を指すか」を
種別ごとに列挙してから**本文へ入る（テンプレート冒頭の①②③の形）。
**定義しないまま「APIが無いので書けない」と止めない。**

### 0. 認証・認可の詳細

02の非機能要件を**引いて詳細化する**（そこに無いものだけ、ここで決める）。

- 利用者の種別ごとの認証方式と、**トークンをどこに載せるか**
- **有効期限・失効の扱い**（ログアウトを専用APIにするか、クライアント破棄だけか。その理由）
- **権限の境界**。誰がどの範囲を触れるか、**それをパス・ルールのどこで表すか**
- **秘密情報の扱い**（環境変数管理・クライアントに埋めてよい値の線引き）
- BaaS直アクセスなら、**認可の実体はセキュリティルール**であることを明記する
  （アプリ側のコードは認可の根拠にならない）

### 1. 一覧

表: `# / （形態により）種別 / インターフェース / 機能(②) / 呼び出し元 / 認証 / 必要権限 / 対応フロー`

- **機能(②)** は `FUNC-01` の形で02を指す。02に無い呼び名を発明しない。
- **認証**は「要 / 不要」を全行に書く。空欄を作らない。
- **必要権限**は、要認証の行に**誰なら通るか**を書く（`管理者（対象物件の管理権限）`）。
- **対応フロー**を入れると、1章と2章の照合が機械的にできる。**空欄を作らない。**
- HTTP APIなら**メソッドとパスの組で1行**（同じパスのGET/POSTは別行）。
- 外部サービスも**1行として立てる**（呼び出し元と、キーの管理方法を備考に書く）。
- Scope 2 以降のものを載せるなら `（Scope2）` の注記を付ける。

### 2. フローごとのIPO

**この章が本書の中心。**フローの切り方を最初に1行で宣言してから並べる。

- **フローは「ユースケース（利用者が1つの目的を達成する単位）」で切る。**
  開始トリガーから結果が出るまでを1フローとし、**画面・APIを複数跨いでよい。**
  画面単位・API単位で切らない（それでは一覧の焼き直しになる）。
- 各フローの見出し直下に **`**対応機能(②)**: FUNC-xx ／ **画面(③)**: SCR-xx`** を置く。
- 表: `ステップ / Input / Process / Output / 対応API / 対応データ(④)`
  - **末尾2列の名前は形態に合わせて言い換えてよい**（`対応API` → `対応インターフェース`、
    `対応データ(④)` → `対応テーブル(④)`）。**ただし1つの文書の中では表記を統一する**
    — 章をまたいだ照合がこの列名で行われるため、揺れると点検が目視に落ちる。
  - **Input** = そのステップに入ってくるもの（利用者の操作・前ステップの出力・受け取る値）
  - **Process** = **何をするか。**「処理する」で終わらせない。
    どのデータをどう変えるか、どう絞り込むかまで書く
  - **Output** = **出てくるもの。**画面に何が出るか、何が保存されるか。
    **03のエラー・完了表示と文言レベルで矛盾させない**
- **各フローに例外の行を必ず1行以上置く。**02の例外・03のエラー表示が落ちる場所。
  「例外」行の Input には**発生条件**、Process には**検知して何をするか**、
  Output には**利用者に何を見せるか**を書く。
- ループする処理（1件ずつ繰り返す）は、**「IPOの繰り返し」として1フロー**にまとめてよい。
  そのことを見出し下に1行書く。

### 3. 詳細

1章の**全インターフェース**を1つずつ。小見出しを立て、**まずメタ情報を箇条書き**で置く。

- HTTP APIなら `Method / Path / 目的 / 認証 / 必要権限 / 対応データ(④) / 対応フロー / スキーマ`
- それ以外は `種別 / 目的 / 呼び出し元 / 対象パス・引数 / 認可 / 対応データ(④) / 対応フロー`

続けて**3つの表**を必ず置く。**1つでも欠けたら不足。**

| 表 | 列 | 守ること |
|---|---|---|
| リクエスト（入力） | `パラメータ / 必須 / 意味` | パス・クエリ・ボディ・ヘッダーの**どこに載るか**を書く。既定値・上限も意味の列へ |
| レスポンス（成功・出力） | `フィールド / 意味` | **何を表す値か**を書く。0件・null になる条件も書く |
| レスポンス（エラー） | `ステータス / 意味 / エラーコード` | **意味は具体的に**（「不正なリクエスト」ではなく「本文が空」） |

共通で守ること:

- **型を書かない。**（型は04・スキーマがSSOT。表の下に「型・構造は〜を参照」と1行置く）
- **エラーの網羅**。最低限、次を漏らさない。
  - 入力不正（400 VALIDATION_ERROR）
  - 未認証（401 UNAUTHORIZED）と権限なし（403 FORBIDDEN）— **混ぜない**
  - 対象不在（404 `{RESOURCE}_NOT_FOUND`）
  - サーバ内部エラー（500 INTERNAL_ERROR）
  - **02・03に固有の例外**（重複・状態不整合・外部サービス障害・レート超過）
- HTTPを持たない形態では、ステータス列の代わりに**例外種別／停止条件**を書く。
  **リトライするか・何回か・超えたらどうするか**まで書く。
- **副作用のあるインターフェースには、冪等性の扱いを書く**
  （再実行したら二重に起きるか、防ぐならどう防ぐか）。

### 末尾

設計書の範囲を切る一文を引用で置く（形態に合わせて言い換える）:

```
> 実際に動くルーティング・コントローラ・バリデーション実装は Build フェーズの成果物とする。
> この設計書ではAPI一覧・IPO・入出力の意味・エラー意味論までを正とする。
```

そのうえで「次のステップ」。文書の連番が違うプロジェクトでは、その次工程の名前に合わせる。

## やらないこと

- **動くルーティング・コントローラ・SDK呼び出し・バリデーション実装を書くこと** → Buildフェーズ
- **型・JSON構造・バリデーション規則の二重定義** → 04またはスキーマがSSOT。**参照で済ませる**
- **テーブル定義・カラム・制約を書き直すこと** → 04の内容。05は参照するだけ
- **画面構成・UI要素・モック** → 03の内容
- **テストケース・テスト手順・テストデータ** → 06以降
- **要件定義書（02）の不足を埋めること** → `requirement-doc-review`。
  05の中で機能や受入基準を足さない（気づいたら手順8で報告する）
- **章ごとにユーザーの承認を取りながら進めること** → 手順8でだけ人間に渡す
  （重大な確認事項があるときだけ手順5を挟む）
- **インフラ・デプロイ構成・スケーリングの設計** → インフラ設計（07）
- **`api-ipo-doc-review` を走らせずに提出すること**（手順7は省略しない）

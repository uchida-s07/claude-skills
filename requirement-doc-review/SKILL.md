# 要件定義書のレビュー

対象は要件定義書（`02-requirement.md`）1本。**新規に書き直さない。**
既にあるものに観点を当て、**不足だけを埋める。**

作成は `requirement-doc` スキルの仕事。まだ文書が無いならそちらへ回す。

**要求定義書（01）は照合用に必ず読む。**02は01を「何を作るか」に翻訳した文書なので、
01を見ずに過不足は判定できない。ただし**直すのは02だけ。**
01側に不足を見つけたら `request-doc-review` へ回す。

## 大原則

1. **全文を読んでから判断する。**一部だけ見て「足りている」と言わない。
   **01と02の両方**を読む。
2. **勝手に書き足さない。**不足を埋めるには判断が要る。ユーザーに聞いてから直す。
3. **決めるのは人間。**推奨案は出してよいが、承認なしに決定として書かない。
4. **指摘は場所と一緒に出す。**「FUNC-03の例外・バリデーションが無い」のように、
   どこの何が足りないかを機能IDで言う。
5. **03以降（仕様・DB・API）の内容を要求しない。**画面構成・テーブル定義・
   エンドポイントが無いのは不足ではなく正しい状態。
6. **01の内容を蒸し返さない。**課題設定やペルソナへの異議はこのレビューの範囲外。
   02が01と食い違っているかどうかだけを見る。

## 手順

### 1. 対象を特定する

`docs/requirements/02-requirement.md` など、要件定義書の場所を確認する。
複数あるなら、どれを見るのかユーザーに聞く。見つからなければ、
**まだ作成の段階なので `requirement-doc` を使うよう案内して終了する。**

あわせて**対になる要求定義書（01）の場所も特定する。**
01が見つからない場合は、トレーサビリティの観点（B）を当てられないことを伝えたうえで、
残りの観点だけで点検するか、先に01を作るかをユーザーに選んでもらう。

### 2. 全文を読む

飛ばし読みしない。02の4章と「次のステップ」を最後まで通し、**01も通しで読む。**

### 3. 観点を当てる

下の「点検の観点」を全部当てる。
**B（トレーサビリティ）とD（受入基準）は漏れが最も出るので必ず見る。**

### 4. 結果を提示する

- **不足がある場合** → 見つかった不足を**一覧でユーザーに提示してから**直しに入る（手順5へ）
- **不足がない場合** → 何も書き換えない。
  **「不足のない要件定義書が既にある」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのかも一緒に伝える（当てた観点と、その結果を示す）

### 5. 不足を埋める

1件ずつ「質問 → ドラフト → 赤入れ → 確定 → ファイルへ書く」で進める。

- 埋めるのに必要な事実は**ユーザーに聞く**。推測で埋めない
- ただし**01から一意に導ける記述**（対応する要求の欄、01の課題に対応する機能の概要など）は、
  先に案を書いて見せてよい。**書いた根拠を01のどこかで示す**こと
- 「まだ決まっていない」と言われたら、選択肢を2〜3案に絞り、推す案に `（推奨）` と理由を添えて聞き直す。
  それでも決まらないなら、持ち帰るか暫定で決めるかを**ユーザーに選んでもらう**
- **機能を増減させたら、2章・3章（スコープ）・4章への波及を必ず追う。**
  1章に足した機能の要件が2章に無い、スコープ表に載っていない、が起きやすい
- 一度に聞くのは2件まで。まとめて並べない
- **直した箇所はその都度ファイルへ書く。**まとめて最後に書かない

### 6. ユーザーの承認をもって完了とする

直した内容を報告し、承認を得て終わる。自分の判断で締めない。

- 何が足りず、どう直したかを短く一覧で見せる
- 決着させた未確定事項があれば、何をどう決めたかも見せる
- **03（仕様書）が既にある状態で02を直したなら、`requirement-spec-crossreview` を勧める。**
  02を直した時点で**03が古くなっている可能性がある**（足した機能に画面が無い、
  変えた例外に03が追随していない、リネームした機能名を03が古いまま使っている）。
  横断レビューは文書を書き換えず、02×03の食い違いだけを指摘レポートで出す。
  **走らせるかはユーザーが決める。**ここで勝手に起動しない
- 03がまだ無いなら「これで03（仕様書）へ進んでよいか」を確認する

## 点検の観点

### A. 章と項目が揃っているか

| 章 | 揃っているべきもの |
|---|---|
| 冒頭 | Vモデル上の位置（要件定義 / システムテスト）と、この文書で何を定義するかの引用ブロック |
| 1. 機能一覧 | 表（`# / 機能ID / 機能名 / 概要 / 対応する要求`）。必要なら技術方針・扱うデータの補足 |
| 2. 各機能の要件 | 機能IDごとに 概要 / 事前条件 / 正常フロー / 例外・バリデーション / 受入基準 の5項目 |
| 3. スコープ | 区分の定義 / Scope 1〜3 の表（`機能ID / 機能名 / 備考`）/ Out of Scope（`項目 / 実装しない理由`） |
| 4. 非機能要件 | 表（`カテゴリ / 要件`）。性能 / セキュリティ / 可用性 / ユーザビリティ / 保守性 |
| 末尾 | 次のステップ |

**行数や箇条書きの数は問わない。**「項目があるか」だけを見る。

2章は**機能ID1つにつき5項目**。1つでも欠けている機能があれば不足として出す。

### B. 要求定義（01）とのトレーサビリティ（最も漏れが出る）

**両方向で照合する。**片方向だけだと必ず抜ける。

**01 → 02（拾い漏れ）**

- 01の課題一覧の各行が、**どこかの機能ID**で解かれているか
- 01のユーザージャーニーの各ステップが、機能かOut of Scopeのどちらかに落ちているか
- 01のビジネスゴール・ユーザーゴールに対応する機能があるか
- **どちらにも出てこない項目があれば、それが不足。**
  「機能にしない」判断ならOut of Scopeに理由付きで書く

**02 → 01（出どころ不明）**

- 機能一覧の「対応する要求」欄がすべて埋まっているか
- そこに書かれた参照先が**01に実在するか**（`課題4` と書いてあるのに01の課題が3つまで、など）
- 01のどこにも根拠が無い機能が紛れていないか。
  あるなら、01を直すのか（→ `request-doc-review`）02から落とすのかをユーザーに聞く

### C. 章をまたいだ整合

- 1章にある機能IDが、**2章にすべて登場するか**。逆に2章にだけある機能IDが無いか
- 1章・2章の機能IDが、**3章のスコープ表にすべて現れるか**（どのScopeにも無い機能が無いか）
- 機能名が章をまたいで揃っているか（1章と2章で呼び名が違わないか）
- 2章の事前条件が、前工程にあたる機能の出力と噛み合っているか。
  「FUNC-03の事前条件がFUNC-02の出力を前提にしているのに、FUNC-02がScope 2」のような
  **スコープの前後矛盾**が無いか
- **Scope 1 だけで01のユーザージャーニーが1周するか。**
  1周しないなら、Scope 1 に足りない機能があるか、ジャーニーの想定が過剰か

### D. 受入基準が検証可能か（最も漏れが出る）

- 全機能に受入基準があるか
- **システムテストで○×が付く文になっているか。**
  「使いやすいこと」「正しく動作すること」「適切に処理されること」は基準ではない
- 「〜すると、〜であること」の形で、**入力と期待結果**が読み取れるか
- 01の成功指標のうち、02のどこにも○×の線が引かれていないものが無いか
  （機能をまたぐものは4章の非機能要件側でよい）

### E. 各機能の要件に穴が無いか

- **例外・バリデーションが空の機能が無いか。**ここが最も飛ばされる
- 例外について「入力が空 / 対象外 / 処理に失敗」の3方向が検討されているか。
  それぞれ**止めるのか、飛ばして続けるのか**が読み取れるか
- 正常フローに分岐が混ざっていないか（分岐は例外側へ寄せる）
- 事前条件が「特になし」で済まされている機能が、本当に前提を持たないか

### F. 非機能要件が埋まっているか

- 5カテゴリすべてに記述があるか。空欄・「—」だけの行が無いか
- **該当しないものが「該当なし」+ 理由の形で書かれているか**
  （単一ユーザーのローカル実行なら認証は「なし」と明記されていればよい）
- 性能に**測る対象と測り方**が書かれているか。数値だけ置かれて何を測るか不明でないか
- ユーザビリティが、01のペルソナの技術スキルと噛み合っているか

### G. 書いてはいけないものが混ざっていないか

- 画面構成・画面遷移・モックHTML・UI文言 → 03以降の内容
- テーブル定義・カラム・型・ER図 → 04の内容（**項目名の列挙までは可**）
- APIエンドポイント・リクエスト/レスポンス定義 → 05の内容
- テストケース・テスト手順 → 06の内容（**受入基準までは可**）
- 技術選定の比較検討・工数見積り・担当分担

見つかったら「不足」ではなく**削除の提案**として出す。消す判断もユーザーに仰ぐ。

> **技術方針の前提**（言語・SDK・入出力の形式・処理の順番）は1章に数行あってよい。
> 混入として扱うのは、**選定理由の比較検討**や設計の詳細に踏み込んでいる場合。

### H. スコープの書き方

- Out of Scope の各行に**実装しない理由**が書かれているか（「やらない」だけの行が無いか）
- Scope 1 の備考に、その版での**制限**が書かれているか
- Scope 2・3 が空でないか。無いなら「今回で完結」と明記されているか

### I. 未確定が残っていないか

- **「未定」「未確認」「TBD」「要検討」が1つも無いか。**
  02は実装が直接参照する文書で、ここが宙ぶらりんだと仕様書・DB設計・実装が止まる。
  残っていたら、そこを決めるところまでやって閉じる

## やらないこと

- 新規に書き起こす → `requirement-doc`
- 要求定義書（01）の点検・不足埋め → `request-doc-review`。
  01側の不足はここでは直さず、そちらへ回す
- 03以降の内容（画面構成・テーブル定義・API・テストケース）を要求する
- 実装コードとの突き合わせ。**文書どうしの整合だけを見る**
- 文書の全面的な書き直し。不足を埋めるだけにとどめる

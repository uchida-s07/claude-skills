# 仕様書のレビュー（基本設計）

対象は**仕様書（`03-spec.md`）と画面モック（`mocks/mockup.html`）の2つで1組**。
**新規に書き直さない。**既にあるものに観点を当て、**不足だけを埋める。**

作成は `spec-doc` スキルの仕事。まだ文書が無いならそちらへ回す。

**要件定義書（02）は照合用に必ず読む。**03は02を画面へ翻訳した文書なので、
02を見ずに過不足は判定できない。**要求定義書（01）も読む**（ペルソナの技術スキルが、
画面の情報量が適切かの唯一の基準になる）。ただし**直すのは03とモックだけ。**
02側に不足を見つけたら `requirement-doc-review` へ回す。

## 大原則

1. **全部読んでから判断する。**一部だけ見て「足りている」と言わない。
   **02・03・モックのHTML**を通しで読む（01はペルソナとジャーニーを見る）。
2. **文書とモックは必ず両方見る。**片方だけの点検で終えない。
   **本文が正、モックは本文に従う。**食い違いはモック側を直すのが基本
   （本文のほうが誤っていると判断したときだけ、そう申告して本文を直す）。
3. **勝手に書き足さない。**不足を埋めるには判断が要る。
   ただし**02から一意に導ける記述**は、聞く前に案を書いて見せてよい
   （そのとき02のどこから起こしたかを必ず示す）。
   02から導けないもの（動線の細部、文言、空状態の扱い）は案を添えて聞く。
4. **決めるのは人間。**推奨案は出してよいが、承認なしに決定として書かない。
5. **指摘は場所と一緒に出す。**「SCR-04の操作表に、ログアウトの挙動が無い」のように、
   **どこの何が足りないかを画面IDで言う。**
6. **見た目の良し悪しは判定しない。**モックはブラウザで開いてユーザーに見てもらう。
   Claudeが点検するのは**構造**（画面IDの一致・要素の過不足・外部依存・ロジック混入）まで。
   **スクリーンショットを撮るコマンドを自分で実行しない。**
7. **04以降（DB・API・テスト）の内容を要求しない。**テーブル定義・エンドポイントが
   無いのは不足ではなく正しい状態。
8. **02の内容を蒸し返さない。**機能の切り方やスコープへの異議はこのレビューの範囲外。
   03が02と食い違っているかどうかだけを見る。

## 手順

### 1. 対象を特定する

`docs/requirements/03-spec.md` など、仕様書の場所を確認する。
複数あるなら、どれを見るのかユーザーに聞く。見つからなければ、
**まだ作成の段階なので `spec-doc` を使うよう案内して終了する。**

あわせて次も特定する。

- **モック**（`mocks/mockup.html`）。**無ければそれ自体が不足**（観点E）。
- **対になる要件定義書（02）。**見つからない場合は、トレーサビリティの観点（B・C）を
  当てられないことを伝えたうえで、残りの観点だけで点検するか、先に02を作るかを
  ユーザーに選んでもらう。
- **要求定義書（01）。**無ければ観点Hを飛ばす（それだけで止めない）。

### 2. 全部読む

飛ばし読みしない。03の3章と「次のステップ」を最後まで通し、**02も通しで読む。**
**モックのHTMLも通しで読む**（`<section>` のID・UI要素・`<script>`・外部参照）。

### 3. 観点を当てる

下の「点検の観点」を全部当てる。
**B（トレーサビリティ）・C（例外の網羅）・E（モックとの一致）は漏れが最も出るので必ず見る。**

機械的に確かめられるものは、目視より先にコマンドで潰す（「モックの点検のしかた」）。

### 4. 結果を提示する

- **不足がある場合** → 見つかった不足を**一覧でユーザーに提示してから**直しに入る（手順5へ）。
  一覧は**03側の不足とモック側の不足を分けて**出す。どちらを先に直すかも示す
  （本文が先、モックは本文に合わせる）。
- **不足がない場合** → 何も書き換えない。
  **「不足のない仕様書が既にある」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのかも一緒に伝える（当てた観点と、その結果を示す）。

### 5. 不足を埋める

1件ずつ「（必要なら質問 →）ドラフト → 赤入れ → 確定 → ファイルへ書く」で進める。

- **02から一意に導ける不足は、先に案を書いて見せる**（原則3）。
  「FUNC-05の例外『必須項目未入力』がどの画面にも無いので、SCR-08の例外表に
  この行を足す案です」の形。ユーザーは選ぶか直すだけで済む状態にする。
- 02から導けない事実（動線の細部・文言・運用）は**推測で埋めず聞く。**
  「まだ決まっていない」と言われたら、選択肢を2〜3案に絞り、推す案に `（推奨）` と
  理由を添えて聞き直す。それでも決まらないなら、持ち帰るか暫定で決めるかを
  **ユーザーに選んでもらう。**
- **画面を増減させたら、波及を必ず追う。**1章の画面一覧・遷移図・2章の該当節・
  他画面からの導線・モックの `<section>` と `screenIds` 配列とナビ — この5箇所が
  そろって直っているかを毎回確認する。**ここが最も取りこぼす。**
- **本文を直したらモックも直す。**逆も同じ。片方だけ直して次へ進まない。
- 一度に聞くのは2件まで。まとめて並べない。
- **直した箇所はその都度ファイルへ書く。**まとめて最後に書かない。

### 6. ユーザーの承認をもって完了とする

直した内容を報告し、承認を得て終わる。自分の判断で締めない。

- 何が足りず、どう直したかを短く一覧で見せる（03側 / モック側を分ける）
- 決着させた未確定事項があれば、何をどう決めたかも見せる
- **モックを触ったなら、ブラウザで開いて見てもらうよう伝える**
  （`mocks/mockup.html`。`#SCR-03` を付ければ直接その画面へ）
- 「これで04（DB設計）へ進んでよいか」を確認する

## 点検の観点

### A. 章と項目が揃っているか

| 章 | 揃っているべきもの |
|---|---|
| 冒頭 | Vモデル上の位置（基本設計 / 結合テスト）と、この文書で何を定義するかの引用ブロック。GUIでない対象なら**「画面」の定義**があるか |
| 1. 画面構成 | 表（`画面ID / 画面名 / 目的 / 対応機能(②) / モック`）と**画面遷移図**（mermaid） |
| 2. 画面ごとの仕様 | 画面IDごとに 目的 / UI要素 / 操作とインタラクション / エラー・例外表示 / モックリンク の**5ブロック** |
| 3. モックHTML | モックが何を持ち何を持たないかの記述（単一ファイル完結・アンカー・ダミーデータ・ロジック非搭載） |
| 末尾 | 次のステップ |

**行数や箇条書きの数は問わない。**「項目があるか」だけを見る。

2章は**画面ID1つにつき5ブロック。**1つでも欠けている画面があれば不足として出す。
例外が本当に無い画面は `該当なし（〜）。` の1行があればよい（**空欄は不足**）。

### B. 要件（02）とのトレーサビリティ（最も漏れが出る）

**両方向で照合する。**片方向だけだと必ず抜ける。

**02 → 03（拾い漏れ）**

- 02の機能一覧の**機能IDが1つ残らず**、どこかの画面の「対応機能」欄に現れているか
- 現れない機能があるなら、**なぜ画面を持たないかが補足に書かれているか**
  （定時バッチ / 他機能に内包 / Out of Scope）。無言で消えているのは不足
- 02の各機能の**正常フロー**が、画面の操作と遷移として追えるか。
  途中の工程だけ画面が無く、動線が飛んでいないか

**03 → 02（出どころ不明）**

- 画面一覧・UI要素・操作・例外の**全行に対応機能IDがあるか**（空欄が無いか）
- そこに書かれたIDが**02に実在するか**（`FUNC-09` と書いてあるのに02は08までで終わっている、など）
- 02のどこにも根拠が無い画面・UI要素が紛れていないか。
  あるならそれは**新規要件**。02を直すのか（→ `requirement-doc-review`）
  03から落とすのかをユーザーに聞く

### C. 02の例外が全部画面に落ちているか（最も漏れが出る）

- 02の各機能の「例外・バリデーション」を**1行ずつ指で追い**、
  **対応する行がどこかの画面の「エラー・例外表示」にあるか**を照合する
- 例外表の「画面の挙動・表示」に、**表示する文言まで**書かれているか。
  「エラーを表示する」だけの行は不足（実装者が文言を発明することになる）
- 02にある例外が、**どの画面にも現れていない**ものが無いか
- 逆に、画面側で足された例外（0件・空状態・権限なし）が02に無い場合、
  それが妥当な補完か、02側の抜けか（→ `requirement-doc-review`）を判定する
- 最低ラインを当て直す: **0件・空入力・必須未入力・処理失敗・権限/認証エラー。**
  該当しない画面ならそれでよいが、**一度は全部当てたか**を確認する
- **削除など取り返しのつかない操作**に、確認ダイアログが例外表に書かれているか

### D. 章をまたいだ整合

- 1章の画面一覧にある画面IDが、**2章にすべて登場するか。**逆に2章にだけある画面IDが無いか
- **遷移図と2章の「挙動」が一致するか。**図にある矢印が2章の操作表に無い（逆も）が無いか
- **戻り導線が閉じているか。**「SCR-07 → SCR-08」があるのに、SCR-08側に
  保存/キャンセルで戻る操作が無い、が起きやすい
- **孤立した画面が無いか。**どこからも遷移できない画面、どこへも出られない画面
- **UI要素と操作が対応しているか。**押せるUI要素の挙動が操作表に無い／
  操作表にしか出てこないUI要素がある
- 画面名が章をまたいで揃っているか（1章と2章で呼び名が違わないか）
- 画面IDが通し番号で、**欠番を詰めた形跡が無いか**（下流がIDで参照するため詰めてはいけない）

### E. モックと本文が一致しているか（最も漏れが出る）

- **モックが存在するか。**無ければ不足（3章に「作成した」と書いてあるのに無いのは特に）
- 03の**全画面IDが `<section id="SCR-xx">` にあるか。**表記ゆれ（`scr-01`・`SCR-1`）が無いか
- モックにしか無い画面、03にしか無い画面が無いか
- **切替スクリプトの `screenIds` 配列が、実在する `<section>` と一致するか。**
  ここがずれると、ナビから開けない画面ができる
- 03からのアンカーリンク（`./mocks/mockup.html#SCR-01`）が、**実在するIDを指しているか**
- **2章のUI要素がモックに出ているか。**逆にモックにあって03に無い要素を作っていないか
- **単一ファイル完結か。**CDN・外部フォント・外部画像・外部CSS/JSを参照していないか
  （オフラインで開けること）
- **ロジックが混入していないか。**`fetch` / `XMLHttpRequest` / `localStorage` /
  本物の認証・永続化。表示切替とエラー文言の出し分けまでは可
- **実データが入っていないか。**実在の個人名・メールアドレス・社名・本番URL
- ワイヤーフレーム調（グレースケール中心）か。**見た目の良し悪しは判定しない**（原則6）

### F. mermaidが壊れていないか

- **`subgraph` のラベルに空白・括弧・記号があるのにクォートされていない**
  （`subgraph 入居者 (ログイン不要)` は**パースに失敗して図が出ない**。
  `subgraph P["入居者（ログイン不要）"]` が正）
- ノードラベル内の `(` `)` `[` `]` が `["..."]` で囲まれているか
- 未定義ノード・閉じ忘れ・矢印の書き間違い
- 矢印にラベル（`-->|編集を押す|`）が付いているか。無いと図の情報量が落ちる
- 図に出てくる画面IDが、**すべて1章の画面一覧に実在するか**

**図は壊れていても本文だけ読むと気づけない。**ここは必ず目で追う。

### G. スコープとの整合

- 02の**Scope 1 の機能が全部画面になっているか**（初版が画面として成立するか）
- **Out of Scope から画面を起こしていないか**（作らないと決めたものの画面がある）
- Scope 2/3 の機能が画面に混ざっているなら、**`（Scope2）` の注記があるか。**
  注記が無いと、初版の実装範囲が読み取れない
- Scope 2 でしか成立しない画面を立てているなら、画面一覧の備考にScope区分があるか

### H. 要求（01）のペルソナと噛み合っているか

- 01のペルソナの技術スキルで操作できる画面か。専門用語・情報量が過剰でないか
- 01のユーザージャーニーの各ステップが、画面の動線として追えるか。
  ジャーニーで「1アクションで終わる」ことが、3画面またぐ形になっていないか
- 01が想定する利用場面（モバイル / 屋外 / 短時間）と、画面の作りが噛み合っているか

01が無ければこの観点は飛ばす。**飛ばしたことはユーザーに伝える。**

### I. 書いてはいけないものが混ざっていないか

- テーブル定義・カラム・型・ER図 → 04の内容。CREATE文（DDL）はBuildフェーズの内容（**画面に出す項目名までは可**）
- APIエンドポイント・リクエスト/レスポンス定義・IPO → 05の内容
- テストケース・テスト手順 → 06の内容
- 実装の詳細（コンポーネント設計・状態管理・ライブラリ選定）
- 本番のデザイン確定（配色・タイポグラフィ・ブランド適用）→ モックはワイヤーフレームまで

見つかったら「不足」ではなく**削除の提案**として出す。消す判断もユーザーに仰ぐ。

> 画面が扱うデータに**項目名レベルで触れる**のは正しい。
> 混入として扱うのは、型・制約・テーブル名まで踏み込んでいる場合。

### J. 未確定が残っていないか

- **「未定」「未確認」「TBD」「要検討」「{}」が1つも無いか。**
  03は実装が直接参照する文書で、ここが宙ぶらりんだとDB設計・API設計・実装が止まる。
  残っていたら、そこを決めるところまでやって閉じる
- モック側にも `{プレースホルダ}` が残っていないか（雛形の穴が埋まらないまま残りやすい）

## モックの点検のしかた（先に機械的に潰す）

目視の前に、次を確かめる。**ここで出た差分が、そのままE観点の指摘になる。**

| 確かめること | 見かた |
|---|---|
| 03の画面IDの一覧 | 1章の表から `SCR-xx` を拾う |
| モックの `<section>` のID | `id="SCR-` を検索して列挙し、上と**差集合を取る** |
| 切替スクリプトの対象 | `screenIds` 配列を読み、`<section>` の実在IDと突き合わせる |
| ナビのリンク | `data-scr` / `href="#SCR-` を列挙し、同じく突き合わせる |
| 外部依存 | `http://` `https://` `cdn` `src=` `@import` を検索。**1件でもあれば単一ファイル完結でない** |
| ロジック混入 | `fetch(` `XMLHttpRequest` `localStorage` `sessionStorage` を検索 |
| 穴の残り | `{` `TBD` `未定` を検索 |

**開いた見た目の確認はユーザーに任せる。**ブラウザで開いてもらい、
崩れ・読みにくさ・情報量の過不足を見てもらう（原則6）。

## やらないこと

- **新規に書き起こす** → `spec-doc`
- **要件定義書（02）の点検・不足埋め** → `requirement-doc-review`。
  02側の不足はここでは直さず、そちらへ回す
- **要求定義書（01）の点検・不足埋め** → `request-doc-review`
- **04以降の内容（テーブル定義・API・テストケース）を要求する**
- **実装コードとの突き合わせ。文書どうし・文書とモックの整合だけを見る**
- **モックのデザインを作り込む。**ワイヤーフレームとして構造が読めれば十分
- **文書の全面的な書き直し。**不足を埋めるだけにとどめる

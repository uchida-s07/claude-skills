# 要求定義書づくり

Vモデルの **要求分析**（対応する検証は受入テスト）にあたる文書を1本作る。
成果物の骨組みは同ディレクトリの `template.md`。**章立てと表の列を見るための参考**であって、
埋め方の指示書ではない。分量はそこに合わせにいかなくてよい。

書き上げた文書の点検は `request-doc-review` スキルが担う。**このスキルは作成に専念する。**

**使う場面**: 新機能に着手するとき、新しいプロジェクトを立ち上げるとき。
**やり方**: 既存の実装プランや過去資料を読み込んで要約するのではなく、**ユーザーと一緒にゼロから組み直す。**
既存資料に引きずられると、そこにある前提をそのまま引き継いでしまう。白紙から始める。

## 大原則

1. **ゼロベースで組み直す。** 手元に既存の資料があっても、それを土台にしない。
   ユーザーが「この資料を踏まえて」と明示した場合だけ参照する。
2. **質問して埋める。ただし聞きっぱなしにしない。** 質問 → 答えを解釈してドラフトを書く →
   「こう理解しました」と見せて赤入れしてもらう、を1セットにする。
3. **要件定義に渡せる粒度まで上げる。** 各章を書き終えるたびに
   「この記述から、02で何を作るかを起こせるか」を自問する。
   「使いやすく」「スムーズに」のような言葉が残っていたら、具体的な場面に置き換わるまで掘る。
   ただし**実装に渡せる粒度までは求めない。**そこは02の仕事。
4. **「未定」「未確認」「TBD」を本文に残さない。** これは全工程の最上位文書で、
   以降の文書はすべてここを前提に書かれる。ここが宙ぶらりんだと下流すべてが揺れる。
   **この文書づくりのゴールは、未確定事項を決定まで持っていくこと。**
5. **決めるのは人間。Claudeは決めない。** 未確定の事項は必ずユーザーに判断を仰ぐ。
   推奨案を提示するのはよい（というより、そうすべき）。だが**ユーザーの承認なしに決定として書かない。**
   「決まっていない」と言われて会話が止まりそうなときも、こちらが決めて先へ進むのではなく、
   判断しやすい形に整えて聞き直す。
6. **機能・データモデル・画面・API・スキーマは書かない。** 「〜できること」まで。
   データの持ち方を書きたくなったら、それは要件定義（02）の内容。
7. **表を主体にする。** 散文は背景・感情の変化など、表にすると死ぬところだけ。
8. 日本語で書く。

## 手順

### 0. 既存の要求定義書があるか確認する

`docs/requirements/` などに、対象の要求定義書が既にあるか探す。
対象がまだ聞けていない段階なので、**候補が複数見つかったら、どれのことかユーザーに聞く。**

- **ある** → このスキルの出番ではない。**`request-doc-review` スキルへ回す**（点検して不足を埋める）
- **ない** → 1へ進む

### 1. 対象を1問で掴む

まず「何を作るのか / 誰のためか」だけを聞く。ここは白紙なので開かれた質問でよい。
返ってきた一言から、以降の章の**たたき台を自分で書ける状態**にする。
足りなければ、この段階で2〜3往復して機能の輪郭（何が起きたら成功か）を掴む。

### 2. 出力先を決める

既定は `docs/requirements/01-request.md`。
プロジェクトに既に文書の置き場があればそれに従い、機能が複数並ぶなら
`docs/requirements/<機能名>/01-request.md` のように機能ごとに分ける。
ここは推測せずユーザーに確認する。

### 3. 章ごとに「質問 → ドラフト → 赤入れ → 確定 → ファイルへ追記」

**1章 → 2章 → … と章順に進める。**前の章が決まらないと次の章は書けない
（課題が決まらないとゴールが書けない、ペルソナが決まらないとジャーニーが書けない）。

1章の時点では、困っている人は**役割で書けば足りる**（「受付をする人」「申し込む人」）。
人物像を作り込むのは3章の仕事なので、1章で年齢や技術スキルまで聞きに行かない。

**1章確定するごとにファイルへ書く。**まとめて最後に書かない（`/clear` や中断で消えるため）。

最後に「次のステップ」として、要件定義（02）へ何を渡すかを書く。

### 4. 書き上がったら `request-doc-review` で点検する

全章そろったら、**レビューは `request-doc-review` スキルに任せる。**
点検の観点はそちらが正典なので、ここで独自のチェックリストを作らない。

不足が出たら、レビュー側の流れ（一覧で提示 → 質問しながら直す）でそのまま埋める。

### 5. ユーザーの承認をもって完成とする

点検の結果と直した箇所をユーザーに提示し、**承認を得てはじめて完成**とする。
自分の判断で締めない。

- 直した箇所を短く報告する
- 決着させた未確定事項があれば、何をどう決めたかを一覧で見せる
- 「これで02（要件定義）へ進んでよいか」を確認する

## 質問の作法

**選択式と記述式を使い分ける。**選択肢に押し込むこと自体が目的ではない。

| 聞き方 | 使いどころ |
|---|---|
| 記述で聞く（普通の質問文） | 答えがユーザーの頭の中にしかないもの。背景・経緯・現場の実情・「どう回しているか」。こちらが選択肢を作れないところを無理に選択式にすると、的外れな案から選ばせることになる |
| 選択式（`AskUserQuestion`） | 方向性が2〜3通りに割れていて、どれを採るかで以降の記述が変わるとき。ユーザーが即断できる形にしたいとき |

どちらの場合も守ること:

- **一度に聞くのは2件まで。**章の切れ目ごとに刻む。まとめて4件並べると保留される。
- 選択式にするなら、選択肢は抽象語ではなく**その機能の文脈に落とした具体案**にする。
  妥当な案を先頭に置き `（推奨）` を付ける。ユーザーは選ぶか直すだけで済む状態にする。
- 記述で聞くなら、**こちらの理解を先に置いてから聞く**。
  「〜という理解で合っていますか。違う点を教えてください」の形にすると、白紙より答えやすい。
- 選択式で聞いた場合でも、ユーザーは選択肢外を文章で返してよい。返ってきたらそちらを優先する。
- 一度答えをもらったら、それを**文章・表の形にして見せる**。合意した形をそのまま本文に使う。
- 業務側の事実（誰が運用するか、どの規模でやるか）は勝手に決めない。必ず聞く。

### 未確定の事項をどう決着させるか

**決定権はユーザーにある。Claudeは推奨案を出すところまで。**
「まだ決まっていない」と言われても、そのまま「未定」と書いて逃げない。決めやすい形にして聞き直す。

1. **選択肢を2〜3案に絞って出す。**各案について「これを採るとどうなるか」を一言添える。
   妥当だと思う案には `（推奨）` を付け、なぜそれを推すかも1行で言う
2. **選べないと言われたら、何が分かれば決まるのかを言語化して、その一点だけ聞く。**
   「利用者が何人くらいかが分かれば決まります。おおよそで構いません」のように絞る
3. **その場のユーザーだけでは決められない事項なら、そのことを伝えて判断を仰ぐ。**
   持ち帰って確認してもらうのか、いま暫定で決めて後で改訂するのかを**ユーザーに選んでもらう**

**どの段でも、ユーザーが「それでいく」と言うまでは決定として書かない。**
推奨案をそのまま本文に書き込んで既成事実にしない。合意した内容だけが本文に入る。

## 各章に必要な項目

**必要なのは「どの項目があるか」まで。分量は問わない。**
内容が過不足なく書けていれば、行数や箇条書きの数は多くても少なくてもよい。

### 冒頭の引用ブロック

```
> Vモデル: 要求分析 / 対応する検証: 受入テスト
> このプロジェクトで「誰の・どんな課題を・なぜ解決するか」を定義する。
```

### 1. 背景・課題

| 項目 | 中身 |
|---|---|
| 背景 | 誰が、どんな状況で、何のためにこれを必要としているか |
| 現状 | いまその仕事がどう回っているか（その機能が無い状態でどう凌いでいるか） |
| 課題一覧 | 表: `# / 課題 / 影響度 / 優先度`。高・中・低で揃える |

聞くこと: いまどう回しているか。何が一番困っているか。困っているのは誰か。

### 2. ゴール

| 項目 | 中身 |
|---|---|
| ビジネスゴール | 作る側・提供する側から見て何が達成されるか |
| ユーザーゴール | 使う人から見て何が良くなるか |
| 成功指標 | 表: `指標 / 目標値 / 測定方法`。**厳密さは求めない** |

成功指標は「どうなったら成功と言えるか」が伝わればよい。
測定方法は分かる範囲で短く。測りようがないものは `—` や「運用で目視」程度で構わない。
数値目標が置けないなら定性で書く。**測り方を詰めるために章を止めない。**

厳密でなくてよいのは、**合否の線は02（要件定義）が機能ごとの受入基準として引く**から。
01は成功の方向を示すところまでで、○×の付く条件はここでは書かない。

聞くこと: 何をもって成功とみなすか。数値で置ける指標があるかどうか。

### 3. ペルソナ

**ペルソナはユーザーが創作する。Claudeが作らない。**
名前・年齢・職業・技術スキルを勝手に置かず、ユーザーから受け取って表の形に整えるだけにする。
運用に合う人物を立てられるのはユーザーであって、こちらが埋めると4章以降の行動が架空の前提に乗る。
ここは大原則2（ドラフトを書いて赤入れしてもらう）の例外で、**先に聞く。**

**メインペルソナ1人が基本。**別々の要求を持つアクターが複数いる機能
（使う人と、現場で受け付ける人が別、など）は複数立てる。何人にするかもユーザーが決める。

| 項目 | 中身 |
|---|---|
| 属性表 | `名前 / 年齢 / 職業 / 部門（所属） / 技術スキル` |
| 目標・ゴール | 箇条書き |
| 課題（ペインポイント） | 箇条書き。1章の課題一覧と対応させる |
| 利用状況 | 表: `利用場面 / 頻度 / 詳細` |

副次的ユーザーを想定しないならその旨を1行の引用で明記する。

聞くこと: 想定利用者の実像（年齢層・端末の慣れ・使う場面と頻度）。ペルソナを何人にするか。

### 4. ユーザージャーニー

| 項目 | 中身 |
|---|---|
| mermaid図 | ```` ```mermaid ```` の `journey`。`title` + `section` + `タスク: スコア: アクター` |
| メインフロー | 表: `# / フェーズ / 行動 / 課題・感情 / 解決` |
| 感情の変化 | 開始時 / 最初のつまずき / ブレークスルー / ゴール達成時 の4点 |

mermaid図のスコアは**その場面での満足度**を1〜5で表す（1 = つらい・不満、5 = 満足）。
所要時間や重要度ではない。「感情の変化」やメインフローの「課題・感情」列と、上下の向きを揃える。

「解決」列には、その課題を何が解消するかを書く。**機能名ではなく体験で書く。**

**大まかな行動の流れが追えればよい。**受け取る → 使う → 終わる、程度の粒度で足りる。
画面単位の操作や分岐条件まで割らない（それは要件定義以降の仕事）。

聞くこと: 最初のきっかけは何か。どこで詰まりそうか。終わった後どうなるか。

#### 書き終えたら流れを点検する（漏れが出やすい章）

ユーザーに見せる前に、**`request-doc-review` の「C. ユーザージャーニー」の観点**を自分で当てる
（流れの途切れ / 矛盾 / 不足）。埋まらない箇所は推測で埋めず、そこだけ質問する。
**細かく割るための点検ではない。**流れとして通っているかだけを見る。

### 5. 利害関係者

表: `利害関係者 / 期待`。ペルソナ本人 + 後工程 + 承認する側。

聞くこと: 巻き込む必要のある関係者（承認・調整先）。

### 末尾: 次のステップ

`→ 02-requirement（要件定義書）で機能一覧・要件・スコープ・非機能要件を定義する`

ここは1行でよい。「後で決めること」の置き場にはしない（決め残しを作らないため）。

冒頭で「対応する検証: 受入テスト」と宣言しているとおり、この文書に書いた課題とゴールが
最後に受入テストで確かめられる。ただし**機能ごとの受入基準（○×の付く条件）を書くのは02**。
01は「何が達成できていれば成功か」を示すところまでを担う。

## やらないこと

- 既存の要求定義書の点検・不足の洗い出し → `request-doc-review`
- 既存の実装プラン・過去資料の読み込みと要約 → このスキルの仕事ではない
- 機能一覧・画面遷移・データモデル・スキーマ・API・状態遷移 → 要件定義（02）以降
- 技術選定・使用するライブラリやサービスの名前 → 要求定義には出さない。
  特定のプロダクト固有の事情を持ち込むと、要求が実装の都合に引きずられる
- 実装計画・工数・担当分担 → 別文書

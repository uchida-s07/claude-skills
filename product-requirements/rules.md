# 要件の書き方（共通ルール）

仕様駆動ワークフロー（docs/product・docs/specs）で要件（What）と受入基準を書くとき、点検するときの正典。
ここに無い独自ルールを各スキルで作らない。要求（Why）＝ vision.md の書き方は product-vision が持つ。

## 1. 文書の役割分担

| 文書 | 書くこと | 書かないこと |
|---|---|---|
| vision.md（要求・常設） | 課題 P-n / ゴール G-n / 非目標 / ペルソナ / ジャーニー J-n | 機能・要件・データの持ち方 |
| requirements/<領域>.md（要件・常設） | システムが「今」満たしている振る舞い。要件ごとの5項目と受入基準 | 画面構成・テーブル定義・API・予定（まだ作っていないもの） |
| specs/NNN/spec.md（変更ごと） | 今回の変更の要求・新しく作る/変える要件の「変更後の姿」・廃止する要件・DB/API/画面の差分 | 変更に関係しない既存要件の書き写し |

- 要件は「何を作るか」まで。「どう作るか」（画面構成・モック・テーブル定義・カラム型・エンドポイント・クラス設計）は書かない。
- spec では DB・API・画面は「変更差分」節に差分だけ書く。常設要件には書かない（コードが正）。
- 要件の中でデータに触れるのは項目名の列挙まで。
- 技術方針の前提は必要なら数行。選定理由の比較検討は ADR に書く。

## 2. ID

| 種類 | 置き場所 | 形式 | 例 |
|---|---|---|---|
| 課題 | vision.md | `P-n` | `P-3` |
| ゴール | vision.md | `G-n` | `G-2` |
| ジャーニーのステップ | vision.md | `J-n` | `J-4` |
| 機能要件 | requirements/<領域>.md（spec でも同じ ID） | `<領域>-F-nnn` | `MEAL-F-003` |
| 非機能要件（領域固有） | requirements/<領域>.md（同上） | `<領域>-N-nnn` | `MEAL-N-001` |
| 非機能要件（全体共通） | requirements/common.md（同上） | `COMMON-N-nnn` | `COMMON-N-002` |
| 受入基準 | 要件の中 | `<要件ID>/AC-n` | `MEAL-F-003/AC-2` |
| spec | docs/specs/ | `NNN`（3桁ゼロ埋め） | `012` |
| レビュー指摘 | レビューの出力 | `R-n` | `R-5` |
| 機械点検の指摘 | spec-check の出力 | `SC:<点検名>:<対象>` | `SC:dup-id:MEAL-F-003` |

- **spec でも常設 ID を使う。** 新しい要件の番号は、その領域の常設要件と、進行中（draft / approved）の spec がすでに予約した番号の**最大値＋1**。予約が重なったら spec-check が検出し、後から閉じる spec の側で振り直す（振り直せるのは done になる前だけ）。
- 受入基準の番号は**要件ごと**に振る。要件ブロックの中では `AC-n` と書き、外から指すときは `<要件ID>/AC-n` と書く。
- 既存要件を変えるとき：既存の AC は同じ番号のまま中身を書き換える。足す AC は次の番号。無くす AC は欠番にし「（廃止）」と残す。
- 常設になった番号は**詰めない・振り直さない**。廃止した ID は欠番にし、廃止の記録を残す。
- vision の項目を廃止するときは、ID を取り消し線（`~~P-3~~`）にして行を残し、理由を変更履歴に書く。
- 領域コードは英大文字2〜8文字（先頭は英字）。requirements/README.md の領域一覧に登録してから使う。spec で新しい領域を作る場合は spec の「新しい領域」節に書き、/spec-close で登録する。
- テスト名（またはテストの説明文）に `[<要件ID>/AC-n]` を含める。例：`[MEAL-F-004/AC-1] 前日21時に不要を登録すると一覧から除外される`。1つのテストが複数の AC を確かめるときはタグを並べてよい。

## 3. 粒度

- 1要件 = ユーザーから見て「〜できる」が1つ。パイプライン型の処理なら1工程1要件。
- 数に上限・下限を置かない。揃えるのは粒度。5項目が書けないほど大きいなら割る。単独で「〜できる」にならないなら束ねる。

## 4. 1要件に書く5項目

| 項目 | 中身 |
|---|---|
| 概要 | 何を受け取り、何を出すか。1〜2文 |
| 事前条件 | 動き出せる状態。他の要件の結果を前提にするならその ID |
| 正常フロー | A → B → C。分岐は書かない（例外側へ） |
| 例外・バリデーション | 5章の3方向を必ず検討する |
| 受入基準 | 6章の形で書く |

このほかに「対応する要求」（G-n / P-n / J-n）と「出典」を持つ（8章）。
spec でも、新しく作る要件・変える要件は同じ5項目で「変更後の姿」を書く。/spec-close はそれを常設要件へそのまま移す。

## 5. 例外の3方向

| 方向 | 例 |
|---|---|
| 入力が空・欠けている | 必須項目が未入力、0件 |
| 対象外・想定外の入力 | 締切後、権限なし、形式違い、境界値の外側 |
| 処理に失敗した | 外部サービスの失敗、保存の失敗、同時更新 |

それぞれ「止める / その1件だけ飛ばして続ける / どう知らせる」を明示する。
機能によっては 境界値・権限・同時操作・繰り返し（同じ操作を2回）も確認する。

## 6. 受入基準

- テストで○×が付く文にする。Given（具体的な値・時刻まで）/ When（1つの操作）/ Then（観察できる結果）。
- 基準にならない言葉：「使いやすい」「正しく動く」「適切に処理される」「スムーズに」「エラーにならない」。出てきたら具体的な結果に置き換わるまで掘る。
- 1つの機能要件に少なくとも1つの AC。例外の3方向のうち「止める」ものは AC にする。
- 非機能要件は「測り方」を必ず書き、自動テストで確かめられるものは AC も付ける。
- 要件をまたぐ性能・精度は非機能要件へ。vision.md の成功指標は方向まで、合否の線は受入基準が引く。

## 7. 非機能要件

全体共通は requirements/common.md に置き、性能 / セキュリティ / 可用性 / ユーザビリティ / 保守性 の5カテゴリを必ず埋める（該当なしなら理由を書く）。
性能は「何を・どう測るか」まで。セキュリティは認証方式・有効期限・権限モデル・秘密情報の扱い。
ユーザビリティは vision.md のペルソナの技術スキルと合わせる。数値は決め切る（根拠が無ければ「目安」と添える）。

## 8. トレーサビリティ（両方向）

- 要件 → 要求：すべての要件に「対応する要求」（G-n / P-n / J-n）があり、参照先が vision.md に実在し、廃止されていない。
- 要求 → 要件：vision.md の課題・ゴール・ジャーニーの各項目が、どこかの要件か「やらないこと」（理由付き）で拾われている。
- 常設要件は「出典」（specs/NNN、Issue・コミット、または「導入時の既存実装」）を持つ。
- 受入基準 → テスト：常設要件のすべての AC に、`[<要件ID>/AC-n]` を含むテストがある。テストのタグは実在する AC を指す。

## 9. スコープ

- spec の「スコープ外」には必ず理由を書き、「後回し（次の spec 候補）」か「やらない」かを区別する。
- 常設要件の「やらないこと」には「やらない」と決めたものだけを移す。後回しは予定なので常設要件には書かない。
- Lティアの初版では、今回のスコープだけで vision.md のジャーニーが1周するかを確かめる。

## 10. 決め方

1. 決めるのは人間。Claude は案を出すところまで。ユーザーが「それでいく」と言うまで決定として書かない。
2. 書ける部分は聞く前に書く。vision・既存要件・コードから起こせるものは Claude が先に書き切って見せる。
3. 書いた以上は根拠を示す。何から起こし、どこを推測したかを添え、根拠の弱い行を自己申告する。
4. 赤入れが無かったこと＝承認ではない。Claude が決めた箇所は最後に一覧で承認を取る。
5. 業務側の事実（誰が運用するか・規模・今どう回しているか）は書かずに聞く。
6. 常設要件には「未定」「TBD」「要検討」を1つも残さない。spec は draft の間だけ「未決事項」に置いてよく、空になるまで approved にしない。

## 11. 質問の作法

- 答えがユーザーの頭の中にしかないものは記述で聞く。先に「〜という理解で合っていますか」と理解を置く。
- 方向が2〜3通りに割れるものは選択式（AskUserQuestion）。具体案にし、妥当な案を先頭に「（推奨）」と理由1行。
- 一度に聞くのは2件まで。書いてあることを聞き返さない。選択肢外の回答はそちらを優先する。
- 決まらないとき：①2〜3案に絞る → ②何が分かれば決まるかを言語化してその一点を聞く → ③持ち帰るか暫定で決めるかをユーザーに選んでもらう。

## 12. レビュー指摘の扱い

### 重大度

| 重大度 | 意味 | 関門での扱い |
|---|---|---|
| 矛盾 | 2つの記述が同時に成り立たない（文書どうし、文書とコード、文書とテスト） | 未解決なら先へ進めない |
| 欠落 | 必要な項目・対応が無い（AC が無い要件、拾われていない課題、テストの無い AC など） | 未解決なら先へ進めない |
| 注意 | 成り立つが危うい（抽象語、粒度の不揃い、放置された spec） | ユーザーの判断で進めてよい |

### 状態

| 状態 | 意味 | 関門での扱い |
|---|---|---|
| 未解決 | まだ直していない・扱いが決まっていない | 矛盾・欠落なら先へ進めない |
| 修正済み | 文書かコードを直し、再点検で出なくなった | 解消 |
| 誤検知 | ユーザーが「指摘が誤り」と判断した | 解消（理由を記録） |
| 承知で進める | ユーザーが「問題は認めるが今回は直さない」と判断した | 解消（理由を記録） |

- 誤検知・承知で進めるは、**ユーザーが判断したときだけ**付ける。Claude が自分で解消扱いにしない。理由は docs/review-notes.md に書く。
- 関門は「**未解決の矛盾・欠落が0件**」。

### 指摘の書式

各指摘に次を書く：

- ID（LLM のレビューは `R-n`、機械点検は `SC:<点検名>:<対象>`）
- 重大度 / 観点 / 場所（ファイルと ID）
- 何がどうぶつかっているか（両方の記述を引用）
- 直し方の案（どちらを正とするかの選択肢を含む）
- 直す先（どのファイル、どの Skill）

あわせて守ること：

- 指摘が無い観点も「確認した観点と結果」として一覧に残す（「問題なし」と言うだけにしない）。
- 照合する材料が無くて確かめられなかった観点は「照合不能」として分けて書く。問題なしに混ぜない。
- docs/review-notes.md で除外済みの指摘は出さず、件数だけを書く。ただし除外した日より後に対象のファイルが変わっていれば、改めて判断する。
- 書いてあってはいけないもの（混入）は「削除の提案」として出す。
- レビューの範囲外の不備は直さず「別のレビューへ回す指摘」として分けて書く。

### 直し方（メインの会話で行う）

1. レポートを一覧でユーザーに見せてから直しに入る。
2. 矛盾は「どちらを正とするか」をユーザーに選んでもらう。Claude が勝手に片方へ寄せない。
3. 1件ずつ直し、その都度ファイルに書く。一度に聞くのは2件まで。
4. ユーザーが「誤検知」「承知で進める」と判断した指摘は、理由を聞いて docs/review-notes.md に書く。
5. 直したら、影響した範囲だけ同じレビュー・点検をもう一度通す。未解決が0件になるまで繰り返す。
6. ユーザーが「今回は飛ばす」と明示してレビューを省いたときも、docs/review-notes.md に「飛ばした」と書く。

### docs/review-notes.md の書き方

| 列 | 中身 |
|---|---|
| 日付 | YYYY-MM-DD |
| レビュー | spec-check / spec-review / spec-verify / docs-review |
| 対象 | spec 番号、領域コード、要件 ID、または「全体」 |
| キー | spec-check の指摘は `SC:<点検名>:<対象>` をそのまま書く（spec-check はこの完全一致で除外する）。LLM のレビューは空欄でよい |
| 指摘の要旨 | 1行 |
| 扱い | 誤検知 / 承知で進める / 飛ばした |
| 理由 | ユーザーから聞いた理由 |

`docs-review all` を行い、指摘を処理し終えたら、冒頭の「最後の全体レビュー:」を その日付にする。

### いつレビューするか

レビューのタイミングはワークフローで決まっている（プロジェクトの CLAUDE.md「開発ワークフロー」節のタイミング表）。
作成用スキルは決められた位置で必ずレビュー・点検を呼び、未解決の矛盾・欠落が0件になるまで次の段階へ進めない。
spec-check で判定できるものは spec-check に任せ、LLM のレビューでは同じ点検を繰り返さない。

## 13. 書いたらすぐファイルへ

合意した部分はその都度ファイルに書く。まとめて最後に書かない。

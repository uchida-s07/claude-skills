# product-requirements（常設要件の導入と直接の更新）

`docs/product/requirements/` の常設要件は、システムが「今」満たしている振る舞いを領域ごとにまとめたもの。通常は `/spec-close` で積み上がる。このスキルを使うのは次の2つの場面だけ。

| 引数 | 場面 |
|---|---|
| `init` | 既存プロジェクトにこのワークフローを入れるとき、今の振る舞いを常設要件に起こす |
| `update` | spec を経ない変更：S ティアの修正で振る舞いが変わった、要件の文言修正、要件の廃止 |

引数が無ければ、`requirements/` に要件が1件も無いなら `init`、あるなら `update` を提案して確かめる。

**要件と受入基準の書き方の正典は `${CLAUDE_SKILL_DIR}/rules.md`。** 必ず全文を読んでから始める。ここに独自のルールを足さない。
雛形：領域ファイル `${CLAUDE_SKILL_DIR}/template-area.md`、全体共通 `${CLAUDE_SKILL_DIR}/template-common.md`、索引 `${CLAUDE_SKILL_DIR}/template-readme.md`。見出し・表・ID の書式は `spec-check` が読むので変えない。

## 大原則

1. **vision.md が前提。** 無ければ始めない。`/product-vision` を案内して止める。vision に不足があるだけなら、要件の中で補わず `/product-vision update` へ回す。
2. **書ける部分は聞く前に書く。** 材料（旧02・コード・テスト・vision）が読める以上、要件一覧と各要件の5項目は Claude が書き切れる。空欄を質問で埋めさせず、完成形をファイルに置いてから見てもらう。人間の時間は、書かれたものを直すことに使ってもらう。
3. **書いた以上は根拠を示す。** どこを何から起こし、どこを推測したかを添える。根拠の弱い行を自己申告する（「MEAL-F-003 の例外はコードに処理が無く、推測で書いた」など）。
4. **書いたものは提案であって決定ではない。** 業務側の事実（誰が運用するか・規模・今の運用）は案を書かず、聞く。赤入れが無かったこと＝承認ではない。最後に一覧で承認を取る（rules.md 第10章）。
5. **常設要件は「今の振る舞い」。** 予定・まだ作っていないものは書かない（それは spec）。
6. **未定・TBD・要検討を残さない**（rules.md 第10章6）。
7. **書いたらすぐファイルへ**（rules.md 第13章）。

## init：既存プロジェクトへの導入

### 1. 前提を確かめる

- `docs/`（`/spec-setup` 済み）と `docs/product/vision.md` があるか確かめる。無ければ案内して止める。
- 材料を探して読む：旧 `02-requirement.md`（あれば全文）、コード（入口：画面・API・コマンド・バッチ）、テスト、vision.md（全文）。

### 2. 領域の分け方と要件一覧を先に閉じる

**まず領域の分け方と要件一覧だけを書き切り、切り方と抜け漏れを見てもらう。** ここで要件が増減すると後が連鎖するので、先に閉じる。

- 領域：コード（英大文字2〜8文字）/ 領域名 / 範囲。`requirements/README.md` の領域一覧に書く。
- 要件一覧：領域ごとに `ID / 要件名 / 概要 / 対応する要求 / 出典`。ID は `<領域>-F-001` から。粒度は rules.md 第3章。
- 対応する要求は vision.md の `G-n` / `P-n` / `J-n`。vision に対応が無い振る舞いが見つかったら、要件から落とすのか vision を足すのか（`/product-vision update`）をユーザーに聞く。
- 逆向きも見る：vision の課題・ゴール・ジャーニーのうち、どの要件にも拾われないものは、要件の漏れか「やらないこと」か。
- 自分で決めた箇所と迷った箇所を明示して見せる。

### 3. 領域ごとに5項目を書き、まとまりで見せる

領域ファイル（`<code>.md`）を雛形から作り、各要件の5項目（rules.md 第4章）と「対応する要求」「出典」を書く。**1要件ずつではなく、領域ごとのまとまりで見せて赤入れを受ける。** 多ければ数要件ずつ区切る。赤入れはその場でファイルに反映してから次へ進む。

- **コードが実際にしていること**を書く。旧02の記述ではなく実装が正（振る舞いの事実として）。
- 旧02に書いてあるが実装されていないもの → 要件にせず「次の spec の候補」として一覧にし、最後にユーザーに渡す。
- 旧02とコードが食い違うもの → どちらが正しいかをユーザーに聞く（コードがバグなら、要件は正しい振る舞いで書き、バグ修正を S ティアの候補として一覧に載せる）。
- 出典は「導入時（旧02 FUNC-03 / 既存実装）」のように書く。旧 `FUNC-xx` との対応表を `requirements/README.md` に残す。
- 例外は3方向（rules.md 第5章）を必ず検討する。コードに処理が無い方向は、今の振る舞い（例：落ちる）を書いたうえで、直すべきならバグ修正の候補に載せる。
- 受入基準は既存テストがあればそこから起こし、無ければ案を書く（rules.md 第6章）。

### 4. 既存テストとの結び付けを決める

受入基準に対応する既存テストがあるなら、テスト名（または説明文）に `[<要件ID>/AC-n]` のタグを付けるかをユーザーに聞く（選択式）。

- 付ける（推奨：`spec-check` がテストの有無を追えるようになる）→ タグを付ける変更を案として一覧で見せ、承認を得てから付ける。
- 付けない・後で付ける → `spec-check` が `ac-no-test` を出し続けるので、`docs/review-notes.md` に「承知で進める」として、キーを `SC:ac-no-test:<領域>-*` のようにまとめて書く。
- 対応するテストが無い受入基準は、テストを足すか、承知で進めるかをユーザーに決めてもらう。

### 5. 全体共通の非機能要件を決める

`common.md` の5カテゴリ（性能 / セキュリティ / 可用性 / ユーザビリティ / 保守性）は、**質問して決める**（rules.md 第7章）。コードや設定から読める事実（認証方式など）は案として書いて見せ、水準（許容できる処理時間など）は聞く。Claude の案を1つ添えて決めてもらう。該当なしなら理由を書く。

### 6. 点検する（タイミング②）

1. `spec-check` を呼ぶ（Skill ツールで `spec-check`、引数 `all`）。
2. `docs-review` を呼ぶ（Skill ツールで `docs-review`、引数 `all ②`）。要件の中身・要件どうしの矛盾・要件とコードのずれ・旧文書の残骸まで見たレポートが返る。
3. rules.md 第12章の「直し方」で進める。
   - レポートを一覧で見せてから直しに入る。矛盾はどちらを正とするかをユーザーに選んでもらう。
   - 今直すものと、次の spec に回すものをユーザーと決める。次の spec に回すと決めた矛盾・欠落は「承知で進める」として `docs/review-notes.md` に書く。
   - 旧文書（01〜06）を残すか消すかはユーザーに聞く（消すのはユーザーの承認を得てから）。
   - 直したら影響した範囲だけ点検をもう一度通す。**未解決の矛盾・欠落が0件になるまで繰り返す。**
4. `docs/review-notes.md` の「最後の全体レビュー:」を今日の日付にする。

### 7. ユーザーの承認をもって完了とする

- Claude が決めて書いた箇所のうち、そのまま残ったものを一覧で見せて承認を取る。
- 次の spec の候補（旧02にあって未実装のもの、バグ修正の候補、次の spec に回した指摘）を一覧で渡す。

## update：spec を経ない変更

対象は、S ティアの修正で振る舞いが変わったとき、要件の文言修正、要件の廃止。**新しい振る舞いを足すなら spec（`/spec-new`）を案内する。**

1. 何を変えたか（Issue・コミット・説明）を受け取る。コミットがあれば差分を読む。
2. 影響する要件を特定し、直し方を案として書いて見せる（rules.md に従う）。
   - 振る舞いの変更：該当要件の5項目と受入基準を直す。既存の AC は同じ番号で書き換え、足す AC は次の番号、無くす AC は「（廃止）」と残す。出典に Issue やコミットを足す。
   - 文言修正：意味が変わらないことを確かめる。変わるなら振る舞いの変更として扱う。
   - 廃止：要件を「廃止した要件」表へ移す（ID は欠番）。その要件を事前条件に使っている要件が無いか探す。
   - 受入基準を変えたら、対応するテスト（`[<要件ID>/AC-n]`）も直す必要があることを伝える（テストの修正はこのスキルではしない。必要なら一覧で渡す）。
3. ユーザーの承認を得てからファイルに書く。領域ファイルの `updated:` を今日にする。
4. 点検する（タイミング②）：`spec-check`（引数 `area <領域コード>`）→ `docs-review`（引数 `requirements <領域コード> ②`）。rules.md 第12章の「直し方」で、未解決の矛盾・欠落が0件になるまで直す。
5. 直した要件と、テストの修正が要る箇所を報告する。

## やらないこと

- 通常の機能追加で要件を足す → `/spec-new` 〜 `/spec-close`
- vision の修正 → `/product-vision update`
- 画面構成・テーブル定義・API（コードが正。spec の「変更差分」に書く）
- テストやコードの修正（update で必要な箇所は一覧で渡すだけ）
- 旧フローの要件定義書（`02-requirement.md`）の作成・点検 → `requirement-doc` / `requirement-doc-review`

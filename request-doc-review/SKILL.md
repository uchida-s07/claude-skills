# 要求定義書のレビュー

対象は要求定義書（`01-request.md`）1本。**新規に書き直さない。**
既にあるものに観点を当て、**不足だけを埋める。**

作成は `request-doc` スキルの仕事。まだ文書が無いならそちらへ回す。

## 大原則

1. **全文を読んでから判断する。**一部だけ見て「足りている」と言わない。
2. **勝手に書き足さない。**不足を埋めるには判断が要る。ユーザーに聞いてから直す。
3. **決めるのは人間。**推奨案は出してよいが、承認なしに決定として書かない。
4. **指摘は場所と一緒に出す。**「3章の利用状況の表が無い」のように、どこの何が足りないかを言う。
5. **02（要件定義）の内容を要求しない。**機能一覧・データモデル・画面・受入基準が無いのは
   不足ではなく正しい状態。

## 手順

### 1. 対象を特定する

`docs/requirements/01-request.md` など、要求定義書の場所を確認する。
複数あるなら、どれを見るのかユーザーに聞く。見つからなければ、
**まだ作成の段階なので `request-doc` を使うよう案内して終了する。**

### 2. 全文を読む

飛ばし読みしない。5章と「次のステップ」を最後まで通す。

### 3. 観点を当てる

下の「点検の観点」を全部当てる。**4章（ユーザージャーニー）は漏れが最も出るので必ず見る。**

### 4. 結果を提示する

- **不足がある場合** → 見つかった不足を**一覧でユーザーに提示してから**直しに入る（手順5へ）
- **不足がない場合** → 何も書き換えない。
  **「不足のない要求定義書が既にある」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのかも一緒に伝える（当てた観点と、その結果を示す）

### 5. 不足を埋める

1件ずつ「質問 → ドラフト → 赤入れ → 確定 → ファイルへ書く」で進める。

- 埋めるのに必要な事実は**ユーザーに聞く**。推測で埋めない
- 「まだ決まっていない」と言われたら、選択肢を2〜3案に絞り、推す案に `（推奨）` と理由を添えて聞き直す。
  それでも決まらないなら、持ち帰るか暫定で決めるかを**ユーザーに選んでもらう**
- 一度に聞くのは2件まで。まとめて並べない
- **直した箇所はその都度ファイルへ書く。**まとめて最後に書かない

### 6. ユーザーの承認をもって完了とする

直した内容を報告し、承認を得て終わる。自分の判断で締めない。

- 何が足りず、どう直したかを短く一覧で見せる
- 決着させた未確定事項があれば、何をどう決めたかも見せる
- 「これで02（要件定義）へ進んでよいか」を確認する

## 点検の観点

### A. 章と項目が揃っているか

| 章 | 揃っているべきもの |
|---|---|
| 冒頭 | Vモデル上の位置と、この文書で何を定義するかの引用ブロック |
| 1. 背景・課題 | 背景 / 現状 / 課題一覧（`# / 課題 / 影響度 / 優先度`） |
| 2. ゴール | ビジネスゴール / ユーザーゴール / 成功指標（`指標 / 目標値 / 測定方法`） |
| 3. ペルソナ | 属性表（名前・年齢・職業・部門・技術スキル）/ 目標・ゴール / ペインポイント / 利用状況（`利用場面 / 頻度 / 詳細`） |
| 4. ユーザージャーニー | mermaid `journey` 図 / メインフロー表（`# / フェーズ / 行動 / 課題・感情 / 解決`）/ 感情の変化（開始時・つまずき・ブレークスルー・達成時） |
| 5. 利害関係者 | 表（`利害関係者 / 期待`） |
| 末尾 | 次のステップ |

**行数や箇条書きの数は問わない。**「項目があるか」だけを見る。

### B. 章をまたいだ一貫性

- 1章の課題が、2章のゴールと4章のジャーニーで解決されているか
- 1章の課題一覧のうち、どこでも解消されていないものが残っていないか
- 3章のペルソナのペインが、1章の課題一覧と食い違っていないか
- 3章の技術スキル・利用頻度と、4章の行動が噛み合っているか

### C. ユーザージャーニー（最も漏れが出る）

**流れの途切れ**

- 各行の終わりの状態が、次の行の始まりになっているか。間に飛びがないか
- 始まりと終わりが書けているか
- **入口を探し直す。**書かれている以外のきっかけで使い始める経路が無いか
  （通知から / 人に言われて / 別の作業の途中で、など）

**矛盾**

- 「感情の変化」の4点と、メインフロー表の「課題・感情」列が同じ話をしているか
- mermaid図と、メインフロー表の行が対応しているか
- 図のスコアが**満足度**（1 = つらい、5 = 満足）として一貫しているか。
  所要時間や重要度で振られていないか

**不足**

- 登場人物が複数いるなら、相手側の行動も出てくるか（片方だけの視点になっていないか）

> ここで**細かく割らせない。**大まかな行動の流れが追えれば足りる。
> 画面単位の操作や分岐条件が書かれていないことは不足ではない。

### D. 書いてはいけないものが混ざっていないか

- 機能一覧・画面遷移・データモデル・スキーマ・API・状態遷移 → 02以降の内容
- 技術選定・使用するライブラリやサービスの名前
- 実装計画・工数・担当分担

見つかったら「不足」ではなく**削除の提案**として出す。消す判断もユーザーに仰ぐ。

### E. 言葉の具体性

- 「使いやすく」「スムーズに」「効率的に」のような抽象語が、具体的な場面に置き換わっているか
- 02で「何を作るか」を起こせる記述になっているか
  （**実装に渡せる粒度までは要求しない。**そこは02の仕事）

### F. 未確定が残っていないか

- **「未定」「未確認」「TBD」「要検討」が1つも無いか。**
  要求定義書は全工程の最上位文書で、以降の文書はすべてここを前提に書かれる。
  残っていたら、そこを決めるところまでやって閉じる

## やらないこと

- 新規に書き起こす → `request-doc`
- 02以降の内容（機能一覧・受入基準・スキーマ）を要求する
- 文書の全面的な書き直し。不足を埋めるだけにとどめる

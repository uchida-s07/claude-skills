# product-vision（要求の常設文書）

`docs/product/vision.md` を作る・更新する。プロダクト全体について「誰の・どんな課題を・なぜ解決するか」を定義する常設文書で、要件（`requirements/`）と変更ごとの spec（`specs/`）はすべてここを参照する。
雛形は `${CLAUDE_SKILL_DIR}/template.md`。**章立てと表の列を見るための参考**であって、分量をそこに合わせにいかなくてよい。ただし ID の列の位置は `spec-check` が読むので変えない。
共通ルール（決め方・質問の作法・レビュー指摘の扱い）は `${CLAUDE_SKILL_DIR}/../product-requirements/rules.md` に従う。

## 大原則

1. **ゼロベースで組み直す。** 手元に既存の資料があっても、それを土台にしない。ユーザーが「この資料を踏まえて」と明示した場合と、旧 `01-request.md` を移行元にすると決めた場合（下の「旧文書からの移行」）だけ参照する。
2. **質問して埋める。ただし聞きっぱなしにしない。** 質問 → 答えを解釈してドラフトを書く → 「こう理解しました」と見せて赤入れしてもらう、を1セットにする。
3. **要件に渡せる粒度まで上げる。** 各章を書き終えるたびに「この記述から、要件（何を作るか）を起こせるか」を自問する。「使いやすく」「スムーズに」のような言葉が残っていたら、具体的な場面に置き換わるまで掘る。ただし実装に渡せる粒度までは求めない。
4. **「未定」「未確認」「TBD」を本文に残さない。** これは最上位の常設文書で、要件と spec はすべてここを前提に書かれる。この文書づくりのゴールは、未確定事項を決定まで持っていくこと。
5. **決めるのは人間。Claude は決めない。** 推奨案は出す（というより、そうすべき）。だがユーザーの承認なしに決定として書かない（rules.md 第10章）。
6. **機能・データモデル・画面・API・技術選定は書かない。** 「〜できること」まで。書きたくなったら、それは要件か spec の内容。
7. **ID は振り直さない・詰めない。** 課題 `P-n`、ゴール `G-n`、ジャーニー `J-n`。廃止は ID を取り消し線（`~~P-3~~`）にして行を残し、理由を変更履歴に書く。
8. **表を主体にする。** 散文は背景・感情の変化など、表にすると死ぬところだけ。日本語で書く。

## モード

| 引数 | 動き |
|---|---|
| なし | `docs/product/vision.md` が無ければ新規作成。あれば「更新か点検か」を聞く（点検なら手順5の点検だけを行う） |
| `update` | 課題・ゴール・非目標・ジャーニーの追加・変更・廃止。`/spec-new` から「この変更の目的に対応するゴールが vision に無い」と案内されたときにも使う |

`docs/` が無ければ、先に `/spec-setup` を案内して止める。

## 新規作成の手順

### 1. 旧文書からの移行を確かめる

旧 `01-request.md` があるか探す。あれば、**移行元にするかをユーザーに聞く**。
- 使う → 章を新形式に移し、課題・ゴール・ジャーニーに ID を振る。ゴールには「解決する課題」を書く。足りない章（非目標・変更履歴など）だけ質問する。移した内容もユーザーに確認してから確定とする。
- 使わない → 2 へ（ゼロから）。

### 2. 対象を1問で掴む

まず「何を作るのか / 誰のためか」だけを聞く。ここは白紙なので開かれた質問でよい。返ってきた一言から、以降の章のたたき台を自分で書ける状態にする。足りなければ2〜3往復して輪郭（何が起きたら成功か）を掴む。

### 3. 章ごとに「質問 → ドラフト → 赤入れ → 確定 → ファイルへ書く」

**1章 → 2章 → … と章順に進める。** 課題が決まらないとゴールが書けず、ペルソナが決まらないとジャーニーが書けない。
**1章確定するごとにファイルへ書く。** まとめて最後に書かない（`/clear` や中断で消えるため）。

### 4. 書き上がったら点検する（手順5へ）

## 更新（update）の手順

1. vision.md を全文読む。何を変えたいか（きっかけの spec 番号・Issue があればそれも）を聞く。
2. 変える箇所を「追加 / 変更 / 廃止」に分けて案を書き、ユーザーの赤入れを受ける。
   - 追加は次の番号を使う。**既存の番号は振り直さない。**
   - 廃止は ID を `~~G-2~~` の形にして行を残す。
   - 変更履歴に「日付 / 変更 / きっかけ」を1行書く。`updated:` を今日にする。
3. ゴール・課題・ジャーニーを変更・廃止した場合は、それを参照している常設要件（`docs/product/requirements/` の「対応する要求」）と、進行中の spec（`docs/specs/` の draft / approved）を grep で探し、影響の一覧を作る。
4. 点検する（手順5へ）。

## 5. 点検する（タイミング①）

1. `spec-check` を呼ぶ（Skill ツールで `spec-check`、引数 `all`）。vision の中の ID の重複・参照（ゴールの「解決する課題」、成功指標の「対応するゴール」）・未定の残り、要件からの参照切れ（廃止した項目を要件が参照している）が機械的に分かる。
2. `docs-review` を呼ぶ（Skill ツールで `docs-review`、引数 `vision ①`）。fork したサブエージェントが、章の揃い・課題→ゴール→ジャーニーの一貫性・ジャーニーの途切れ・混入・抽象語・非目標との矛盾・参照している要件への影響を見て、レポートを返す。
3. 両方の結果を合わせて、rules.md 第12章の「直し方」で進める。
   - レポートを一覧で見せてから直しに入る。矛盾はどちらを正とするかをユーザーに選んでもらう。
   - 1件ずつ直し、その都度ファイルに書く。一度に聞くのは2件まで。
   - ユーザーが「誤検知」「承知で進める」と判断した指摘は、理由を聞いて `docs/review-notes.md` の表に書く（spec-check の指摘はキーも書く）。
   - 直したら、影響した範囲だけ `spec-check` と `docs-review vision ①` をもう一度通す。**未解決の矛盾・欠落が0件になるまで繰り返す。**
   - ユーザーが「今回は飛ばす」と明示したときだけ省いてよい。その場合も `docs/review-notes.md` に「飛ばした」と書く。
4. 要件への影響（update の手順3、または点検で出た「別のレビューへ回す指摘」）があれば、直し方をユーザーと決める。
   - 要件の文言だけ直せば済む → `/product-requirements update`
   - 振る舞いが変わる → 新しい spec（`/spec-new`）
   - 決めた内容を報告に載せる（ここで要件は直さない）。

## 6. ユーザーの承認をもって完成とする

- 直した箇所を短く報告する。
- 決着させた未確定事項があれば、何をどう決めたかを一覧で見せる。
- Claude が決めて書いた箇所のうち、そのまま残ったものを一覧で見せ、承認を取る（赤入れが無かったこと＝承認ではない）。
- 次の一手を案内する：新規プロジェクトなら最初の機能を `/spec-new`（L ティア）、既存プロジェクトの導入なら `/product-requirements init`。

## 質問の作法

rules.md 第11章に従う。この文書で特に守ること：

- **記述で聞く**：背景・経緯・現場の実情・「いまどう回しているか」。答えがユーザーの頭の中にしかないもの。こちらの理解を先に置いてから聞く（「〜という理解で合っていますか。違う点を教えてください」）。
- **選択式（AskUserQuestion）**：方向性が2〜3通りに割れていて、どれを採るかで以降の記述が変わるとき。選択肢はその文脈に落とした具体案にし、妥当な案を先頭に「（推奨）」と理由1行。
- 一度に聞くのは2件まで。一度答えをもらったら、表や文章の形にして見せる。
- 業務側の事実（誰が運用するか、どの規模でやるか）は勝手に決めない。
- 「まだ決まっていない」と言われたら：2〜3案に絞る → 何が分かれば決まるかの一点を聞く → 持ち帰るか暫定で決めるかをユーザーに選んでもらう。ユーザーが「それでいく」と言うまで決定として書かない。

## 各章に必要な項目

**必要なのは「どの項目があるか」まで。分量は問わない。**

### 1. 背景・課題

| 項目 | 中身 |
|---|---|
| 背景 | 誰が、どんな状況で、何のためにこれを必要としているか。経緯まで |
| 現状 | いまその仕事がどう回っているか（無い状態でどう凌いでいるか） |
| 課題一覧 | 表: `ID / 課題 / 困っている人 / 影響度 / 優先度`。ID は `P-n`。困っている人はここでは役割で書けば足りる |

聞くこと：いまどう回しているか。何が一番困っているか。困っているのは誰か。

### 2. ゴール

| 項目 | 中身 |
|---|---|
| ゴール | 表: `ID / 種別（ビジネス / ユーザー）/ ゴール / 解決する課題`。ID は `G-n`。解決する課題は `P-n` で書く |
| 成功指標 | 表: `指標 / 目標値 / 測定方法 / 対応するゴール`。**厳密さは求めない** |

成功指標は「どうなったら成功と言えるか」が伝わればよい。測れないものは `—` や「運用で目視」でよい。**合否の線は要件の受入基準が引く**ので、ここで測り方を詰めるために章を止めない。

### 3. 非目標

表: `やらないこと / 理由`。**プロダクトとしてやらないこと**を書く。AI が気を利かせて作り込まないための線引きで、要件と spec はこれに反してはいけない。
聞くこと：似たプロダクトならやりそうだが、このプロダクトではやらないことは何か。なぜやらないか。

### 4. ペルソナ

**ペルソナはユーザーが創作する。Claude が作らない。** 名前・年齢・職業・技術スキルを勝手に置かず、ユーザーから受け取って表の形に整えるだけにする。ここは大原則2の例外で、**先に聞く**。
メインペルソナ1人が基本。別々の要求を持つアクターが複数いるなら複数立てる。何人にするかもユーザーが決める。

| 項目 | 中身 |
|---|---|
| 属性表 | 名前 / 年齢 / 職業 / 部門 / 技術スキル |
| 目標・ゴール | 箇条書き |
| 課題（ペインポイント） | 箇条書き。対応する `P-n` を併記する |
| 利用状況 | 表: `利用場面 / 頻度 / 詳細` |

### 5. ユーザージャーニー

| 項目 | 中身 |
|---|---|
| mermaid 図 | `journey`。スコアは**その場面での満足度**（1 = つらい、5 = 満足）。所要時間や重要度ではない |
| メインフロー | 表: `ID / フェーズ / 行動 / 課題・感情 / 解決`。ID は `J-n`。解決は機能名ではなく**体験で書く** |
| 感情の変化 | 開始時 / 最初のつまずき / ブレークスルー / ゴール達成時 |

大まかな行動の流れが追えればよい。画面単位の操作や分岐条件まで割らない。
書き終えたら、見せる前に流れを自分で点検する：各行の終わりが次の行の始まりになっているか / 始まりと終わりがあるか / 書かれている以外の入口（通知から・人に言われて・別の作業の途中で）が無いか / 図と表と感情の変化が同じ話をしているか / 登場人物が複数なら相手側の行動もあるか。埋まらない箇所は推測で埋めず、そこだけ質問する。

### 6. 利害関係者

表: `利害関係者 / 期待`。ペルソナ本人＋後工程＋承認する側。

### 変更履歴

表: `日付 / 変更 / きっかけ（spec 番号など）`。初版もここに1行書く。

## やらないこと

- 機能一覧・画面・データモデル・API・状態遷移 → 要件（`/product-requirements`）と spec（`/spec-new`）
- 技術選定・ライブラリやサービスの名前 → 要求が実装の都合に引きずられるため出さない（判断は ADR）
- 実装計画・工数・担当分担
- 要件の修正 → 影響の一覧を作り、直し方をユーザーと決めるところまで
- 旧フローの要求定義書（`01-request.md`）の作成・点検 → `request-doc` / `request-doc-review`

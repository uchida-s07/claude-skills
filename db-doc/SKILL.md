# データ構造・ファイルレイアウト設計づくり

Vモデルの **詳細設計**（対応する検証は単体テスト）にあたる文書を1本作る。
機能（②）・画面（③）が扱うデータを、**実装の土台になる構造**へ落とし込む。

成果物の骨組みは同ディレクトリの3つのテンプレート。**どれを使うかは手順1のDB確認で決まる。**
章立てと表の列を見るための参考であって、埋め方の指示書ではない。分量はそこに合わせにいかなくてよい。

| テンプレート | 使う場面 |
|---|---|
| `template-rdb.md` | RDB（PostgreSQL / MySQL / SQLite など）を使う |
| `template-document.md` | ドキュメントDB（Firestore / MongoDB / DynamoDB など）を使う |
| `template-file.md` | 永続化DBを持たない（ファイル出力・中間JSON・構造化データモデルのみ） |

**前提条件**: **仕様書（03）が存在すること。**無い状態でこのスキルを始めない。
（03は02を前提に作られるので、03があれば02もある。無ければ `spec-doc` へ回す）
**使う場面**: 要件（02）と仕様書（03）が固まり、実装に入る前。データの器を確定させるとき。

## このスキルの進め方（他の文書スキルと違うところ）

**人間に判断を仰ぐのは、最初と最後の2回。加えて、重大な確認事項が出たときだけ完了前にもう1回。**

1. **最初**: 「今どのDBを使っているか／これから何を使うか」を確認する。
   これだけは推測で進めない。**設計の形そのものが変わるため。**
2. **途中**: Claudeが01・02・03を正典として**全章を最後まで自律的に書き切る。**
   章ごとに「これでいいですか」と伺いを立てない。判断が要る箇所は決めて書き、
   **決めた事実を記録しておく。**
3. **完了前**: 書く過程で**重大な確認事項**（後から直すとデータ移行が要る／取り返しがつかない）
   が出ていたら、**設計を完了させる前にまとめて確認する**（手順4）。
   出ていなければこの段は飛ばす。**「重大」の線引きは手順4の表が正典。**
   軽い判断まで持ち込むと自律の意味が消えるので、そこだけは厳しく絞る。
4. **最後**: 完成品をユーザーがレビューする。
   このときClaudeは **「自分で決めた箇所」の一覧を必ず添える**（手順6）。

> ここで数えているのは**設計の中身についての判断**。
> 「どのファイルを対象にするか」「既存の04を上書きしてよいか」のような
> **作業の段取りの確認（手順0）は、いつ聞いてもよい。**

要件定義スキルのように1章ずつ見せて赤入れを受ける進め方は**しない。**
DB設計は章どうしの依存が強く（一覧 → 関連図 → 定義 → インデックス）、
途中で1つ変えると全章に波及する。**通しで書き切ってから、まとめて直す方が速い。**

## 大原則

1. **入力は 01・02・03。無ければ着手しない。** **03（仕様書）が必須。**
   画面に出る項目・並び順・絞り込みが、器とインデックスの根拠になるため、
   03を見ずに04は書けない。02（要件定義書）も必ず併読し、01（要求定義書）は背景の確認用。
   03が見当たらなければ探し、それでも無ければ**この文書を書き始めず** `spec-doc` へ案内する
   （02すら無ければ `requirement-doc` から）。
   02・03に穴があるだけなら、04の中で補わず
   **`requirement-doc-review` / `spec-doc-review` で上流を直してから**戻ってくる。
2. **DBの現状は推測せず、実物を見てから聞く。** 白紙で「どのDBを使いますか」と投げない。
   **先にリポジトリを調べ、「現状こう見えますが合っていますか」の形で確認する**（手順1）。
   既存プロジェクトなら、既にあるスキーマが**設計の入力**になる。
3. **DBを持たない選択も設計である。** 「DB不要」と判断したら、
   **なぜ不要か（要件のどこから導けるか）**と、**将来必要になったときの逃げ道**を冒頭に書く。
   黙って省略しない。
4. **トレーサビリティを切らさない。** 1章の各行に「関連機能(②)」を必ず書く。
   逆向きにも照合する — **02の全機能が、どこかのデータストアに対応している**こと。
   対応するデータストアが無い機能があるなら、02に抜けがあるか、器を立て忘れている。
   **03の画面が表示する項目・並び順・絞り込み条件も、すべて器があるか確かめる。**
5. **「どういう構造か」まで。「動くコード」は書かない。**
   CREATE文・マイグレーション・Pydantic/Dartのモデル実装・ORMの定義は Build フェーズ。
   本書は**定義表・関連図・制約・配置**までを正とする。
   末尾にその線引きを1行で書き添える。
6. **制約を空欄にしない。** PK / FK / NOT NULL / UNIQUE / DEFAULT / ON DELETE を埋める。
   ここを曖昧にすると実装者が握りつぶす。NULLを許すなら**許す理由**を説明列に書く。
7. **列の説明に「なぜ」を書く。** `created_at: 作成日時` で終わらせない。
   その項目がどの機能・受入基準を支えているかまで書けたら書く。
8. **「未定」「TBD」「要確認」を本文に残さない。**
   決め切れないものも**暫定で決めて書き、決めた箇所として手順6で申告する。**
   保留を本文に残すと、下流のAPI設計・実装がそこで止まる。
   **ただし「重大な確認事項」だけは暫定で押し切らず、完了前に聞く**（手順4）。
   聞くと決めた項目も、**本文には暫定案を書き込んだうえで**印を付けておく
   （空欄にして手を止めない。回答が来たら差し替える）。
9. **表を主体にする。** 散文は章冒頭の「目的」と、表にすると死ぬ補足だけ。
10. 日本語で書く。ただし**識別子（テーブル名・カラム名・キー）は実装で使う表記のまま**書く。

## 手順

### 0. 既存の設計書があるか確認する

`docs/requirements/` などに `04-db.md` が既にあるか探す。
**候補が複数見つかったら、どれのことかユーザーに聞く。**

- **ある** → 上書きしてよいか確認する。改訂なら差分で直す（全面書き直しをしない）
- **ない** → 1へ進む

### 1. DBの種類と現状を確認する（**ユーザーに聞く最初の場面**）

**まず自分で調べる。**聞くのは調べた後。

調べる先（あるものだけ）:

- スキーマの実体 — `schema.sql` / `migrations/` / `prisma/schema.prisma` /
  `*.entity.ts` / `models.py` / `firestore.rules` / `firestore.indexes.json`
- 接続設定 — `docker-compose.yml` / `.env.example` / `application.yml` / 依存パッケージ
  （`pubspec.yaml`・`package.json`・`requirements.txt`・`go.mod` にDBドライバがあるか）
- データアクセス層のコード — 実際に読み書きしているパス・コレクション・テーブル名。
  **設定に無くてもコードが正**（ドキュメントDBは特にここでしか分からない）
- 02の非機能要件・03の技術方針 — 既にDBが名指しされていないか

調べた結果を**先に提示してから**、`AskUserQuestion` で確認する。**一度に聞くのは2件まで。**

| 聞くこと | 選択肢の作り方 |
|---|---|
| DBの種類（必須） | 調査で見えたものを `（現状）` 付きで先頭に置く。見えなければ、02の非機能要件から妥当なものを `（推奨）` 付きで先頭に置く。**「DBを持たない」も選択肢に入れる**（単一ユーザーCLI・1実行完結の処理なら本命） |
| 既存スキーマの扱い（既存プロジェクトのみ） | `現行を踏襲して足す` / `新スキーマへ移行する` / `新旧併存（移行途中）` |

**確認できたこと**（DBエンジン・バージョン・既存スキーマの範囲・移行方針）を短くまとめ、
使うテンプレートを宣言してから2へ進む。**ここから先は、手順4の「重大な確認事項」に当たらないかぎり聞かない。**

> 既存スキーマが現に動いている場合、**それは制約であって設計対象ではない。**
> 変えるなら「なぜ変えるか」と「移行の段取り」を本文に書く。黙って別の形に描き直さない。

### 2. 01・02・03 を読む

- 03（仕様書）を**全文読む**。画面ごとの仕様まで。**画面に出る項目・一覧の並び順・
  絞り込み条件・状態表示は、そのまま器とインデックス方針の根拠になる。**
  モック（`mocks/mockup.html`）があれば、本文に無い項目が出ていないかも見る。
- 02（要件定義書）を**全文読む**。機能一覧・各機能の要件・スコープ・非機能要件のすべて。
- 01（要求定義書）は背景の確認用。ペルソナ・ジャーニーから、
  **誰のデータをどの単位で分けるか**（テナント境界・物件単位・ユーザー単位）を読み取る。

読み終えた時点で、**全章を最後まで書き切れる状態**にする。
足りない情報は02・03の記述から**導く**。導けないものは暫定で決める（大原則8）。

### 3. 全章を自律的に書き切る

**その場では質問しない。**手順1で形は決まっている。01〜03から器を起こすのはClaudeの仕事。
重大な判断に当たっても、**書く手を止めずに印を付けて進む**（下記）。
空欄・`{}`・「TBD」を残したまま出さない。

書く順序（依存の順）:

0. **命名規約を先に決める** — 単数形か複数形か、スネークかキャメルか、真偽値は `is_` か。
   **1章で名前を書き始める前に決める**（後から揃え直すと全章に波及する）。
1. **1章（一覧）** — 02の機能一覧を1行ずつ舐め、その機能が読み書きするデータを列挙する。
   同じものは1つに束ねる。「関連機能(②)」を埋めながら書くと、抜けがその場で見える。
2. **2章（関連図）** — mermaid `erDiagram` で書く。1章に出したものを**1つ残らず**登場させる。
   図に出ていない＝どこにも繋がっていない、なので必ず気づける。
3. **3章（定義）** — 1つずつ表に落とす。ここが本体。**各定義の頭に「目的」を1〜2文**置く。
4. **4章（インデックス／ファイルレイアウト）** — 形によって中身が変わる（下の「各章に必要な項目」）。
5. **5章（正規化・永続化・整合性の方針）** — 非正規化したなら理由を、
   DBを持たないなら将来の逃げ道を書く。
6. **末尾** — 「動くDDL/実装はBuildフェーズの成果物」の1行と「次のステップ」。

**判断したことは、その場で作業メモに残す**（どの項目を02から起こし、どこを自分で決めたか）。
手順6でそのまま使う。**重大な確認事項に当たったものは、メモ上で分けておく**（手順4で使う）。

**手を止めない。**重大な判断に行き当たっても、そこで質問して待たない。
**暫定案を書き込んで印を付け、残りを最後まで書き切ってから**手順4でまとめて聞く。

**印は `<!-- ASK: 何を確認したいか -->` のHTMLコメントで入れる。**
本文の表示には出ないので、途中で中断されても文書が壊れない。
**「要確認」「TBD」の語は本文に書かない**（大原則8のgrepに引っかかり、
本当の書き残しと区別できなくなる）。

**書いたらファイルへ。**まとめて最後に書かない（`/clear` や中断で消えるため）。

### 4. 重大な確認事項があれば、完了前に確認する

**該当が無ければこの手順は飛ばす。**（飛ばしたこと自体は報告しなくてよい）

#### 何が「重大」か

次の**どちらかに当てはまるものだけ**が重大。**両方に当てはまらないものは聞かずに決める。**

- **後から直すと、コードだけでなく既に入っているデータの移行が要る**
- **間違えたときに取り返しがつかない**（消えたデータが戻らない・法令や規約に触れる）
- **01〜03にもコードにも根拠が無く、ユーザーの頭の中にしかない業務の事実に依存する**
  （推測で書くと、根拠の無いものが決定として下流へ流れる）

具体的には次のとおり。

| 重大（完了前に聞く） | なぜ |
|---|---|
| **データの分離単位・所有者**（テナント／組織／ユーザーのどれで分けるか） | 後から変えると全データストアに波及し、既存データの振り分けが要る |
| **主キー・識別子の決め方**（自動採番か業務キーか。外部システムのIDを主キーにするか） | 参照している側すべてに波及する。業務キーは後から変わりうる |
| **既存スキーマを変更・移行する必要が出たとき** | 動いているものを壊す。移行の段取りと停止時間の判断が要る |
| **削除の方針**（物理削除か論理削除か。参照先が消えたときCASCADEするか） | 物理削除・CASCADEは復元できない |
| **個人情報・秘密情報を持つか、どこに置くか、いつまで残すか** | 法令・規約・社内規程が絡む。Claudeが決めてよい範囲を越える |
| **02・03どうしが矛盾していて、どちらかを選ばないと器が決まらないとき** | どちらを正とするかは上流の判断。器を先に決めると誤りが固定される |
| **スコープ外にはみ出す器を作らないと成立しないと判明したとき** | 作らないと決めたものを勝手に作ることになる |
| **業務の事実を知らないと決められないもの**（想定件数の桁・扱う単位・現場の運用） | 推測すると桁違いの構造になる。**ユーザーの頭の中にしかない** |

| 重大でない（聞かずに決めて手順6で申告） | なぜ聞かなくてよいか |
|---|---|
| 列名・テーブル名の表記、`created_at` / `updated_at` の有無 | あとで直せる |
| インデックスを足す・複合にする判断 | データ移行を伴わない。あとから張れる |
| NULL許容の細部、既定値の選び方 | あとで直せる |
| 非正規化の程度（同じ項目を2か所に持つか） | 移行が軽い範囲なら決めてよい。**分離単位に触れるなら重大側** |
| 説明文・目的の書き方 | 文書の記述であって構造ではない |

> 迷ったら**「これを後から変えるとき、既存データをどう動かすか」を1文で言えるか**を考える。
> 言えない（＝移行が要る）なら重大。言える（＝定義を書き換えるだけ）なら聞かない。

#### 聞き方

- **全章を書き切ってから、まとめて聞く。**見つけた時点で止めない（手順3）。
- `AskUserQuestion` で、**一度に聞くのは2件まで。**3件以上あれば**影響の大きい順**に刻む。
- 選択肢は**その設計の文脈に落とした具体案**にする。抽象語で聞かない。
  妥当な案を先頭に置き `（推奨）` を付け、**各案に「これを採ると何が変わるか」を一言添える。**
  暫定で本文に書き込んだ案がどれかも明示する。
- **なぜ聞くのかを1行で言う**（「後から変えると全テーブルの移行が要るため」）。
  聞かれた側が、重さを判断できるようにする。
- 「まだ決まっていない」と言われたら、**何が分かれば決まるのかを言語化して、その一点だけ聞く。**
  それでも決まらないなら、**持ち帰るか暫定で確定させるかをユーザーに選んでもらう。**
  暫定で確定させる場合は、**そう決めた事実と、後で変えるときの影響を本文に1行残す。**

#### 答えが返ったら

- **本文の暫定案を差し替え、印を消す。**
- **波及を必ず追う。**1章の一覧・2章の関連図・3章の定義・4章のインデックス（またはファイルレイアウト）・
  5章の方針 — **この5箇所がそろって直っているか**を毎回確認する。ここが最も取りこぼす。
- 差し替えた内容は、手順6の「決めた箇所の一覧」に**ユーザーが決めたもの**として載せる
  （Claudeが決めたものと混ぜない）。

### 5. 自己点検する

ユーザーに見せる前に、**Claudeが自分で通す。**

- [ ] 02の**全機能**が、1章のどれかの「関連機能(②)」に現れているか
- [ ] 1章の**全データストア**が、2章の関連図と3章の定義に現れているか（3か所で数が合うか）
- [ ] 03の画面が出す項目・並び順・絞り込みが、**すべて器を持っているか**
- [ ] FKの参照先が実在するか。`ON DELETE` の挙動を決めてあるか
- [ ] 一覧・検索の絞り込み条件に、4章のインデックスが対応しているか
- [ ] 02の非機能要件（認証・秘密情報・保持期間）が構造に反映されているか
      （パスワードはハッシュで持つ・個人情報の置き場・ログの保持単位）
- [ ] 「未定」「TBD」「要確認」「{」が本文に残っていないか（**grepで確認する**）
- [ ] 動くDDL・実装コードを書いていないか（設計書の範囲を越えていないか）
- [ ] **手順4の印が1つ残らず消えているか**（`ASK:` でgrepする。暫定案が残っていないか）

引っかかったら**直してから**6へ進む。「点検したら見つかりました」と報告して終わらない。

### 6. ユーザーにレビューを依頼する

**ここが人間の出番。**成果物とあわせて、次の3つを必ず出す。

1. **決めた箇所の一覧** — 「何を・どう決めたか・なぜそう決めたか」を表で。
   **手順4でユーザーが決めたもの / Claudeが決めたもの / 01〜03に根拠があるもの**の3つを
   区別して見せる。**レビューの時間はClaudeが決めたものに使ってもらう。**
2. **迷った箇所と、採らなかった案** — 特に非正規化・分割・NULL許容・削除時の挙動。
   「A案（採用）／B案（不採用、理由）」の形で1行ずつ。
3. **02・03に対して気づいた不足** — 04を書く過程で見つかった上流の穴
   （「FUNC-05の受入基準にある並び順が、02では定義されていない」など）。
   **04の中で勝手に補わず、上流を直すべきものとして報告する。**

**レビュー結果はその場でファイルに反映する。**指摘を溜めない。
反映後、変えた箇所を一覧で見せて**承認をもって完成**とする。自分の判断で締めない。

### 7. 次の工程を案内して終わる

承認が取れたら、**最後に必ず次を伝える。**言わずに締めない。

> 04が固まったので、**次は `api-ipo-doc` スキルで 05（API・IPO一覧）を作成できます。**
> API一覧を整理し、業務フローごとの Input / Process / Output を紐付ける文書で、
> 04で決めた器を、どのインターフェースがどう読み書きするかを確定させます。
> こちらもClaudeが01〜04から一括で書き上げ、ユーザーはレビューだけを行います。

**走らせるかはユーザーが決める。**このスキルの中で勝手に起動しない。
走らせると言われたら `api-ipo-doc` へ切り替える。

## 各章に必要な項目

**必要なのは「どの項目があるか」まで。分量は問わない。**
章タイトルは**形態に合わせて言い換える**（下表）。

| # | RDB | ドキュメントDB | DBなし |
|---|---|---|---|
| 冒頭 | 引用ブロック（Vモデル・前提） | 同左 | 同左＋**DBを持たない理由と逃げ道** |
| 1 | テーブル一覧 | コレクション一覧 | データストア一覧 |
| 2 | ER図 | データモデル関連図 | データモデル関連図 |
| 3 | テーブル定義 | ドキュメント定義 | データ構造定義 |
| 4 | インデックス方針 | インデックス・クエリ方針 | ファイルレイアウト |
| 5 | 正規化・整合性の方針 | 非正規化・整合性の方針 | 正規化・永続化の方針 |
| 末尾 | 次のステップ | 同左 | 同左 |

### 冒頭の引用ブロック

```
> Vモデル: 詳細設計 / 対応する検証: 単体テスト
> 機能（②）・画面（③）が扱うデータを、実装の土台となる構造に落とし込む。
```

さらに**前提**を続ける。DBエンジンが未確定なら「特定のクラウド構成に依存しない汎用的な型で設計する」、
**DBを持たないなら「なぜ持たないか（要件のどこから導けるか）」と「将来の逃げ道」**を数行で書く。

### 1. 一覧

表: `名前 / （DBなしなら）実体 / 目的 / 関連機能(②)`

- **目的**は1〜2文。「何を持つテーブルか」ではなく「**何のために**持つか」。
- **関連機能(②)** は `FUNC-01` の形で02を指す。02に無い呼び名を発明しない。
- 全機能の前提になるマスタは `FUNC-01〜09（全機能の前提）` のようにまとめてよい。

### 2. 関連図

mermaid `erDiagram`。**1章に出したものを全部描く。**

- リレーションの読み方（`has` / `belongs to` / `manages`）をラベルで書く。
- 各エンティティのブロックには**主要な項目だけ**書く（PK・FK・識別子・状態）。
  全列を書き写す場所ではない（それは3章）。
- ドキュメントDB・DBなしの場合は、リレーションではなく**入れ子（コンポジション）**を描く。
  `||--o{` を「1ドキュメントの中に配列で持つ」意味で使い、**図の直前でそう断る。**

### 3. 定義

対象1つにつき小見出しを立て、**「目的」を1〜2文**書いてから表を置く。

| 形態 | 表の列 |
|---|---|
| RDB | `カラム / 型 / 制約 / 説明` |
| ドキュメントDB | `フィールド / 型 / 必須・既定 / 説明`（サブコレクションは別の小見出しに切る） |
| DBなし | `フィールド / 型 / 制約 / 説明`（利用者に渡る成果物があるなら `日本語ラベル` 列を足す） |

共通で守ること:

- **型は具体的に。** `string` `text` `integer` `datetime` `boolean` を使い分ける。
  列挙値は `Literal[...]` や「`unanswered`=未対応 / `answered`=対応済み」の形で
  **取りうる値を全部書く。**
- **制約は必ず埋める。** `PK` / `FK(table.column)` / `NOT NULL` / `UNIQUE` /
  `DEFAULT ...` / `ON DELETE ...`。表に収まらない複合UNIQUEは**表の下に引用で添える。**
- `created_at` / `updated_at` を持つかどうかを、対象ごとに決める（ログ系は `created_at` だけ、など）。
- **命名規約を先に決めて、全体で揃える。** テーブル名は複数形か単数形か、
  スネークケースかキャメルケースか、真偽値は `is_` 接頭辞か。
  実装キーと**利用者に見える日本語ラベル**が別なら、その対応表を作って**写像の場所を明示する。**
- 説明列に、**その項目が支えている機能・受入基準**を書けるなら書く（`FUNC-07の集計対象` など）。

### 4-A. インデックス方針（RDB / ドキュメントDB）

表: `テーブル（コレクション） / カラム（フィールド） / 理由`

- **UNIQUE制約で自動的に張られるものは、その旨を先に1行書いてから**、明示的に足すものを表にする。
- 理由は**どのクエリのためか**まで書く（「一覧取得で毎回絞り込む」「削除時の参照検索」）。
- RDBなら、FKに自動でインデックスが付くかはエンジン差があることに触れる
  （PostgreSQLは付かない / MySQL(InnoDB)は付く）。
- ドキュメントDBなら**複合インデックスと、クエリ制約から来る構造上の制限**を書く
  （複合クエリの可否・`array-contains` の個数制限・セキュリティルールで絞れる形になっているか）。

### 4-B. ファイルレイアウト（DBなし）

ディレクトリツリーをコードブロックで描き、**各ディレクトリの役割を右側のコメントで書く。**
ツリーの下に、読み書きの規律を箇条書きで置く:

- 読取専用にする場所（入力の原本を改変しない）と、書込を許す場所
- 生成物のファイル名規則（**どの入力に対応する出力かを名前で保証する**）
- 中間ファイルの位置づけ（実行状態か、捨ててよいキャッシュか）

### 5. 正規化・永続化・整合性の方針

形態ごとに書くことが違う。**該当するものだけ書けばよい。**

| 形態 | 書くこと |
|---|---|
| RDB | 正規化の程度と、**あえて崩した箇所とその理由**。トランザクション境界。削除は物理か論理か |
| ドキュメントDB | **非正規化した項目と、その同期をどこで担保するか**（書込時にまとめて書く／集計は別処理）。ドキュメントサイズと配列の上限に触れる |
| DBなし | 正規化が対象外である理由。何を永続化し、何を捨てるか。**将来DBが必要になったときの移行先と写像**（どの構造がどのテーブルになるか） |

### 末尾

設計書の範囲を切る一文を引用で置く（形態に合わせて言い換える）:

```
> 実際に動く CREATE 文（DDL）は Build フェーズの成果物として `db/schema.sql` などに作成する。
> この設計書ではテーブル定義表・ER図・制約までを正とする。
```

そのうえで「次のステップ」:

```
→ `05-api-ipo`（API・IPO一覧・詳細設計）でフローごとのIPOとAPI一覧を作成する
→ 必要に応じて `02-requirement`（要件定義書）の「対応テーブル」欄を追記更新する
```

文書の連番が違うプロジェクトでは、その次工程の名前に合わせる。

## やらないこと

- **動くDDL・マイグレーション・ORM定義・モデル実装コードを書くこと** → Buildフェーズ。
  本書は定義表・関連図・制約まで
- **要件定義書（02）の不足を埋めること** → `requirement-doc-review`。
  04の中で機能や受入基準を足さない（気づいたら手順6で報告する）
- **画面構成・モックHTML** → 仕様書（03）。`spec-doc` の仕事
- **APIエンドポイント・リクエスト/レスポンス定義・IPO** → API設計（05）
- **テストケース・テスト手順** → シナリオテスト（06）
- **章ごとにユーザーの承認を取りながら進めること** → このスキルは手順1と手順6でだけ人間に渡す（重大な確認事項があるときだけ手順4を挟む）
- **DBエンジンやクラウド構成の選定・比較検討** → インフラ設計（07）。
  手順1で聞いて決まったものに従う。決まっていなければ**依存しない汎用的な型で設計する**
- **テストデータ・初期投入データの作成** → 別作業

# シナリオテスト仕様書のレビュー（システムテスト）

対象は **`06-scenario-test.md` 1本**。**新規に書き直さない。**既にあるものに観点を当て、**不足だけを埋める。**

作成は `scenario-test-doc` スキルの仕事。まだ文書が無いならそちらへ回す。

**02（要件定義書）・03（仕様書）・05（API/IPO一覧）・04（データ構造設計書）は照合用に必ず読む。**
06は「②の受入基準を、③の画面と⑤のインターフェースを使って人が判定できる手順に翻訳した文書」なので、
上流を見ずに過不足は判定できない。とくに**02は必須**（受入基準と例外が、
シナリオの Then と異常系の**唯一の根拠**になる）。
ただし**直すのは06だけ。**02側は `requirement-doc-review`、03側は `spec-doc-review`、
04側は `db-doc-review`、05側は `api-ipo-doc-review` へ回す。

**06は実行される文書。**読んで分かるかではなく、**そのとおり操作できるか**で見る。
「意味は通るが、実施者がその場で手が止まる」記述は不足として扱う（観点E）。

## 作成スキルから呼ばれたとき

`scenario-test-doc` の手順8は、**提出前にこのスキルを必ず1回通す。**
そのときは進め方を次のように変える。

- **手順1の対象特定は飛ばしてよい**（対象・上流の場所は呼び出し側が知っている）。
- **観点を当てて、指摘の一覧を呼び出し側へ返すところまでが仕事。**
  そこで**ユーザーに承認を求めない**（承認は作成スキルの手順9で1回だけ取る）。
- **02〜05から一意に導ける不足は、そのまま直してよい**（原則3の範囲）。
  導けない不足は、**作成スキル側の「重大な確認事項」へ積み直す**（自分で聞きに行かない）。
- 返すもの: **当てた観点 / 見つかった不足 / 直した内容 / 判断が要るので積み直したもの**。

呼び出し側から独立して（ユーザーが直接このスキルを起動して）使うときは、以下の手順どおり進める。

## 大原則

1. **全部読んでから判断する。**一部だけ見て「足りている」と言わない。
   **02・03・05・06**を通しで読む（04は画面から見えない検証の裏取りに、01は `対応要求(①)` を見るときに）。
2. **正典は02の受入基準。**06の良し悪しは、**「②を満たしたと言えるか」を人が判定できるか**だけで決まる。
   テスト技法として洗練されているかは見ない。
3. **勝手に書き足さない。**不足を埋めるには判断が要る。
   ただし**02〜05から一意に導ける記述**は、聞く前に案を書いて見せてよい
   （02の例外に対応する異常系が無い、03のエラー文言が Then に落ちていない、など）。
4. **決めるのは人間。**推奨案は出してよいが、承認なしに決定として書かない。
5. **指摘は場所と一緒に出す。**「TEST-04 の手順2の Then に表示文言が無い」のように、
   **どのTESTの・何行目の・何が足りないかを名前で言う。**
6. **テスト設計の好みでは指摘しない。**「自分ならシナリオをこう割る」は不足ではない。
   指摘するのは、**②の受入基準を判定できない**か、**実施者が手を止める**か、
   **上流と食い違う**場合だけ。
7. **シナリオを実行しない。判定欄を埋めない。**
   `☐Pass / ☐Fail` は空のまま渡すのが正しい状態。**実行するのは人間。**
   実行しないと分からない指摘（「これは実際にはFailするはず」）は、**書かない。**
8. **自動テストコードが無いのは不足ではない。**単体テスト・E2Eスクリプトは Build の成果物。
   **06にコードが書いてあるほうを疑う**（混入。観点K）。
9. **★設計未対応が書いてあること自体は不足ではない。**むしろ**06が仕事をした証拠**。
   見るのは**書き方**（原因の切り分けまで書けているか）と、**冒頭の注記に載っているか**だけ。
   **消させない。**
10. **02〜05の内容を蒸し返さない。**機能の切り方・画面の切り方・API設計への異議は
    このレビューの範囲外。06が上流を正しく写しているかだけを見る。

## 手順

### 1. 対象を特定する

`docs/requirements/06-scenario-test.md` など、文書の場所を確認する。
複数あるなら、どれを見るのかユーザーに聞く。見つからなければ、
**まだ作成の段階なので `scenario-test-doc` を使うよう案内して終了する。**

あわせて次も特定する。

- **対になる 02・03・05・04。**照合の土台なので、無ければ観点B・C・D・G・Hを当てられない。
  **02が無ければ点検そのものが成立しない**（受入基準が正典のため）ので、
  先に `requirement-doc` へ回す。03〜05が欠けている場合は、そのことを伝えたうえで、
  残りの観点だけで点検するか先に上流を作るかを**ユーザーに選んでもらう**
  （欠けた側の観点を飛ばしたことは必ず伝える）。
- **実行形態**（Web / モバイル / CLI・バッチ）。前提環境の「対象」と05の1章から判定する。
  **観点Eの当て方が変わる**（画面の文言を見るのか、標準出力とログを見るのか）。
- **Build 成果物の有無**（観点J）。無ければその観点を飛ばす。

### 2. 全部読む

飛ばし読みしない。06を冒頭の引用ブロックから「次のステップ」まで通し、**02・03・05も通しで読む。**
02は受入基準と例外・バリデーションとスコープまで、03は画面ごとの操作と**エラー表示の文言まで**読む。

**読みながら、02の受入基準と例外を全部書き出す。**これが観点B・Dの照合表になる。

### 3. 観点を当てる

下の「点検の観点」を全部当てる。
**B（カバレッジ）・C（受入基準との対応）・D（異常系の網羅）・E（実行可能性）・
F（前提環境と初期データ）は漏れが最も出るので必ず見る。**

機械的に確かめられるものは、目視より先にコマンドで潰す（「機械的に潰せるもの」）。

### 4. 結果を提示する

- **不足がある場合** → 見つかった不足を**一覧でユーザーに提示してから**直しに入る（手順5へ）。
  一覧は**判定の中身に波及するもの（シナリオの追加・Then の変更・初期データの追加）と、
  記述の不足（トレーサビリティ欄・出どころの注記の書き漏れ）を分けて**出す。
  **前者を先に直す**（後者は前者の結果で変わるため）。
- **不足がない場合** → 何も書き換えない。
  **「不足のないテスト仕様書が既にある」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのかも一緒に伝える（当てた観点と、その結果を示す）。

### 5. 不足を埋める

1件ずつ「（必要なら質問 →）ドラフト → 赤入れ → 確定 → ファイルへ書く」で進める。

- **02〜05から一意に導ける不足は、先に案を書いて見せる**（原則3）。
  「02の FUNC-03 の例外『本文が空』に対応する異常系が無いので、TEST-07 を足す案です」の形。
- 導けない事実（テスト環境の在り処・実行できる資格情報・非機能要件の水準・
  外部への送信をどう扱うか）は**推測で埋めず聞く。**
  「まだ決まっていない」と言われたら、選択肢を2〜3案に絞り、推す案に `（推奨）` と
  理由を添えて聞き直す。それでも決まらないなら、持ち帰るか暫定で決めるかを
  **ユーザーに選んでもらう。**
- **シナリオを増減させたら、波及を必ず追う。**カバレッジ表・本文のTEST-ID・
  初期データ・他シナリオの Given が参照している依存 — **この4箇所がそろって直っているか**を
  毎回確認する。**ここが最も取りこぼす。**
- **TEST-IDを振り直さない。**途中に足すなら**末尾に採番して**カバレッジ表から参照する。
  振り直すと、実施済みの記録・他文書からの参照が全部ずれる。
- 一度に聞くのは2件まで。まとめて並べない。
- **直した箇所はその都度ファイルへ書く。**まとめて最後に書かない。

### 6. ユーザーの承認をもって完了とする

直した内容を報告し、承認を得て終わる。自分の判断で締めない。
（**作成スキルから呼ばれたときは、この手順を飛ばして呼び出し側へ返す。**）

- 何が足りず、どう直したかを短く一覧で見せる（シナリオの追加・変更 / 記述の追加を分ける）
- 決着させた未確定事項があれば、何をどう決めたかも見せる
- **★設計未対応の一覧を、あらためて見せる**（消していないこと・原因の切り分けが書けていること）
- **02・03・04・05側に見つけた不足があれば、直さずに報告する**（振り先のスキル名も添える）
- 「これでBuild／テスト実行へ進んでよいか」を確認する
- **★設計未対応や上流の不足が1件でもあれば、上流の直しを先にすることを勧める。**
  02×03の食い違いは `requirement-spec-crossreview`、04×05は `db-api-crossreview` が、
  **文書を書き換えずにどちらを直すべきかの指摘だけ**を出す。
  **走らせるかはユーザーが決める**（勝手に起動しない）

## 点検の観点

### A. 章と項目が揃っているか

| # | 章 | 見ること |
|---|---|---|
| 冒頭 | 引用ブロック | Vモデル上の位置（システムテスト / ②要件定義）と、**「Buildした実アプリに人が手で実行する」**の明記 |
| — | 使い方（実施者向け） | 起動 → 実行 → 判定記録 → 原因切り分け → 全Passの意味 |
| — | 注記（対象範囲について） | **該当があるときだけ。**Scope外と★設計未対応（無い文書に要求しない） |
| — | 前提環境 ＋ 初期データ | 観点F |
| 1 | カバレッジ表 | 観点B |
| 2 | シナリオ | 観点C・D・E・G |
| 3 | 判定の切り分けガイド | Fail の症状 → 疑う層 → 確認先 |
| 末尾 | 次のステップ | 全Passの意味 |

- **「手で実行する文書である」ことが冒頭に無いのは不足。**自動テストの仕様書と読み違えられる。
- **判定の切り分けガイドが無いのは不足。**Fail したとき、実施者が
  **要件・設計・実装のどこを疑うか**の道しるべが06の役目の半分。
  最後の行が**「上記が正しいのに動かない → 実装(Build)バグ」**で締まっているか。
- **行数やシナリオ本数は問わない。**「項目があるか」だけを見る。

### B. カバレッジ — 02の全機能が載っているか（最も漏れが出る）

**両方向で照合する。**片方向だけだと必ず抜ける。

**02 → 06（テスト漏れ）**

- 02の機能一覧の**機能IDが1つ残らず**、カバレッジ表の「機能(②)」欄に現れているか
- 現れない機能があるなら、**冒頭の注記に「なぜ対象外か」が書かれているか**
  （Scope 2 以降 / Out of Scope）。**無言で消えているのはテスト漏れそのもの**
- カバレッジ表の**「正常系」「異常系」の両方が、全行で埋まっているか。**
  **無言の空欄はテスト漏れ。**ただし **`（②に例外の定義なし）`** のように
  **根拠を示して空けてあるのは不足ではない**（02側の不足として報告されるべきもの）。
  **見分けるのは「なぜ無いかが書いてあるか」だけ。**
  なお、**02にも03にも例外の定義が無い機能に、異常系がでっち上げられていないか**も見る
  （02に無い期待結果は、実装が正しくてもFailする。観点Cの「過剰な要求」と同じ穴）
- **各機能の受入基準が「要約」欄に残っているか。**「〜できること」だけに削られて、
  **判定の観点が消えていないか**
- 02の**非機能要件に測れる基準がある**なら（処理時間・精度・件数）、
  それを確かめるシナリオがあるか。**無いなら（横断）の行として立てるべき**

**06 → 02（出どころ不明）**

- カバレッジ表・シナリオに出る**機能IDが、02に実在するか**（存在しないIDを参照していないか）
- **02のどこにも根拠が無いシナリオ**が紛れていないか。
  あるならそれは**新規要件**。02を直すのか（→ `requirement-doc-review`）
  06から落とすのかをユーザーに聞く

### C. Then が受入基準と対応しているか（最も漏れが出る）

**シナリオを1本ずつ指で追って**照合する。

- 各 Then の末尾に、**どこから来たかの注記**があるか
  （`（②の受入基準に対応）` `（③のエラー表示に対応）`）。**出どころ不明の Then が無いか**
- **02の各受入基準が、どれかの Then に落ちているか。**
  1機能に受入基準が複数あるとき、**1つだけ拾って残りが消えている**のが最も多い
- Then が**受入基準を言い換えただけで、判定できない**ものになっていないか
  （「正しく処理されること」「適切に表示されること」は判定できない）
- **受入基準に無いことを勝手に期待結果にしていないか**（過剰な要求。
  実装が正しくてもFailする）
- 複数画面をまたぐ受入基準（「送信した内容が管理者側の一覧に表示される」）が、
  **片側だけで終わっていないか**

### D. 異常系が網羅されているか（最も漏れが出る）

**異常系の種は02と03にしかない。**両方を舐めて照合する。

- **02の各機能の「例外・バリデーション」が、すべてどれかの異常系シナリオにあるか。**
  **ここが最大の穴**
- **03の各画面の「エラー・例外表示」が、すべてどれかの Then にあるか。**
  **表示文言まで一致しているか**（03が「内容を入力してください」なら、
  06も同じ文言。勝手に言い換えると実施者がFailと判定する）
- 05の3章の**エラー意味論**（未認証・権限なし・対象不在・状態不整合）に対応する異常系があるか。
  とくに**権限の境界**（他人のデータを触れないこと）を確かめるシナリオがあるか
- 異常系の見出し直下に、**どこから来たかの1行**があるか
- 異常系が**バリデーション（空欄送信）だけに偏っていないか。**
  02にある**業務的な例外**（重複・状態不整合・対象外データ・外部障害）が落ちていないか
- CLI・バッチなら、**失敗の局所化**（1件失敗しても他が止まらない）と
  **停止条件**（リトライ上限・タイムアウト）を確かめるシナリオがあるか

### E. 人が手で実行できるか（最も漏れが出る）

**「実施者がこの行を読んで、その場で手が止まらないか」**で見る。

- **When に具体値があるか。**「適切なキーワードを入力する」「不正な値を入力する」は不足。
  **実際に打つ文字列**まで書かれているか
- **Then が観測できる形か。**表示される**文言・件数・遷移先の画面ID**まで書かれているか。
  「正しく動作する」「エラーになる」は不足
- **画面から見えないものを確かめる手順**（DBの値・ログ・生成ファイル）があるなら、
  **その手段が前提環境の「検証補助」に書かれているか。**書かずに手順へ出ているのは不足
- **Given が「今どうなっているか」だけになっているか。**操作が混ざっていないか
- **1行に判定が2つ以上混ざっていないか**（「保存され、かつ一覧に反映される」は2行に割る）
- **判定欄が全行に `☐Pass / ☐Fail`** で入っているか。**空欄・欠けが無いか**
- **実施者メモ欄が空で置かれているか**（あらかじめ何か書かれていないか）
- **実施者が用意できない前提**を置いていないか（実データ・本番アカウント・
  外部システムの実接続・特定の時刻）。あるなら、それをどう用意するかが書かれているか

### F. 前提環境と初期データが足りているか（最も漏れが出る）

- 前提環境に、**対象 / 起動手順 / アクセス経路 / テストデータ / 初期状態**があるか。
  **空欄・「—」でごまかしていないか**
- **起動手順が、実施者がそのとおり打てる粒度か。**「アプリを起動する」だけは不足
- **Given が参照する値が、すべて初期データ表に実在するか。**
  **本文で初めて出てくるデータが無いか**（「登録済みのFAQ『駐輪場の利用方法は？』」が
  初期データに無い、など）。**ここが最も多い不足**
- **初期データ表が別立てされていないこと自体は不足ではない。**
  投入するのがDBのレコードではなく入力ファイル群の形態（CLI・バッチ）では、
  前提環境の「テストデータ」行に**どんな性質のファイルを何件置くか**が列挙されていれば足りる。
  **見るのは表の有無ではなく、「Given が参照するものがシナリオの外で先に確定しているか」**
- **アカウントのIDとパスワードが値のまま書かれているか**（実施者が打てないと意味がない）。
  逆に、**本物の秘密情報（APIキー・本番の資格情報）が平文で書かれていないか**
  （書かれていたら**削除の提案**として出す）
- **シナリオ間の依存が明示されているか。**前のTESTの結果を Given にするなら、
  **どのTESTで作られるか**が書かれているか。書かれていないと**単独で実行できない**
- **実行順に依存があるなら、そう書かれているか。**逆に、**依存が無いのに順番でしか
  通らない**作りになっていないか（初期データを消費するシナリオが先にある、など）
- 実装依存で変わりうる値（ポート番号・URLのパス構造）に、
  **「実際の値は起動環境に読み替える」**の断りがあるか

### G. トレーサビリティ欄が埋まっているか

- 全シナリオに **`対応機能(②)`** と **`種別`** があるか。**空欄が無いか**
- **`画面(③)` の SCR-ID が03に実在するか**（両方向。03の全画面がどこかのシナリオに出るか）
- **`対応フロー(⑤)` の FLOW-ID が05に実在するか**（05にフローがある場合のみ）
- `対応要求(①)` が、01の課題・ジャーニーを指しているか（01がある場合のみ）
- **見出しだけで何を確かめるか分かるか。**「機能テスト1」のような名前になっていないか
- `種別` が **正常系 / 異常系 / 正常系＋異常系** のいずれかで、
  **表の中身と一致しているか**（正常系と書いてあるのに全ステップが異常系、など）

### H. 章をまたいだ整合

- **カバレッジ表の全TEST-IDが、2章に実在するか**
- **2章の全TESTが、カバレッジ表のどこかに現れるか**（逆向き。**片方にしか無いものが
  最も見つかりにくい不足**）
- **TEST-IDが重複・欠番していないか**（欠番自体は不足ではないが、
  カバレッジ表からの参照が切れていたら不足）
- カバレッジ表の「正常系 / 異常系」の割り当てと、**本文の `種別` が一致するか**
- 冒頭の注記に書かれた★設計未対応が、**本文の該当ステップに実在するか**（逆向きも）
- 用語が上流と揃っているか（02・03の呼び名を勝手に言い換えていないか）

### I. ★設計未対応の扱い（消させない）

**★設計未対応が書いてあること自体は不足ではない**（原則9）。見るのは書き方。

- 該当ステップの Then に、**次の3つが全部書かれているか**
  1. なぜ確認できないか（③〜⑤のどこに対応が無いか）
  2. **「このステップは仕様上Failする想定」**であること
  3. **Failの原因が実装ではなく要件(②)と設計(③〜⑤)の不整合**であること
- **冒頭の注記にも1件として載っているか**（本文だけに埋もれていないか）
- **逆に、★設計未対応にすべきものが普通のシナリオになっていないか。**
  Then に書かれた画面・操作が**03に実在するか**を確かめる。
  **03に無い画面を発明して辻褄を合わせているのが最悪の形**（実装者がそれを作りに行く）
- **★設計未対応が多すぎて、その機能のシナリオが1本も成立していない**なら、
  それは06の不足ではなく**上流を直す段階**。そう報告する

### J. 実物（Build成果物）と食い違っていないか

**Build成果物がある場合だけ当てる。**無ければ飛ばし、飛ばしたことを伝える。

- **起動手順が実際に通るか**（`package.json` の `scripts`・`README`・
  CLIの引数定義と、前提環境の記述が一致するか）
- **初期データの投入先**（シード・マイグレーション・フィクスチャ）に、
  06が書いた値が実在するか
- **画面のパス・URLの形**が、ルーティングの実装と一致するか
- **文言**が実装と食い違っていないか。**ただし、文言の正は03**。
  実装と03がずれているなら、それは**実装か03の問題**であって06の不足ではない — そう報告する

**食い違いを見つけても、実装は直さない。**文書が古いのか実装が先走ったのかをユーザーに確認し、
**06側だけ**直す。**シナリオを実行して確かめない**（原則7）。

### K. 書いてはいけないものが混ざっていないか

- **自動テストコード**（`test(` / `describe(` / `it(` / `assert` / `expect(` /
  `pytest` / `flutter test`） → Buildフェーズ。**06は人が手で実行する文書**
- **単体テスト・結合テストの設計**（関数単位の入出力表・モックの定義） →
  単体は⑤、結合は③に対応する検証
- **実装コード・SQL・DDL** → Buildフェーズ・04の内容
- **画面構成・UI要素の定義・モック** → 03の内容（参照はよい、再定義は混入）
- **テーブル定義・API仕様の再掲** → 04・05の内容
- **Scope 2 以降・Out of Scope のシナリオ** → 冒頭の注記に回す
- **判定欄が埋まっている・実行結果が書き込まれている** → 06は空で渡す文書。
  実行記録を残したいなら**別ファイル**にする
- **テスト計画・工数見積り・体制** → 06の範囲外

見つかったら「不足」ではなく**削除の提案**として出す。消す判断もユーザーに仰ぐ。

> **短い例示（打ち込むコマンド1行、入力する文字列、確認するログの1行）まで削らせない。**
> 混入として扱うのは、**そのまま走らせれば判定が付いてしまうテストコード**が置かれている場合。

### L. 未確定が残っていないか

- **「未定」「未確認」「TBD」「要検討」「要確認」「適宜」「{}」が1つも無いか。**
  06は人が手で実行する文書で、ここが宙ぶらりんだと**実施者がその行で止まる。**
  残っていたら、そこを決めるところまでやって閉じる
  （**`★設計未対応` は確定した記述なので対象外。**混同して消さない）
- テンプレートの `{プレースホルダ}` が埋まらないまま残っていないか
- **`<!-- ASK: ... -->` のコメントが残っていないか**（`scenario-test-doc` が完了前の確認用に置く印。
  残っている＝聞かずに暫定案のまま出ている。**本文だけ読んでも見えないので必ずgrepする**）
- 「〜かもしれない」「必要に応じて」「環境によっては」で逃げている箇所が無いか。**決め切る**
  （**「実際の値は起動環境に読み替える」は逃げではない。**読み替え先が示されていれば足りる）

## 機械的に潰せるもの（目視の前に）

**ここで出た差分が、そのままB・C・G・H・L観点の指摘になる。**

| 確かめること | 見かた |
|---|---|
| 02の機能IDの拾い漏れ | 02から `FUNC-\d+` を全部拾い、06のカバレッジ表にあるものと差集合を取る |
| **受入基準の拾い漏れ**（観点C。機能ID単位では検出できない） | 02の各機能の受入基準を**文単位に割って番号を振り**（`FUNC-03-a` `FUNC-03-b`）、**1つずつ「これを判定している Then はどれか」を書き出す。**対応が付かない番号がそのまま指摘になる |
| 02の例外の拾い漏れ | 02の各機能の「例外・バリデーション」の箇条書きを1つずつ拾い、対応する異常系シナリオを書き出す。付かないものが指摘 |

## やらないこと

- **新規に書き起こす** → `scenario-test-doc`
- **シナリオを実行する・判定欄を埋める** → 実行するのは人間。**判定欄は空で渡す**
- **要件定義書（02）の点検・不足埋め** → `requirement-doc-review`。
  受入基準そのものを06側で足さない
- **仕様書（03）の点検・不足埋め** → `spec-doc-review`
- **データ構造設計書（04）の点検・不足埋め** → `db-doc-review`
- **API/IPO一覧（05）の点検・不足埋め** → `api-ipo-doc-review`
- **★設計未対応を消させる／こじつけのシナリオに書き換える** → 上流の不整合を隠すことになる
- **自動テストコード・E2Eスクリプトを書く／要求する** → Buildフェーズ
- **単体テスト・結合テストの設計を要求する** → 単体は⑤、結合は③に対応する検証
- **コードや既存の実装を直す。**観点Jで食い違いを見つけても、**直すのは文書だけ**
- **テスト設計の作り直し・好みによる作り替え。**不足を埋めるだけにとどめる
- **TEST-IDの振り直し** → 参照が全部ずれる。足すなら末尾に採番する

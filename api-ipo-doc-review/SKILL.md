# API・IPO一覧のレビュー（詳細設計）

対象は **`05-api-ipo.md` 1本**。**新規に書き直さない。**既にあるものに観点を当て、**不足だけを埋める。**

作成は `api-ipo-doc` スキルの仕事。まだ文書が無いならそちらへ回す。

**04（データ構造設計書）・03（仕様書）・02（要件定義書）は照合用に必ず読む。**
05は「03の画面操作と04のデータを、どのインターフェースが繋ぐか」を書いた文書なので、
上流を見ずに過不足は判定できない。とくに**04は必須**（読み書きの対象と制約が、
リクエスト・レスポンス・エラーの唯一の根拠になる）。
ただし**直すのは05だけ。**02側は `requirement-doc-review`、03側は `spec-doc-review`、
04側は `db-doc-review` へ回す。

**05は3つの形態がある。**どれなのかを最初に見極めてから観点を当てる
（章タイトルと点検内容が変わる）。

| 形態 | 見分け方 |
|---|---|
| HTTP API | API一覧（メソッド＋パス） / エンドポイント詳細 / HTTPステータスのエラー表 |
| BaaS直アクセス | インターフェース一覧に「データアクセス」「サーバレス関数」の種別 / 認可がセキュリティルール |
| CLI・バッチ | インターフェース一覧に「コマンド」「ツール」「外部API」の種別 / エラーが例外種別・停止条件 |

## 作成スキルから呼ばれたとき

`api-ipo-doc` の手順7は、**提出前にこのスキルを必ず1回通す。**
そのときは進め方を次のように変える。

- **手順1の対象特定は飛ばしてよい**（対象・形態・上流の場所は呼び出し側が知っている）。
- **観点を当てて、指摘の一覧を呼び出し側へ返すところまでが仕事。**
  そこで**ユーザーに承認を求めない**（承認は作成スキルの手順8で1回だけ取る）。
- **02〜04から一意に導ける不足は、そのまま直してよい**（原則3の範囲）。
  導けない不足は、**作成スキル側の「重大な確認事項」へ積み直す**（自分で聞きに行かない）。
- 返すもの: **当てた観点 / 見つかった不足 / 直した内容 / 判断が要るので積み直したもの**。

呼び出し側から独立して（ユーザーが直接このスキルを起動して）使うときは、以下の手順どおり進める。

## 大原則

1. **全部読んでから判断する。**一部だけ見て「足りている」と言わない。
   **02・03・04・05**を通しで読む（01は権限の境界を見るときだけ）。
2. **既存の実装があるなら、実物と照らす。**05は実装が直接参照する文書なので、
   **文書と現物がずれていること自体が最大の不足。**
   ルート定義・データアクセス層・セキュリティルール・CLIの引数定義を読み、
   05と食い違っていないか確かめる。**ただし直すのは文書側だけ。**
   実装を直すべきだと判断したら、そう報告してユーザーに委ねる。
3. **勝手に書き足さない。**不足を埋めるには判断が要る。
   ただし**02・03・04から一意に導ける記述**は、聞く前に案を書いて見せてよい
   （そのとき上流のどこから起こしたかを必ず示す）。
   導けないもの（認証方式・外部サービスの仕様・冪等性の方針・レート制限）は案を添えて聞く。
4. **決めるのは人間。**推奨案は出してよいが、承認なしに決定として書かない。
5. **指摘は場所と一緒に出す。**「`POST /api/inquiries` のエラー表に403が無い」のように、
   **どのインターフェースの・何が足りないかを名前で言う。**
6. **設計の好みでは指摘しない。**「自分ならこう切る」は不足ではない。
   指摘するのは、**02〜04の要求を満たせない**か、**実装者が判断に迷う**か、
   **現物と食い違う**場合だけ。
7. **06以降（テスト）とBuildの内容を要求しない。**
   テストケースが無いのは不足ではなく正しい状態。
   **動くコントローラ・SDK呼び出しの実装が無いのも正しい**（あったらむしろ混入。観点J）。
8. **型が書かれていないのは不足ではない。**型のSSOTは04またはスキーマ定義。
   **05に型が細かく書いてあるほうを疑う**（二重定義。観点G）。
   ただし**「型のSSOTがどこか」が書かれていないのは不足。**
9. **02〜04の内容を蒸し返さない。**機能の切り方・画面の切り方・テーブルの切り方への
   異議はこのレビューの範囲外。05が上流と食い違っているかだけを見る。

## 手順

### 1. 対象を特定する

`docs/requirements/05-api-ipo.md` など、設計書の場所を確認する。
複数あるなら、どれを見るのかユーザーに聞く。見つからなければ、
**まだ作成の段階なので `api-ipo-doc` を使うよう案内して終了する。**

あわせて次も特定する。

- **形態**（HTTP API / BaaS直アクセス / CLI・バッチ）。冒頭の前提と1章の種別から判定する。
  判定できないなら、それ自体が不足（観点A）。
- **対になる 04・03・02。**照合の土台なので、無ければ観点B・C・Dを当てられない。
  見つからない場合は、そのことを伝えたうえで、残りの観点だけで点検するか、
  先に上流を作るかを**ユーザーに選んでもらう**（欠けた側の観点を飛ばしたことは必ず伝える）。
- **既存実装**（観点I）。無ければその観点を飛ばす。

### 2. 全部読む

飛ばし読みしない。05を冒頭の前提から「次のステップ」まで通し、**02・03・04も通しで読む。**
03は画面ごとの操作・エラー表示まで、04は定義と制約まで読む。

### 3. 観点を当てる

下の「点検の観点」を全部当てる。
**B（02とのトレーサビリティ）・C（画面操作の対応）・D（04との整合）・
F（IPOの完備）・H（章をまたいだ整合）は漏れが最も出るので必ず見る。**

機械的に確かめられるものは、目視より先にコマンドで潰す（「機械的に潰せるもの」）。

### 4. 結果を提示する

- **不足がある場合** → 見つかった不足を**一覧でユーザーに提示してから**直しに入る（手順5へ）。
  一覧は**契約に波及するもの（インターフェースの追加・パラメータの増減・エラーの追加）と、
  記述の不足（意味・目的・対応欄の書き漏れ）を分けて**出す。
  **前者を先に直す**（後者は前者の結果で変わるため）。
- **不足がない場合** → 何も書き換えない。
  **「不足のない設計書が既にある」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのかも一緒に伝える（当てた観点と、その結果を示す）。

### 5. 不足を埋める

1件ずつ「（必要なら質問 →）ドラフト → 赤入れ → 確定 → ファイルへ書く」で進める。

- **02〜04から一意に導ける不足は、先に案を書いて見せる**（原則3）。
  「SCR-04の削除確認に対応するAPIが1章に無いので、`DELETE /api/{resources}/{id}` を足す案です」の形。
- 導けない事実（認証方式・外部サービスの制限・冪等性・レート制限・SLA）は**推測で埋めず聞く。**
  「まだ決まっていない」と言われたら、選択肢を2〜3案に絞り、推す案に `（推奨）` と
  理由を添えて聞き直す。それでも決まらないなら、持ち帰るか暫定で決めるかを
  **ユーザーに選んでもらう。**
- **インターフェースを増減させたら、波及を必ず追う。**0章の方針・1章の一覧・2章のIPO・
  3章の詳細 — **この4箇所がそろって直っているか**を毎回確認する。**ここが最も取りこぼす。**
- 一度に聞くのは2件まで。まとめて並べない。
- **直した箇所はその都度ファイルへ書く。**まとめて最後に書かない。

### 6. ユーザーの承認をもって完了とする

直した内容を報告し、承認を得て終わる。自分の判断で締めない。
（**作成スキルから呼ばれたときは、この手順を飛ばして呼び出し側へ返す。**）

- 何が足りず、どう直したかを短く一覧で見せる（契約の変更 / 記述の追加を分ける）
- 決着させた未確定事項があれば、何をどう決めたかも見せる
- **02・03・04側に見つけた不足があれば、直さずに報告する**（振り先のスキル名も添える）
- **既存実装と食い違っていた箇所は、文書と実装のどちらが正なのかを確認する**
- 「これで06（シナリオテスト）／実装へ進んでよいか」を確認する
- **`db-api-crossreview`（04 × 05 の横断レビュー）を勧める。**
  この点検は「05を直すために」04を読む片方向なので、**04側が古い・足りない**タイプの
  食い違いは拾い切れない。横断レビューは文書を書き換えず、
  **どちらを直すべきかを付けた指摘レポートだけ**を出す。
  **走らせるかはユーザーが決める**（勝手に起動しない）

## 点検の観点

### A. 章と項目が揃っているか

形態によって章タイトルが変わる。**中身の役割が揃っているか**を見る（名前の一致は問わない）。

| # | HTTP API | BaaS直アクセス | CLI・バッチ |
|---|---|---|---|
| 冒頭 | Vモデル上の位置（詳細設計 / 単体テスト）＋前提 | 同左＋**「API」が何を指すかの定義** | 同左＋**「API」が何を指すかの定義** |
| 0 | 認証・認可の詳細 | 認証・認可の詳細（アクセス制御の実体） | 認証の方針・外部APIのキー管理（1章冒頭に畳んでよい） |
| 1 | API一覧 | インターフェース一覧 | インターフェース一覧 |
| 2 | フローごとのIPO | 同左 | 同左 |
| 3 | エンドポイント詳細 | インターフェース詳細 | インターフェース詳細 |
| 末尾 | 範囲を切る一文 ＋ 次のステップ | 同左 | 同左 |

冒頭の前提に、次の3つが**書かれているか**。1つでも無ければ不足。

- **認証・認可の方針の在り処**（02のどこか。無ければここで決めた旨）
- **型のSSOTがどこか**（04 / スキーマ定義ファイル）
- **スコープ**（本書がどのFUNCまでを対象にするか）

- HTTP APIを持たない形態なのに、**「ここでのAPIが何を指すか」の定義が無い**のは不足。
- **行数や項目数は問わない。**「項目があるか」だけを見る。

### B. 要件（02）とのトレーサビリティ（最も漏れが出る）

**両方向で照合する。**片方向だけだと必ず抜ける。

**02 → 05（インターフェースの不足）**

- 02の機能一覧の**機能IDが1つ残らず**、1章のどこかの「機能(②)」欄に現れているか
- 現れない機能があるなら、**なぜインターフェースを持たないかが書かれているか**
  （画面内で完結する / 他機能に内包 / Out of Scope）。無言で消えているのは不足
- 02の各機能の**受入基準**が、この契約で満たせるか
  （「〜順に表示されること」に対応する並び順のパラメータ、
  「重複を登録できないこと」に対応するエラーがあるか）
- 02の各機能の**例外・バリデーション**が、**すべて3章のエラー表か2章の例外行にあるか**
  （観点Gと繋がる。**ここが最大の穴**）

**05 → 02（出どころ不明）**

- 1章の全行に機能IDがあるか（空欄が無いか）。そのIDが**02に実在するか**
- 02のどこにも根拠が無いインターフェースが紛れていないか。
  あるならそれは**新規要件**。02を直すのか（→ `requirement-doc-review`）
  05から落とすのかをユーザーに聞く
- **Out of Scope からインターフェースを起こしていないか。**
  Scope 2/3 のためのものなら、**`（Scope2）` の注記があるか**
- 冒頭で宣言したスコープと、実際に載っているインターフェースの範囲が一致しているか

### C. 仕様書（03）の画面操作に対応があるか（最も漏れが出る）

**画面を1つずつ指で追って**照合する。

- 画面の**操作（ボタン・送信・遷移・絞り込み・並べ替え・ページング）**が、
  すべてどれかのインターフェースに対応しているか。
  **「削除確認だけあってDELETEが無い」「検索欄はあるがクエリパラメータが無い」が起きやすい**
- 画面が**表示する項目**が、対応APIのレスポンス（成功）に**すべて含まれているか**。
  一覧に出す名前・件数・状態が、そのAPIの戻りから作れるか
- 画面の**入力フォームの必須／任意**が、リクエスト表の必須欄と**一致しているか**
- 画面の**エラー・例外表示**が、**すべてエラー表か例外行に対応を持つか。**
  逆に、画面に出しようのないエラーだけが並んでいないか
- 2章の各フローの「画面(③)」欄が埋まっているか。**03の全画面IDが、どこかのフローに現れるか**
- **画面の遷移とフローのステップ順が矛盾していないか**（03では確認画面を挟むのに、
  IPOでは1ステップで確定している、など）

### D. データ構造設計（04）との整合（最も漏れが出る）

- 2章・3章の「対応データ(④)」に出てくる**テーブル・コレクション・データストアが、
  04に実在するか**（名前まで一致するか）
- **04の全データストアが、どこかのフローで読み書きされているか。**
  誰も読まない・誰も書かない器があるなら、04が余分か、05に抜けがある
- **書き込み系インターフェースが、04のNOT NULL項目をすべて受け取れるか。**
  受け取らないなら、既定値・サーバ側生成のどちらかが書かれているか
- **04のUNIQUE制約に対応するエラー**（重複）が、エラー表にあるか
- **04の `ON DELETE` の挙動と、削除APIの説明が矛盾していないか**
  （04はRESTRICTなのに、05は「関連ごと消える」と書いている、など）
- 04の**列挙値（status等）**と、05のリクエスト・レスポンスで使う値が**一致しているか**
  （05側だけに知らない値が出ていないか）
- 03の一覧の**絞り込み・並び順**が、04のインデックス方針と**噛み合っているか**
  （05でクエリパラメータとして受けるのに、04にインデックスが無い → 04側の不足として報告）

### E. 1章（一覧）そのものが実装に足りるか

- **全行の「認証」欄が埋まっているか**（空欄・「-」でごまかしていないか）
- 要認証の行に、**必要権限が具体的に書かれているか**（「認証済み」だけで、
  誰の何を触れるかが読み取れないのは不足）。
  **認証と必要権限が1列にまとまっていること自体は不足ではない**
  （BaaS直アクセスでは `認証・認可` の1列に畳むほうが自然）。**中身が読み取れるかだけを見る**
- **CRUDの欠け。**03の画面が使う操作のうち、一覧・詳細・作成・更新・削除で
  **足りないものが無いか**（詳細画面があるのに単体取得APIが無い、など）
- **命名が全体で揃っているか。**パスの単複、階層の切り方、パラメータ名の表記
- HTTP APIなら、**メソッドの選択が操作と噛み合っているか**
  （取得がPOSTになっている、更新と作成が同じパス・同じメソッドで混ざっている）
- **外部サービスが1行として立っているか。**呼び出し元と、キーの管理方法が書かれているか
- **「対応フロー」欄があり、埋まっているか**（無いと1章と2章の照合が目視になる）

### F. 2章（IPO）が実際に機能しているか（最も漏れが出る）

**この章がこの文書の中心。**表の形だけあって中身が無い、が最も起きやすい。

- **Input / Process / Output の3列が、全行で実際に埋まっているか。**
  `-` や「同上」で流していないか
- **Process が「処理する」「登録する」で終わっていないか。**
  **どのデータをどう変えるか・どう絞り込むか**まで書かれているか
- **Output が、利用者から見て何が起きるかになっているか**
  （内部の戻り値だけで、画面に何が出るか分からないのは不足）
- **各フローに例外の行が1行以上あるか。****1つも例外行が無いフローは不足**
- **フローの切り方が「ユースケース」になっているか。**
  1画面1フロー・1API1フローに割れているなら、それは一覧の焼き直し
  （ただし**好みの問題として指摘しない。**02の正常フローと対応が取れていれば足りる）
- 各フローの見出し下に**「対応機能(②)」と「画面(③)」があるか**
- **「対応API」欄のインターフェースが1章に実在するか**（観点Hと繋がる）。
  **列名は形態により `対応インターフェース` / `対応データ(④)` / `対応テーブル(④)` と
  言い換えられている。名前の違いは指摘しない**が、**同じ文書の中で揺れているのは不足**
  （章をまたいだ照合がこの列で行われるため）
- 02の**正常フローと、IPOのステップ順が一致するか**。02にあるステップが飛んでいないか
- 繰り返し・並列処理があるなら、**そう明記されているか**（1件ずつなのか一括なのか）

### G. 3章（詳細）が契約として成立しているか

1章の**全インターフェース**について、次を見る。

- **3章に項目そのものがあるか**（1章にあって3章に無いのが最も多い不足）
- **リクエスト / レスポンス（成功） / エラー の3つが揃っているか。**1つでも欠けたら不足
- リクエストの**必須欄が全パラメータで埋まっているか。**
  パス・クエリ・ボディ・ヘッダーの**どこに載るか**が分かるか
- レスポンスの各フィールドに**意味が書かれているか**（名前だけの羅列は不足）。
  **0件・null になる条件**が書かれているか
- **エラーの網羅。**次が漏れていないか。
  - 入力不正（400）／未認証（401）／権限なし（403）／対象不在（404）／内部エラー（500）
  - **401と403を混ぜていないか**（未認証と権限なしは別物）
  - **404と403の使い分け**が意図的か（存在を隠すために404にするならその旨）
  - **02・03に固有の例外**（重複・状態不整合・外部サービス障害・レート超過）
- **エラーの「意味」が具体的か。**「不正なリクエスト」ではなく「本文が空」まで書けているか。
  **エラーコードの体系が全体で一貫しているか**
- **副作用のあるインターフェースに、冪等性の扱いが書かれているか**
  （再実行で二重に起きるか、防ぐならどう防ぐか）。
  **送信・課金・削除を伴うものに書かれていないのは不足**
- **型が書かれていないこと自体は不足ではない**（原則8）。
  ただし**「型・構造は〜を参照」の1行**があるか。**逆に型を細かく定義しているなら二重定義**
- HTTPを持たない形態なら、ステータスの代わりに**例外種別・停止条件**が書かれているか。
  **リトライの有無・回数・超過時の扱い**まであるか
- メタ情報（目的 / 認証 / 必要権限 / 対応データ(④) / 対応フロー）が埋まっているか

### H. 章をまたいだ整合（最も漏れが出る）

- **1章のインターフェース数と、3章の詳細の数が一致するか。**
  **どれか1つにしか出てこないものが最も見つかりにくい不足**
- **2章の「対応API」に出るものが、すべて1章に実在するか**（名前・パス・メソッドまで一致するか）
- **1章の「対応フロー」に書かれたFLOW-IDが、2章に実在するか**（逆向きも）
- 名前が章をまたいで揃っているか（1章は `/api/faqs`、3章は `/api/faq` になっていないか）
- **0章の認証方針と、1章の認証・必要権限の列が矛盾していないか**
  （0章で「管理者のみ」と書いたAPIが、1章では認証不要になっている）
- 冒頭で宣言した形態・スコープと、本文の中身が一致しているか
- 図（mermaid のシーケンス図・フローチャート）があるなら、**登場するインターフェースが
  1章に実在するか。**図が壊れていないか（矢印・participant の閉じ、
  ラベル内の `:` や `-` のクォート）

### I. 実物（既存実装）と食い違っていないか

**既存実装がある場合だけ当てる。**無ければ飛ばし、飛ばしたことを伝える。

- ルート定義（`routes/` / `*.controller.ts` / `app.py` / `openapi.yaml`）にあるパス・メソッドが、
  1章と**一致するか**（片方にしか無いものを両方向で洗う）
- BaaS直アクセスなら、**データアクセス層が実際に触っているパス**と3章の対象パスが一致するか。
  `firestore.rules` の条件と、0章・1章の認可の記述が一致するか
- CLIなら、**引数定義の実物**（`argparse` / `commander` / `cobra`）と3章のパラメータ表が一致するか
- **公開済み・配布済みのインターフェースを、文書が黙って変えていないか**
  （互換を切るなら、その旨と移行の段取りが書かれているか）
- 移行途中なら、**新旧2系統あることが05に書かれているか。**どちらが正か、いつ寄せるか

**食い違いを見つけても、実装は直さない**（原則2）。
文書が古いのか実装が先走ったのかをユーザーに確認し、**文書側だけ**直す。

### J. 書いてはいけないものが混ざっていないか

- **動くルーティング・コントローラ・SDK呼び出し・バリデーション実装のコード** → Buildフェーズ。
  **05に載せるのは一覧・IPO・入出力の意味・エラー意味論まで**
- **SQL・DDL・テーブル定義の再掲** → 04の内容（参照はよい、再定義は混入）
- **型・JSONスキーマの詳細な二重定義** → 04またはスキーマ定義がSSOT（原則8）
- **画面構成・UI要素・モック** → 03の内容
- **テストケース・テスト手順・テストデータ** → 06以降
- **インフラ・デプロイ・スケーリングの構成** → インフラ設計（07）
- **技術選定の比較検討**（フレームワーク・認証ライブラリの選び方） → 05の範囲外

見つかったら「不足」ではなく**削除の提案**として出す。消す判断もユーザーに仰ぐ。

> **短い例示（`Authorization: Bearer {token}` の書き方、パスの形）まで削らせない。**
> 混入として扱うのは、**そのままコピーすれば動いてしまう成果物**が置かれている場合。

### K. 非機能要件（02）が契約に反映されているか

- **秘密情報。**APIキー・トークンの管理方法が書かれているか。
  **レスポンスに秘密情報（パスワードハッシュ・内部ID・他人の個人情報）を返していないか**
- **認証の有効期限・失効**の扱いが0章にあるか。期限切れが401として定義されているか
- **個人情報を運ぶインターフェース**が、02のセキュリティ要件と噛み合っているか
- **02に性能要件がある**なら、一覧系に**ページネーション（上限つき）があるか**。
  上限なしで全件返す設計になっていないか
- **レート制限・同時実行**の扱いが必要な設計（外部API・課金・通知送信）で、
  何も書かれていないなら不足
- **監査・ログ**が02で要求されているなら、記録するインターフェースがあるか

### L. 未確定が残っていないか

- **「未定」「未確認」「TBD」「要検討」「{}」が1つも無いか。**
  05は実装が直接参照する文書で、ここが宙ぶらりんだと実装とテストが止まる。
  残っていたら、そこを決めるところまでやって閉じる
- テンプレートの `{プレースホルダ}` が埋まらないまま残っていないか
- **`<!-- ASK: ... -->` のコメントが残っていないか**（`api-ipo-doc` が完了前の確認用に置く印。
  残っている＝聞かずに暫定案のまま出ている。**本文だけ読んでも見えないので必ずgrepする**）
- 「〜かもしれない」「必要に応じて」「適宜」で逃げている箇所が無いか。**決め切る**

## 機械的に潰せるもの（目視の前に）

**ここで出た差分が、そのままB・C・D・H・L観点の指摘になる。**

| 確かめること | 見かた |
|---|---|
| 1章と3章の数が合うか | 1章の表の行数と、3章の小見出しの数を数えて突き合わせる |
| 2章のAPIが1章に実在するか | 2章の「対応API」（形態により「対応インターフェース」）列の値を列挙し、1章と**差集合を取る** |
| フローIDの整合 | 1章の「対応フロー」の `FLOW-\d+` と、2章の見出しの `FLOW-\d+` で差集合 |
| 02の機能IDの拾い漏れ | 02から `FUNC-\d+` を全部拾い、05の本文にあるものと差集合を取る |
| 存在しない機能IDの参照 | 逆向きの差集合（05にあって02に無いID） |
| 03の画面IDの拾い漏れ | 03から `SCR-\d+` を全部拾い、05の「画面(③)」欄と差集合を取る |
| 04のデータの拾い漏れ | 04の1章からテーブル・コレクション名を拾い、05の「対応データ(④)」と両方向で差集合 |
| エラー表の欠け | 3章の小見出しごとに `#### レスポンス（エラー）` 相当の見出しが在るか数える |
| 401/403の混同 | `401` を含む行に「権限」、`403` を含む行に「未認証」が混ざっていないか検索 |
| IPOの空欄 | 2章の表の行で、セルが `-` や空になっているものを探す |
| 例外行の欠け | 各 `### FLOW-` ブロック内に「例外」を含む行があるか |
| 未確定の残り | `未定` `TBD` `要検討` `要確認` `適宜` `{` `ASK:` を検索 |
| 実装・SQLの混入 | `CREATE TABLE` `@app.` `@Get(` `router.` `async function` `class ` を検索 |
| 実物との差 | ルート定義・`firestore.rules`・CLIの引数定義からパス／メソッドを拾い、1章と突き合わせる |

## やらないこと

- **新規に書き起こす** → `api-ipo-doc`
- **要件定義書（02）の点検・不足埋め** → `requirement-doc-review`
- **仕様書（03）の点検・不足埋め** → `spec-doc-review`
- **データ構造設計書（04）の点検・不足埋め** → `db-doc-review`。
  04側の不足はここでは直さず、そちらへ回す
- **06以降の内容（テストケース）を要求する**
- **動く実装コード・DDLを書く／要求する** → Buildフェーズ
- **コードや既存の実装を直す。**観点Iで食い違いを見つけても、**直すのは文書だけ**
- **設計の作り直し・好みによる作り替え。**不足を埋めるだけにとどめる
- **技術選定・インフラ構成の見直し** → 07の範囲

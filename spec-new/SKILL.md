# spec-new（変更ごとの spec を作る）

変更1件ぶんの spec を作る。対象：$ARGUMENTS

**要求は聞き、要件は書いてから見せる。** 要求（なぜ・誰のため）はユーザーの頭の中にしかないので質問で埋め、要件と受入基準は vision・常設要件・コードから起こせるので Claude が先に書き切る。
**コードは書かない。**

- 要件と受入基準の書き方・ID・決め方・質問の作法・レビュー指摘の扱いの正典：`${CLAUDE_SKILL_DIR}/../product-requirements/rules.md`（必ず全文を読んでから始める）
- 雛形：`${CLAUDE_SKILL_DIR}/template-spec.md`、L ティアの設計 `${CLAUDE_SKILL_DIR}/template-design.md`。見出し・表・ID の書式は `spec-check` が読むので変えない。

## 手順

### 1. 読む

`CLAUDE.md`（開発ワークフロー節）、`docs/product/vision.md`、`docs/product/requirements/` の README と関係しそうな領域、`glossary.md`、`architecture.md`、進行中の spec（`docs/specs/*/spec.md` のうち status が draft / approved のもの）を読む。
`docs/` が無ければ `/spec-setup` を案内して止める。

### 2. ティアを決める

理由を添えてティアを提案し、ユーザーに確かめる。

| ティア | 目安 | この後 |
|---|---|---|
| S | バグ修正、文言変更、小さな UI 調整 | **ファイルは作らない。** 要件と受入基準を数行（常設 ID を使う）で会話に出して終わる。振る舞いが変わるなら、実装後に `/product-requirements update` を使うよう添える |
| M | 通常の機能追加 | spec.md を作る |
| L | 新規プロジェクト、アーキテクチャに影響する変更 | spec.md と design.md を作る。vision.md が無ければ `/product-vision` を案内して**止める** |

M で vision.md が無ければ作成を勧める。進めるかはユーザーが決める。

### 3. 書き始める前の点検

- **L ティア**：`spec-check` を呼ぶ（Skill ツールで `spec-check`、引数 `all`。**タイミング③**）。未解決の矛盾・欠落があれば一覧で見せ、先に直すか、承知のうえで進めるかをユーザーに決めてもらう。承知で進めるなら `docs/review-notes.md` に書く。
- **進行中の spec が多いとき**：進行中（draft / approved）の spec が、CLAUDE.md の「全体レビューを勧める進行中 spec の件数」（既定2件）以上なら、`docs-review all` の実行を勧める（**タイミング⑨**。実行はユーザーが決める）。

### 4. spec のファイルを作る

- `docs/specs/` を見て次の連番（3桁ゼロ埋め）を決める。名前は英小文字のケバブケースで、ユーザーに確かめる。
- 雛形から `docs/specs/NNN-<name>/spec.md` を作る（`status: draft`、`tier:`、`created:` を埋める）。L なら `design.md` も作る。
- 以降、**合意した部分はその都度このファイルに書く。**

### 5. 1. 要求（Why）を質問で埋める

なぜこの変更をするのか・誰のためか・何をもって成功とするかを聞く（rules.md 第11章の作法。一度に2件まで。理解を先に置いてから聞く）。

- vision.md の `G-n` / `P-n` / `J-n` のどれに効くかを特定し、「関連する要求」に書く。
- **対応するものが vision に無ければ `/product-vision update` を勧める。** 勝手に vision を書き換えない。vision を直すまで進めないか、先に spec を書き進めるかはユーザーが決める（後者なら「未決事項」に残す）。
- vision の**非目標**に当たりそうなら、その場で指摘して方向を確かめる。

### 6. 2. 要件（What）を書き切ってから見せる

vision・既存の常設要件・コードから起こし、rules.md に従って書く。**空欄・`{}`・TBD を残したまま見せない**（決め切れないものは手順8の未決事項へ）。

1. **対象の要件の表を先に閉じる。**
   - 新しく作る要件は「新規」。番号は rules.md 第2章のとおり予約する（その領域の常設要件と、進行中の spec の「対象の要件」表で「新規」になっている番号の最大値＋1）。
   - 既存の常設要件の振る舞いを変えるなら「変更」、無くすなら「廃止」。**既存要件とぶつかるのに「新規」にしない。** 同じ振る舞いを定めた常設要件が無いかを必ず探す。
   - 新しい領域が要るなら「新しい領域」節に書く。
   - この表だけを見せ、切り方と抜け漏れを見てもらう。ここで要件が増減すると後が連鎖するので先に閉じる。
2. **新規・変更の要件ごとに「変更後の姿」を5項目で書く**（rules.md 第4〜6章）。
   - 変更は、常設要件の該当ブロックを写してから直す。変わった項目の見出しに「（変更）」を付け、「変更前との差」を1行添える。**既存の AC は同じ番号のまま書き換え、足す AC は次の番号、無くす AC は「（廃止）」と残す**（黙って消さない）。
   - 例外の3方向と、境界値・権限・同時操作・繰り返しを必ず検討する。「止める」ものは AC にする。
   - 非機能要件があれば表に書く（全体共通なら `COMMON-N-nnn`）。
3. 廃止する要件、スコープ外（区分：後回し / やらない、理由付き）を書く。
4. **見せ方**：まとまりで提示して赤入れを受ける。**Claude が自分で決めた箇所と、根拠の弱い行を自己申告する**（「AC-3 の締切時刻はコードに定数が無く推測」など）。赤入れはその場でファイルに反映してから次へ進む。
5. L ティアでは、今回のスコープだけで vision のジャーニーが1周するかを確かめ、`J-n` ごとに対応する要件 ID を書く。

### 7. 3. 変更差分（DB・API・画面）を書く

現在のスキーマ・API・画面のコードを読んだうえで、**差分だけ**書く（コードが正）。要件の節には書かない。
L ティアなら、全体構成・データモデル・代替案・リスク・移行計画を design.md に書く。

### 8. 4. 未決事項を決着させる

推測で埋めた箇所・決め切れなかった箇所は「4. 未決事項」に `- [ ]` で書き、ユーザーと決着させる（rules.md 第11章の「決まらないとき」）。決まったら `[x]` にして本文へ反映する。

### 9. 点検する（タイミング④）

1. `spec-check` を呼ぶ（Skill ツールで `spec-check`、引数 `spec NNN`）。ID の予約の重なり・参照・節の揃い・AC が黙って消えていないか、が機械的に分かる。未解決の矛盾・欠落を先に直す。
2. `spec-review` を呼ぶ（Skill ツールで `spec-review`、引数 `NNN ④`）。fork したサブエージェントが、spec 単体・vision（非目標を含む）・常設要件・他の spec・設計方針・コードとの矛盾を見て、レポートを返す。
3. rules.md 第12章の「直し方」で進める。
   - レポートを一覧で見せてから直しに入る。矛盾はどちらを正とするかをユーザーに選んでもらう。
   - 1件ずつ直し、その都度ファイルに書く。一度に聞くのは2件まで。
   - ユーザーが「誤検知」「承知で進める」と判断した指摘は、理由を聞いて `docs/review-notes.md` に書く。
   - 直したら影響した範囲だけ `spec-check spec NNN` と `spec-review NNN ④` をもう一度通す。**未解決の矛盾・欠落が0件になるまで繰り返す。**
   - ユーザーが「今回は飛ばす」と明示したときだけ省いてよい。その場合は `docs/review-notes.md` に「飛ばした」と書き、`review:` 欄にも「飛ばした」と書く。
4. spec の `review:` 欄に最後の判定と日付を書く（例：`2026-10-02 合格（R-3 誤検知）`）。

### 10. 承認を取る

**未解決の矛盾・欠落が0件で、未決事項が空**になったら：

- Claude が決めて書いた箇所のうち、そのまま残ったものを一覧で見せる（赤入れが無かったこと＝承認ではない）。
- ユーザーが承認したら `status: approved` にし、`approved:` に日時（`YYYY-MM-DD HH:MM`）を書く。
- 次の一手（`/spec-plan NNN`）を案内する。

**未解決の矛盾・欠落が残る spec、未決事項が残る spec は approved にしない。**

## やらないこと

- コードを書く・テストを書く → 実装（`/spec-plan` の後）
- vision を直す → `/product-vision update` を勧めるだけ
- 常設要件を直す → `/spec-close` で移す（spec の中に「変更後の姿」を書くだけ）
- 変更に関係しない既存要件の書き写し
- 旧フローの仕様書（`03-spec.md`）の作成 → `spec-doc`

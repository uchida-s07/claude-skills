# 要件定義書 × 仕様書 の横断レビュー

対象は**要件定義書（`02-requirement.md`）と仕様書（`03-spec.md`）＋画面モック
（`mocks/mockup.html`）の2文書1組**。見るのは**2つの間の対応関係だけ**で、
それぞれの文書の中身の完備性は見ない（それは単体レビュースキルの仕事）。

**このスキルは文書を1文字も書き換えない。**出すのは**指摘レポート**だけ。
直すのは `requirement-doc-review` / `spec-doc-review` へ渡す。

単体レビューとの違いはここ。

| スキル | 見るもの | 直すもの |
|---|---|---|
| `requirement-doc-review` | 02の内部の完備性（＋01との照合） | 02 |
| `spec-doc-review` | 03とモックの内部の完備性（＋02との照合） | 03・モック |
| **このスキル** | **02と03の間の対応関係だけを、対等に両側から** | **直さない（レポートのみ）** |

単体レビューは「自分の文書を直すために」相手を読む。だから相手側の非を見つけても
振るだけで終わる。**横断レビューは、どちらが誤りかの判定そのものを成果物にする。**

## 大原則

1. **書き換えない。**不足を見つけても直さない。レポートを出して振り先を示すところまで。
   ユーザーから「ついでに直して」と言われたら、**該当のレビュースキルへ切り替える**
   （このスキルの中で直さない）。
2. **全部読んでから判断する。**02の全文・03の全文・モックのHTML。
   一部だけ見て「噛み合っている」と言わない。
3. **両側から見る。**02→03（拾い漏れ）と 03→02（出どころ不明）は別の見落としを生む。
   片方向だけでは必ず抜ける。
4. **どちらを直すべきかまで書く。**「食い違っている」で止めない。
   02が古いのか、03が先走ったのかを判定して、**根拠と一緒に**出す。
   判定できないときは「どちらの可能性もある」と明記し、判断材料を並べる。
5. **指摘は必ず場所と一緒に。**「FUNC-03の例外『対象が0件』が、どの画面の
   エラー・例外表示にも無い」のように、**機能IDと画面IDで言う。**
   IDで指せない指摘は、指摘として弱い。
6. **単体文書の内部の話に踏み込まない。**02の章が欠けている・非機能要件が空欄・
   モックの見た目 — これらは横断の指摘ではない。
   **ただし、それが原因で照合できないときは「照合不能」として出す**（観点J）。
7. **01（要求定義）と04（DB設計）は対象外。**02・03のどちらにも根拠が無い話は、
   このレビューでは扱わない。必要なら `request-doc-review` へ回す。
8. **見た目の良し悪しは判定しない。**モックを見るのは、02由来の要素・例外・文言が
   落ちているかの確認まで。**スクリーンショットを撮るコマンドを自分で実行しない。**

## 手順

### 1. 対象を特定する

`docs/requirements/02-requirement.md` と `docs/requirements/03-spec.md` の場所を確認する。
複数あるなら、どの組を見るのかユーザーに聞く。

- **02が無い** → まだ作成の段階。`requirement-doc` を案内して終了する
- **03が無い** → 突き合わせる相手がいない。`spec-doc` を案内して終了する
- **モックが無い** → 観点Hを飛ばす。**飛ばしたことをレポートの冒頭に書く**

### 2. 全部読む

飛ばし読みしない。02の4章、03の3章、モックのHTML（`<section>` のID・UI要素・
エラー文言）を最後まで通す。

### 3. 対応マトリクスを組む（最初にこれをやる）

**すべての指摘の土台になる。**目視の前に、機械的に拾えるものを潰す。

| 拾うもの | 見かた |
|---|---|
| 02の機能ID | 1章の機能一覧の表から `FUNC-xx` を列挙 |
| 03に現れる機能ID | 1章の「対応機能」欄・2章のUI要素/操作/例外の各表から `FUNC-xx` を列挙 |
| 差集合（02にあって03に無い） | **画面を持たない機能。**理由の記述が無ければ指摘（観点A） |
| 差集合（03にあって02に無い） | **実在しない機能IDへの参照。**ほぼ確実に指摘（観点A） |
| 03の画面ID | 1章の画面一覧から `SCR-xx` を列挙。**これは指摘の対象ではなく、機能IDを画面に結びつけるための地図** |
| モックの `<section>` のID | 観点Hで中身を見るときに、どの画面を開くかの当たりを付けるためだけに拾う |

> **03本文とモックの画面IDの差集合は取らない。**それは `spec-doc-review` 観点Eの仕事で、
> 単体文書の内部の点検にあたる（大原則6）。ここで拾うのは**02と結びつく側だけ。**

コマンドで潰すなら次の形。**出た差分をそのまま観点Aの指摘にする。**

```bash
comm -23 <(grep -o "FUNC-[0-9]\+" 02-requirement.md | sort -u) \
         <(grep -o "FUNC-[0-9]\+" 03-spec.md      | sort -u)   # 02のみ＝画面が無い機能
comm -13 <(grep -o "FUNC-[0-9]\+" 02-requirement.md | sort -u) \
         <(grep -o "FUNC-[0-9]\+" 03-spec.md      | sort -u)   # 03のみ＝出どころ不明の参照
```

**中間ファイルを作業ディレクトリに残さない。**プロセス置換で済ませる。
どうしても一時ファイルが要るなら、リポジトリの外（スクラッチ領域）に置く。

**ID表記のゆれ（`FUNC-1` / `func-01`）で差分が出ることがある。**
差集合を取ったら、ゆれによる偽の差分でないかを一度目で確かめる。

組み上がったマトリクス（機能ID × 画面ID）は、レポートの冒頭に**そのまま載せる。**
横断レビューで最も価値のある1枚がこれ。

### 4. 観点を当てる

下の「点検の観点」を全部当てる。
**A（ID対応）・C（例外の落ち込み）・D（受入基準）は漏れが最も出るので必ず見る。**

**当てる前に、直前に `spec-doc-review` が走っていないか確認する。**
`spec-doc` の手順8から続けて呼ばれた場合がこれにあたる（最も多い入り方）。
走っていたなら、**観点A・C・Eの03側は既に潰れた後**なので、同じ指摘を出し直さない。

- 03側で解消済みのものは**省く**
- **02側に残る分だけを出す。**例: `spec-doc-review` が03へ足した例外（0件・空状態）は、
  「02へ戻す指摘」としてだけ出す。03の不足としては出さない
- 走ったかどうかが分からなければ**ユーザーに聞く**（これは事実確認）

### 5. レポートを出す

「レポートの形式」に沿って出す。**文書は触らない。**

- **食い違いがある場合** → 重大度順に並べたレポートを出す。振り先も一緒に
- **食い違いがない場合** → **「02と03は噛み合っている」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのか（当てた観点と、対応マトリクスの結果）も一緒に出す

レポートを**ファイルに残すかはユーザーに聞く。**既定は会話へ出すだけ。
残すなら `docs/requirements/` ではなく、作業メモの置き場（`_notes/` など）へ置く
（**要求・要件・仕様の連番文書に割り込ませない**）。

### 6. 振り先を示して終わる

指摘ごとの振り先をまとめて示し、次に何をするかをユーザーに選んでもらう。

| 直す対象 | 振り先スキル |
|---|---|
| 02（要件定義書） | `requirement-doc-review` |
| 03・モック | `spec-doc-review` |
| 01まで遡る必要がある | `request-doc-review` |

**このスキルの中で直し始めない。**ユーザーが直すと言ったら、該当スキルへ切り替える。
両方に手が入る場合は、**02を先に確定させてから03**（上流が正）。

## 点検の観点

### A. 機能IDと画面IDの対応（最も漏れが出る）

**02 → 03（拾い漏れ）**

- 02の機能一覧の**機能IDが1つ残らず**、03のどこかの「対応機能」欄に現れているか
- 現れない機能に、**なぜ画面を持たないかの記述があるか**
  （定時バッチ / 他機能に内包 / Out of Scope）。無言で消えているなら指摘
- 逆に、1つの機能が画面に**分散しすぎていないか。**02では1機能なのに03で5画面に
  割れているなら、02の機能の粒度が粗いか、03が画面を割りすぎている

**03 → 02（出どころ不明）**

- 03の画面一覧・UI要素・操作・例外の**全行に対応機能IDがあるか**（空欄が無いか）
- そこに書かれたIDが**02に実在するか**（`FUNC-09` とあるのに02は08までで終わっている）
- 02のどこにも根拠が無い画面・UI要素・操作が無いか。
  あるならそれは**新規要件。**02へ足すのか03から落とすのかの判断が要る

### B. 正常フローと画面遷移の一致

- 02の各機能の**正常フローの各ステップ**が、03の操作表と遷移図で追えるか。
  ステップが3つあるのに画面上の操作が1つしか無い、が起きやすい
- **フローの順番が食い違っていないか。**02が「確認 → 実行」なのに
  03が「実行 → 結果表示」（確認画面が無い）など
- 02の**事前条件**を満たす手段が動線上にあるか。
  「ログイン済みであること」が事前条件なのに、認証画面もログイン導線も03に無い、が典型
- 02のフローで**保存・確定にあたる工程**が、03の操作表に挙動として書かれているか

### C. 02の例外が画面に落ちているか（最も漏れが出る）

- 02の各機能の「例外・バリデーション」を**1行ずつ指で追い**、
  対応する行が03のどこかの「エラー・例外表示」にあるかを照合する。
  **1行も飛ばさない。**ここが横断レビューの本体
- **止めるのか、飛ばして続けるのかが02と03で一致しているか。**
  02が「該当行をスキップして続行」なのに03が「処理を中断してエラー画面へ」なら、
  実装がどちらに従うか決まらない。**これは致命の指摘**
- 03にあって02に無い例外（0件・空状態・権限なし）が、妥当な補完か02の抜けか。
  **画面を作って初めて気づく例外は正常な発見。**02へ戻すべき指摘として出す
- 02の例外の**トリガー条件**と03の「トリガー」欄が同じことを指しているか。
  言葉が違うだけか、条件そのものが違うのかを見分ける

### D. 受入基準が画面で検証できるか（最も漏れが出る）

- 02の各受入基準（「〜すると、〜であること」）について、
  **入力側の「〜すると」が03のどの操作にあたるか**が特定できるか
- **期待結果の「〜であること」が、03のどの画面のどの表示で確認できるか。**
  どこにも表示されない結果を「〜であること」と書いていたら、
  02が画面を持たない検証を求めているか、03に表示が足りない
- 画面上では確かめられない受入基準（バッチの実行結果・ログ・保存先の中身）が、
  **そうと分かる形で02に書かれているか**
- 受入基準が「正しく動作すること」の類で、**03と照合できる形になっていないもの**は
  照合不能として出す（→ `requirement-doc-review`）

### E. スコープの一致

- 02で **Scope 2 / Scope 3 / Out of Scope** の機能から、03が画面を起こしていないか
  （**先食い**）。起こしているなら `（Scope2）` の注記があるか
- **Scope 1 の機能が全部画面になっているか。**初版が画面として成立するか
- **Scope 1 だけで動線が1周するか。**途中の画面がScope 2 で、初版だと行き止まりになる
  経路が無いか。**これは02単体でも03単体でも見えない、横断でしか出ない指摘**
- モックにScope外の画面・要素が紛れていないか

### F. 非機能要件の画面への反映

02の4章は、そのままでは画面に現れないので取りこぼしやすい。

- **セキュリティ（認証・認可）** → ログイン画面・権限による表示の出し分け・
  未認証時の挙動が03にあるか。「権限モデル」があるのに画面が1種類しかない、が典型
- **性能**（処理に時間がかかる） → ローディング・進捗・タイムアウト時の表示が03にあるか
- **ユーザビリティ**（想定利用者のスキル水準） → 画面の情報量・専門用語と噛み合っているか
- **可用性**（止まったときどうなるか） → 障害時・オフライン時の画面が要るなら03にあるか

**該当なしなら不足ではない。**03に無いことが02の記述と矛盾する場合だけ指摘する。

### G. 用語・名称のゆれ

- 02の**機能名**と、03の画面一覧の「対応機能」欄・見出しで、呼び名が揃っているか
- 02が挙げた**データ項目名**と、03のUI要素名・モックのラベルが対応しているか。
  同じものが違う名前で呼ばれていないか、違うものが同じ名前になっていないか
- ユーザーの**役割名**（管理者 / 一般ユーザー）が2文書で一致しているか

**軽微に見えて実装で効く。**名前がずれたまま04（DB設計）へ進むと、
項目名がもう1回ずれる。

### H. モックと02の突き合わせ

（モックが無ければこの観点は飛ばし、飛ばしたことをレポートに書く）

- 02の例外の**表示文言**が、モックのエラー表示に出ているか
- 02が扱うと書いたデータ項目が、モックの画面に現れているか
- モックにだけあるUI要素で、**02にも03本文にも根拠が無いもの**が無いか
- モックのダミーデータが、02の想定（件数・桁・単位）と矛盾していないか
  （02が「最大1000件」なのにモックが3件固定で、その先の表示が読めない、など）

> モックの構造の点検（`screenIds` 配列・外部依存・ロジック混入）は
> `spec-doc-review` の範囲。**ここでは02由来の中身が落ちているかだけを見る。**

### I. 片方だけ更新された痕跡（横断特有）

**どちらが新しいかを判定する。**これは横断レビューにしかできない。

- 02の機能IDに**欠番や末尾の追加**があり、03がそれに追随していないか
- 03が**02に無い古い機能名**を使っていないか（02でリネームされた痕跡）
- 02の例外や受入基準が増えているのに、03の該当画面だけ手が入っていない
- モックだけが新しく、03本文と02の両方から浮いている

判定材料: 機能IDの連番の並び、ファイルの更新時刻、gitのログ
（`git log -1 --format=%ci -- <path>`）。
**更新時刻だけで断定しない。**内容の整合と合わせて判断する。

### J. 照合そのものができない箇所

観点を当てようとして**突き合わせる材料が無かった**ものは、
「食い違い」ではなく**照合不能**として別枠で出す。原因の文書と振り先を書く。

- 02の受入基準が空 / 「正しく動作すること」だけ → 観点Dが当てられない
- 02の例外・バリデーションが空 → 観点Cが当てられない
- 03の対応機能欄が空欄だらけ → 観点Aが当てられない
- 02・03に「未定」「TBD」「要検討」が残っている → その項目は照合できない

**照合不能を「問題なし」に混ぜない。**見ていないものを見たことにしない。

## どちらを直すべきかの判定

大原則4で判定そのものを成果物にすると決めている以上、**「直す先」列を空にしない。**
下を出発点にする。

| 食い違いの型 | 直す先 | 根拠 |
|---|---|---|
| 02にあって03に無い（機能・例外・受入基準） | **03** | 上流が正。02が求めたものが画面に落ちていない |
| 03にあって02に無い例外（0件・空状態・権限なし・必須未入力） | **02** | **画面を作って初めて気づく例外は正常な発見。**02の抜け |
| 03にあって02に無い画面・UI要素・操作 | **02 or 03** | 新規要件。要るなら02へ足す、要らないなら03から落とす。**ユーザー判断** |
| 挙動が正面から矛盾（止める / 飛ばして続ける） | **02** | 運用の判断であって画面の判断ではない。02で決めて03を従わせる |
| スコープの先食い（Out of Scope から画面） | **03** | 02のスコープが正 |
| 用語・名称のゆれ | **02** | 名前の正典は上流。03とモックを揃えにいく |
| 02が古い痕跡（観点I） | **02** | 03のほうが新しい実態を映している |

**「上流が正」を機械的に当てない。**この表の2行目と最終行が示すとおり、
**03のほうが正しい場面は普通にある。**画面に落として初めて分かったこと
（例外・空状態・動線の無理）は、02を直す根拠になる。

判定に迷ったら `02 or 03` と書き、**どちらに倒すと何が起きるかを1行ずつ**添える。
「決められなかった」で流さない。

## レポートの形式

### 冒頭

- 突き合わせた**ファイルのパス**（02・03・モック）と、モックが無いなら飛ばした観点
- **対応マトリクス**（機能ID × 画面ID）。手順3で組んだものをそのまま
- 当てた観点と、**照合不能だった観点**

### 指摘一覧

**重大度の高い順**に並べる。

| 重大度 | 意味 |
|---|---|
| **致命** | 実装が始められない / どちらに従うか決まらない（02と03が正面から矛盾） |
| **重要** | 実装は進むが、後で手戻りになる（拾い漏れ・出どころ不明・スコープの先食い） |
| **軽微** | 意味は通るが読み違えを誘う（用語のゆれ・注記の不足） |

```
| # | 重大度 | 観点 | 02側 | 03側 | 何が噛み合っていないか | 直す先 |
|---|-------|------|------|------|---------------------|-------|
| 1 | 致命 | C | FUNC-03 例外3 | SCR-05 例外表 | 02は「スキップして続行」、03は「中断してSCR-09へ」。実装がどちらに従うか決まらない | 02（運用判断が要る） |
| 2 | 重要 | A | FUNC-07 | — | どの画面の対応機能欄にも無い。バッチか内包かの記述も無い | 03（画面が要るなら追加、不要なら理由を明記） |
```

**「直す先」は必ず埋める**（判定は「どちらを直すべきかの判定」に従う）。
判定できないものは `02 or 03（判断材料: …）` と書く。

### 照合不能の一覧

指摘一覧とは**分けて出す。**何が足りなくて照合できなかったか、振り先はどこか。

### 締め

- 指摘の件数を重大度別に
- **次にどのスキルを、どの順で走らせるべきか**（02が先、03が後）

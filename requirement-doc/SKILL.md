# 要件定義書づくり

Vモデルの **要件定義**（対応する検証はシステムテスト）にあたる文書を1本作る。
成果物の骨組みは同ディレクトリの `template.md`。**章立てと表の列を見るための参考**であって、
埋め方の指示書ではない。分量はそこに合わせにいかなくてよい。

書き上げた文書の点検は `requirement-doc-review` スキルが担う。**このスキルは作成に専念する。**

**前提条件**: **要求定義書（01）が存在すること。**無い状態でこのスキルを始めない。
**使う場面**: 要求定義（01）が固まり、実装に入る前。作る範囲と受入基準を確定させるとき。
**やり方**: 要求定義書を**正典として読み込み**、**1〜2章（機能一覧・各機能の要件）は
Claudeが一気に書き切ってから**ユーザーと一緒に見て直す。
3〜4章（スコープ・非機能要件）は質問して決める。
どの章でも、01の課題・ゴール・ジャーニーが1つ残らず機能に落ちているかを追い続ける。

要求定義（01）が「誰の・どんな課題を・なぜ解決するか」なら、要件定義（02）は
**「そのために何を作るか」**。作り方（どう作るか）は仕様書（03）以降の仕事。

## 大原則

1. **入力は要求定義書。無ければ着手しない。** 全文読んでから始める。
   見当たらなければ探し、それでも無ければ**この文書を書き始めず** `request-doc` スキルで
   要求定義から作るよう案内する。**課題が言語化されていない状態で機能一覧を書き始めない。**
   01に不足があるだけなら、02の中で補わず **`request-doc-review` で01を直してから**戻ってくる。
2. **1〜2章は聞く前に書く。** 01が読める以上、機能一覧と各機能の要件は
   **Claudeが最後まで書き切れる**。空欄を質問で埋めさせるのではなく、
   完成形をファイルに置いてから見てもらう。人間の時間は
   **ゼロから答えることではなく、書かれたものを直すことに使ってもらう。**
   ただし**書いた以上は根拠を示す** — どこを01から起こし、どこを自分で決めたかを添える。
3. **書いたものは提案であって決定ではない。決めるのは人間。**
   1〜2章を先に書くのは、判断材料を目に見える形にするため。
   **ユーザーが「それでいく」と言うまで確定にしない。**
   業務側の事実（誰が運用するか・どの規模でやるか・現行の運用）は案を書かず、聞く。
   ここを埋めた文章を既成事実にしない。
4. **トレーサビリティを切らさない。** 機能一覧の各行に「対応する要求」を必ず書く。
   逆向きにも照合する — 01の課題一覧・ゴール・ジャーニーの各ステップが、
   **すべてどこかの機能IDかOut of Scopeで拾われている**こと。
   どちらにも出てこない項目を残さない。
5. **「何を作るか」まで。「どう作るか」は書かない。** 画面構成・モック・テーブル定義・
   エンドポイント・クラス設計・状態遷移図は03以降。
   技術方針は「前提」として数行だけ（言語・使うSDK・入出力の形式・処理の順番）にとどめる。
6. **受入基準は検証可能に書く。** システムテストで○×が付く文にする。
   「使いやすいこと」「正しく動くこと」は基準ではない。
   *「〜を入力して実行すると、〜が出力されること」*の形まで具体化する。
7. **スコープはユーザーに決めさせる。** 何がMVPかは作る側の判断。
   決めたら **Scope 1 だけで01のユーザージャーニーが1周するか**を確認する。
   1周しないなら、Scope 1 に足りない機能があるか、ジャーニーの想定が過剰かのどちらか。
8. **「未定」「未確認」「TBD」を本文に残さない。** 非機能要件の数値も**ユーザーと決め切る。**
   測りようがないものは定性で書いて**確定させる**（`—` や「運用で目視」でよい）。
   保留を残すと、下流の仕様書・DB設計・テストがそこで止まる。
   決め切れないものは、持ち帰るか暫定で置くかをユーザーに選んでもらう（勝手に「未定」と書かない）。
9. **表を主体にする。** 散文は技術方針の前提と、表にすると死ぬ補足だけ。
10. 日本語で書く。

## 手順

### 0. 既存の要件定義書があるか確認する

`docs/requirements/` などに、対象の要件定義書（`02-requirement.md`）が既にあるか探す。
**候補が複数見つかったら、どれのことかユーザーに聞く。**

- **ある** → このスキルの出番ではない。**`requirement-doc-review` スキルへ回す**（点検して不足を埋める）
- **ない** → 1へ進む

### 1. 要求定義書を読む（前提の確認）

- 要求定義書（01）を探して**全文読む**。パスが分からなければ聞く。
- 見つからなければ**ここで止める。**`request-doc` で要求定義を作ってから戻るよう案内する。
- 見つかっても、課題一覧・ゴール・ジャーニーのどれかが空なら先にそこを埋めてもらう
  （不足の洗い出しは `request-doc-review` の仕事。02の中で01を書き足さない）。

読んだ内容から**1〜2章を最後まで書き切れる状態**にする。
白紙の質問（「どんな機能が必要ですか？」）を投げない。01から機能を起こすのはClaudeの仕事。

### 2. 出力先を決める

既定は要求定義書と同じディレクトリの `02-requirement.md`
（例: `docs/requirements/02-requirement.md`）。
機能ごとに文書を分けている場合はその構成に合わせる。ここは推測せずユーザーに確認する。

### 3. 1〜2章は、Claudeが一気に書いてから一緒に見て直す

**質問から入らない。**01を読んだ時点で機能は起こせるので、
**1章（機能一覧）と2章（各機能の要件）を最後まで書き切り、ファイルに保存してから**
ユーザーに見せる。空欄・`{}`・「TBD」を残したまま出さない。
判断が要る箇所も、**まずClaudeが案として書く**（この時点では提案であって決定ではない）。
ただし業務側の事実だけは書かずに聞く（大原則3）。

粒度の目安:

- 1機能 = ユーザーから見て「〜できる」が1つ。
- パイプライン型の処理なら1工程1機能（取込 / 変換 / 出力）。
- **数は対象次第。上限も下限も置かない。**必要なだけ立てる。
  揃えるのは**数ではなく粒度**で、機能どうしの大きさが極端に食い違っていないかだけ見る
  （1つで2章が5項目書けないほど大きいなら割る、単独では「〜できる」にならないなら束ねる）。
- 機能IDは `FUNC-01` から通し番号。**あとで機能が消えても番号を詰めない**
  （2章以降・下流文書がIDで参照するため）。追加は末尾に足す。

**見てもらう順序**

1. まず**1章の表だけ**を提示する（2章はファイルにあるが、ここではまだ広げない）。
   機能の**切り方と抜け漏れ**に絞って見てもらう。
   ここで機能が増減すると2章の書き直しが連鎖するため、先に1章を閉じる。
2. あわせて**Claudeが自分で決めた箇所と、迷った箇所を明示する。**
   「FUNC-03は01のジャーニー④から起こしたが、01に明示が無いので推測」のように、
   **根拠の弱い行を自己申告する。**ユーザーの時間はそこに使ってもらう。
3. 1章が固まったら2章へ。**機能1つずつではなく、まとまりで提示して赤入れを受ける。**
   全機能を一度に出して埋もれるようなら数機能ずつ区切る。
4. 赤入れは**その場でファイルに反映**してから次へ進む。指摘を溜めない。

### 4. 3〜4章は質問して決める

**ここから質問主体に切り替える。**何がMVPかと、性能・認証の水準は01から導けない。
Claudeの案を1つ添えて、決めてもらう。

最後に「次のステップ」として、仕様書（03）へ渡すものを1行で書く。

**書いたらファイルへ。**まとめて最後に書かない（`/clear` や中断で消えるため）。

### 5. 書き上がったら `requirement-doc-review` で点検する

全章そろったら、**点検は `requirement-doc-review` スキルに任せる。**
点検の観点（章の揃い・トレーサビリティ・受入基準の検証可能性・03以降の内容の混入など）は
そちらが正典なので、ここで独自のチェックリストを作らない。

不足が出たら、レビュー側の流れ（一覧で提示 → 質問しながら直す）でそのまま埋める。

### 6. ユーザーの承認をもって完成とする

点検の結果と直した箇所をユーザーに提示し、**承認を得てはじめて完成**とする。
自分の判断で締めない。

- Claudeが決めて書いた箇所のうち、そのまま残ったものを一覧で見せる
  （**黙って通さない。**最後にもう一度、決定として承認を取る）
- 決着させた未確定事項があれば、何をどう決めたかも見せる
- 「これで03（仕様書）へ進んでよいか」を確認する

## 質問の作法

質問が主役になるのは**1〜2章を見てもらう中で出た論点**と、**3〜4章**。
1〜2章の初稿を書く前に質問を並べない（分からない箇所も一度は自分で案を書く）。

**選択式と記述式を使い分ける。**選択肢に押し込むこと自体が目的ではない。

| 聞き方 | 使いどころ |
|---|---|
| 記述で聞く（普通の質問文） | 答えがユーザーの頭の中にしかないもの。現場の運用の実態、扱うデータの項目、既存システムとの繋がり。こちらが選択肢を作れないところを無理に選択式にすると、的外れな案から選ばせることになる |
| 選択式（`AskUserQuestion`） | 方向性が2〜3通りに割れていて、どれを採るかで以降の記述が変わるとき。スコープの線引きや非機能の水準のように、即断できる形にしたいとき |

どちらの場合も守ること:

- **一度に聞くのは2件まで。**章の切れ目ごとに刻む。まとめて4件並べると保留される。
- 選択式にするなら、選択肢は抽象語ではなく**その機能の文脈に落とした具体案**にする。
  妥当な案を先頭に置き `（推奨）` を付ける。ユーザーは選ぶか直すだけで済む状態にする。
- 選択式で聞いた場合でも、ユーザーは選択肢外を文章で返してよい。
  返ってきたら選択肢に寄せ直さず**そちらを優先する。**
- 01から自明に決まることは聞かない。**書いてあることを聞き返すと信用を失う。**
  聞くのは、01からは導けず**Claudeが決め切るべきでない**もの — スコープの線引き、
  非機能の水準、業務側の事実（誰が運用するか・どの規模でやるか）。
  例外時の振る舞いのように**案が出せるもの**は、聞かずに書いて見てもらう。
- 一度答えをもらったら、それを**表の形にして見せる**。合意した形をそのまま本文に使う。

### 未確定の事項をどう決着させるか

**決定権はユーザーにある。Claudeは案を出すところまで。**
「まだ決まっていない」と言われても、そのまま「未定」と書いて逃げない。決めやすい形にして聞き直す。

1. **選択肢を2〜3案に絞って出す。**各案について「これを採ると何が変わるか」を一言添える。
   妥当だと思う案には `（推奨）` を付け、なぜそれを推すかも1行で言う
2. **選べないと言われたら、何が分かれば決まるのかを言語化して、その一点だけ聞く。**
   「同時に何件処理するかが分かれば決まります。おおよそで構いません」のように絞る
3. **その場のユーザーだけでは決められない事項なら、そのことを伝えて判断を仰ぐ。**
   持ち帰って確認してもらうのか、いま暫定で決めて後で改訂するのかを**ユーザーに選んでもらう**

**どの段でも、ユーザーが「それでいく」と言うまでは決定として書かない。**
1〜2章で先に書いた案も同じで、**赤入れが無かったこと＝承認**とはみなさない。
最後に一覧で見せて確認を取る（手順6）。

## 各章に必要な項目

**必要なのは「どの項目があるか」まで。分量は問わない。**
内容が過不足なく書けていれば、行数や箇条書きの数は多くても少なくてもよい。

### 冒頭の引用ブロック

```
> Vモデル: 要件定義 / 対応する検証: システムテスト
> 要求定義（①）を「何を作るか」に翻訳する。各機能の要件・スコープ・非機能要件を定義する。
```

### 1. 機能一覧

表: `# / 機能ID / 機能名 / 概要 / 対応する要求(①)`

- **概要**は1〜2文。何を受け取り、何を出すかが分かる粒度。
- **対応する要求**は01の項目を指す（`課題1`、`ジャーニー③`、`ビジネスゴール` など）。
  01に無い呼び名を発明しない。参照先が01のどこかを、読み手が引けるように書く。

表の下に補足を置く。必要なものだけ:

| 見出し | 中身 |
|---|---|
| 技術方針（前提） | 箇条書き数行。使う言語・SDK・入出力の形式・処理の順番。**選定理由は書かない** |
| 主要な扱うデータ | 各機能をまたぐデータの構造を、**項目名の列挙レベル**で。テーブル定義は04の仕事 |
| 補足 | 「ジャーニーの◯はアプリ機能として持たない（手作業で足りる）」など、機能にしなかった判断 |

聞くこと: 01のどの課題を機能で解くか。機能の切り方（束ねるか割るか）。前提となる技術方針。

### 2. 各機能の要件

機能IDごとに小見出しを立て、**5項目すべて**を埋める。

| 項目 | 中身 |
|---|---|
| 概要 | 1章の概要を1〜2文で言い直す |
| 事前条件 | この機能が動き出せる状態。前の機能の出力を受ける場合はそれを書く |
| 正常フロー | `A → B → C` の1行、または箇条書き。**分岐は書かない**（分岐は例外側へ） |
| 例外・バリデーション | 入力が想定外だったとき何が起きるか。**ここを埋めないと下流が想像で作る** |
| 受入基準 | システムテストで○×が付く文。「〜すると、〜であること」 |

例外は最低でも「入力が空 / 対象外 / 処理に失敗」の3方向を検討し、
それぞれ**止めるのか、飛ばして続けるのか**を明示する。

受入基準は、01の成功指標に**○×の線を引く**場所。
01は「どうなったら成功か」の方向までで、合否の条件はここで初めて確定する。
「性能」「精度」のように機能をまたぐものは4章（非機能要件）側に置く。

聞くこと: 想定外入力のときどうしたいか。エラーで全体を止めるか、その1件だけ落とすか。

### 3. スコープ

先頭に区分の定義表を置く（`template.md` のまま流用してよい）。

| 区分 | 意味 |
|---|---|
| Scope 1（初版） | まず必ず作る。MVPとして成立させる最小機能 |
| Scope 2（改善） | 初版の次に着手する改善・拡張機能 |
| Scope 3（余裕があれば） | 時間・リソースに余裕があれば実装する機能 |
| Out of Scope | 今回は明確に実装しないと決めたもの |

- Scope 1〜3 は表: `機能ID / 機能名 / 備考`。備考にはその区分での**制限**を書く
  （「日本語のみ対象」「1件ずつ」など）。
- 同じ機能IDが別Scopeに再登場してよい（`（拡張）FUNC-01` の形で範囲を広げる）。
- **Out of Scope は表: `項目 / 実装しない理由`。理由を必ず書く。**
  ここは後から「なぜやらなかったか」を聞かれる場所。

聞くこと: どこまでを初版とするか。落とすものは何で、なぜ落とすか。

### 4. 非機能要件

表: `カテゴリ / 要件`。**次の5カテゴリを必ず埋める**（該当なしなら「該当なし」と理由を書く）。

| カテゴリ | 書くこと |
|---|---|
| 性能 | 処理時間・件数・精度。**測る対象と測り方**まで書く（人の待ち時間を含むかどうかも） |
| セキュリティ | 認証方式 / 有効期限 / 権限モデル / 秘密情報の扱い。単一ユーザーなら「なし」と明記 |
| 可用性 | 常時稼働か手動起動か。停止したときどうなるか |
| ユーザビリティ | 想定利用者のスキル水準（01のペルソナから引く）で操作できること |
| 保守性 | 変更が入りやすい箇所を、差分で直せる構造にする方針 |

数値は決め切る。根拠が無ければ「目安」と添えて数値を置く。空欄で残さない。

聞くこと: 許容できる処理時間。認証の要否。誰がどう動かすか。

### 末尾: 次のステップ

`→ 03-spec（仕様書・基本設計）で画面構成・画面ごとの機能・モックを作成する`

文書の連番が違うプロジェクトでは、その次工程の名前に合わせる。

## やらないこと

- **既存の要件定義書の点検・不足の洗い出し** → `requirement-doc-review`
- **要求定義書（01）の不足を埋めること** → `request-doc-review`。
  01に穴があると気づいたら、02の中で補わずそちらへ回す
- **画面構成・画面遷移・モックHTML・UI文言** → 仕様書（03）
- **テーブル定義・カラム・型・ER図** → DB設計（04）。
  2章で扱うデータに触れるのは**項目名の列挙まで**
- **APIエンドポイント・リクエスト/レスポンス定義・IPO** → API設計（05）
- **テストケース・テスト手順** → シナリオテスト（06）。ここに書くのは受入基準まで
- **要求定義のやり直し** → 01の内容に疑問があれば指摘して01を直す。
  02の中で課題やペルソナを再定義しない
- **技術選定の比較検討・工数見積り・担当分担** → 別文書

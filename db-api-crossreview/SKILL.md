# データ構造設計 × API・IPO一覧 の横断レビュー

対象は**データ構造・ファイルレイアウト設計書（`04-db.md`）と
API・IPO一覧（`05-api-ipo.md`）の2文書1組**。見るのは**2つの間の対応関係だけ**で、
それぞれの文書の中身の完備性は見ない（それは単体レビュースキルの仕事）。

**このスキルは文書を1文字も書き換えない。**出すのは**指摘レポート**だけ。
直すのは `db-doc-review` / `api-ipo-doc-review` へ渡す。

単体レビューとの違いはここ。

| スキル | 見るもの | 直すもの |
|---|---|---|
| `db-doc-review` | 04の内部の完備性（＋02・03との照合） | 04 |
| `api-ipo-doc-review` | 05の内部の完備性（＋02・03・04との照合） | 05 |
| **このスキル** | **04と05の間の対応関係だけを、対等に両側から** | **直さない（レポートのみ）** |

単体レビューは「自分の文書を直すために」相手を読む。だから相手側の非を見つけても
振るだけで終わる。**横断レビューは、どちらが誤りかの判定そのものを成果物にする。**

**04と05はどちらも形態が3つある。**最初に両方を見極めてから観点を当てる
（形態の組み合わせで、見るべき中身が変わる）。

| 04の形態 | 05の形態 | よくある組み合わせと、特に見るところ |
|---|---|---|
| RDB | HTTP API | 最も素直。**FKと`ON DELETE`・UNIQUE・トランザクション境界**が焦点 |
| ドキュメントDB | BaaS直アクセス | **認可の境界（セキュリティルール）とパスの切り方・非正規化の同期担当**が焦点 |
| DBなし（ファイル） | CLI・バッチ | **ファイルの読み書き権限・生成物の命名・中間状態の寿命**が焦点 |

**組み合わせがこの表から外れていること自体は指摘ではない**
（RDB＋CLI、ドキュメントDB＋HTTP APIは普通にある）。ただし
**04が「DBを持たない」と宣言しているのに05が永続化前提のAPIを並べている**ような、
前提そのものの矛盾は最優先の指摘（観点A）。

## 大原則

1. **書き換えない。**食い違いを見つけても直さない。レポートを出して振り先を示すところまで。
   ユーザーから「ついでに直して」と言われたら、**該当のレビュースキルへ切り替える**
   （このスキルの中で直さない）。
2. **全部読んでから判断する。**04の全文・05の全文。
   一部だけ見て「噛み合っている」と言わない。
3. **両側から見る。**04→05（誰も使わない器）と 05→04（根拠の無い読み書き）は
   別の見落としを生む。片方向だけでは必ず抜ける。
4. **どちらを直すべきかまで書く。**「食い違っている」で止めない。
   04が古いのか、05が先走ったのかを判定して、**根拠と一緒に**出す。
   判定できないときは「どちらの可能性もある」と明記し、判断材料を並べる。
5. **指摘は必ず場所と一緒に。**「`POST /api/inquiries` が `inquiries.property_id`
   （04でNOT NULL）を受け取らず、生成主体も書かれていない」のように、
   **インターフェース名とテーブル・カラム名で言う。**
   名前で指せない指摘は、指摘として弱い。
6. **単体文書の内部の話に踏み込まない。**04の章が欠けている・05のエラー表が無い・
   命名が揃っていない — これらは横断の指摘ではない。
   **ただし、それが原因で照合できないときは「照合不能」として出す**（観点J）。
7. **02（要件定義）・03（仕様書）は参照材料であって対象ではない。**
   04と05のどちらが正かを判定するときに**根拠として引く**のはよい
   （「03のSCR-04が削除確認を出すので、05側が正しい」）。
   02・03そのものの不足はこのレビューでは扱わない。必要なら
   `requirement-doc-review` / `spec-doc-review` へ回す。
8. **実装コードとの突き合わせはしない。**文書どうしの整合だけを見る。
   実物との食い違いは、単体レビュー（`db-doc-review` 観点I / `api-ipo-doc-review` 観点I）の仕事。
9. **設計の好みでは指摘しない。**「自分ならこう切る」は食い違いではない。
   指摘するのは、**2文書が矛盾している**か、**片方が要求するものをもう片方が満たせない**場合だけ。

## 手順

### 1. 対象を特定する

`docs/requirements/04-db.md` と `docs/requirements/05-api-ipo.md` の場所を確認する。
複数あるなら、どの組を見るのかユーザーに聞く。

- **04が無い** → まだ作成の段階。`db-doc` を案内して終了する
- **05が無い** → 突き合わせる相手がいない。`api-ipo-doc` を案内して終了する

あわせて**両方の形態**を見極める（上の表）。冒頭の前提と章タイトルから判定する。
判定できないなら、それ自体が観点Aの指摘（前提の宣言が無い）。

### 2. 全部読む

飛ばし読みしない。04の1章から5章まで、05の冒頭の前提から3章の最後まで通す。
**05の2章（IPO）は1行ずつ読む。**ここに「どのデータをどう変えるか」が書いてあり、
横断の指摘はほぼすべてここと04の定義の間から出る。

### 3. CRUDマトリクスを組む（最初にこれをやる）

**すべての指摘の土台になる。**目視の前に、機械的に拾えるものを潰す。

| 拾うもの | 見かた |
|---|---|
| 04のデータストア | 04の1章の表から、テーブル／コレクション／データストア名を列挙 |
| 05が触るデータ | 05の2章・3章の「対応データ(④)」「対応テーブル(④)」欄から列挙 |
| 差集合（04にあって05に無い） | **誰も読み書きしない器。**観点Aの指摘 |
| 差集合（05にあって04に無い） | **根拠の無い読み書き。**ほぼ確実に指摘（観点A） |
| 05のインターフェース | 05の1章から列挙。**これは指摘の対象ではなく、器を操作に結びつけるための地図** |

各データストアについて、**どのインターフェースが C / R / U / D のどれをするか**を埋める。
これが**このレビューで最も価値のある1枚**なので、レポート冒頭にそのまま載せる。

```
| データストア | C | R | U | D | 備考 |
|---|---|---|---|---|---|
| inquiries | POST /api/properties/{token}/inquiries | GET .../inquiries | PUT .../answer | — | 削除手段が無い（04は物理削除想定） |
```

**空欄になった列が、そのまま指摘の候補になる。**

- **C が無い** → 誰も作らない器。初期データ投入なら、その旨が04にあるか
- **R が無い** → 誰も読まない器。書くだけのログなら正常
- **U が無い** → 更新されない前提が04と一致するか（`updated_at` があるのに更新手段が無い、など）
- **D が無い** → 04の削除方針（物理／論理／保持期間）と噛み合うか

コマンドで潰すなら次の形。**出た差分をそのまま観点Aの指摘にする。**

```bash
comm -23 <(grep -oE "^\| *[a-z_]+" 04-db.md | tr -d '| ' | sort -u) \
         <(grep -oE "[a-z_]+" 05-api-ipo.md | sort -u)      # 04のみ＝誰も使わない器
```

**器の名前の拾い方は04の書き方に依存する**（1章の表の1列目・3章の小見出し）。
機械的な差集合は当たりを付けるためのもので、**出た差分は必ず目で確かめる。**
**中間ファイルを作業ディレクトリに残さない。**プロセス置換で済ませる。

### 4. 観点を当てる

下の「点検の観点」を全部当てる。
**A（対応）・B（書き込み）・C（削除と状態）・F（認可の境界）は漏れが最も出るので必ず見る。**

**当てる前に、直前に `api-ipo-doc-review` が走っていないか確認する。**
`api-ipo-doc` の手順7から続けて呼ばれた場合がこれにあたる（最も多い入り方）。
走っていたなら、**観点A・B・Cの05側は既に潰れた後**なので、同じ指摘を出し直さない。

- 05側で解消済みのものは**省く**
- **04側に残る分だけを出す。**例: `api-ipo-doc-review` が05へ足した重複エラーは、
  「04のUNIQUE制約が足りない」側の指摘としてだけ出す
- 走ったかどうかが分からなければ**ユーザーに聞く**（これは事実確認）

### 5. レポートを出す

「レポートの形式」に沿って出す。**文書は触らない。**

- **食い違いがある場合** → 重大度順に並べたレポートを出す。振り先も一緒に
- **食い違いがない場合** → **「04と05は噛み合っている」ことをユーザーに伝えて終了する。**
  何を確認した結果そう言えるのか（当てた観点と、CRUDマトリクスの結果）も一緒に出す

レポートを**ファイルに残すかはユーザーに聞く。**既定は会話へ出すだけ。
残すなら `docs/requirements/` ではなく、作業メモの置き場（`_notes/` など）へ置く
（**連番の設計文書に割り込ませない**）。

### 6. 振り先を示して終わる

指摘ごとの振り先をまとめて示し、次に何をするかをユーザーに選んでもらう。

| 直す対象 | 振り先スキル |
|---|---|
| 04（データ構造設計書） | `db-doc-review` |
| 05（API・IPO一覧） | `api-ipo-doc-review` |
| 03（仕様書）まで遡る必要がある | `spec-doc-review` |
| 02（要件定義書）まで遡る必要がある | `requirement-doc-review` |

**このスキルの中で直し始めない。**ユーザーが直すと言ったら、該当スキルへ切り替える。
両方に手が入る場合は、**04を先に確定させてから05**（器が決まらないと契約が決まらない）。

## 点検の観点

### A. データストアとインターフェースの対応（最も漏れが出る）

**両方向で照合する。**手順3のマトリクスがそのまま材料になる。

**04 → 05（使われない器）**

- 04の1章の**全データストアが、05のどこかで読み書きされているか**
- されていないなら、**なぜ誰も触らないかが分かるか**
  （マスタデータの手動投入 / 外部システムが書く / Scope 2 で使う）。
  無言で浮いているなら指摘
- 04の**サブコレクション・中間テーブル**まで見る。親だけ05に出てきて、
  子を作る手段がどこにも無い、が起きやすい

**05 → 04（根拠の無い読み書き）**

- 05の「対応データ(④)」に出てくる名前が、**04に実在するか**（表記まで一致するか）
- 04に無い器を触っているなら、それは**04の抜けか05の勝手な発明**のどちらか
- 05が**04の1章に無い項目を返している**（レスポンスのフィールドに対応する列が無い）

**前提そのものの矛盾**

- 04が「**DBを持たない**」と宣言しているのに、05が永続化・一覧取得・更新のAPIを並べている
- 04が宣言したDBエンジン・構成と、05の0章（**CLI・バッチでは1章の冒頭に畳まれている**）の
  認証・アクセス方式が噛み合わない
  （04はサーバ側DB前提なのに、05はクライアントが直接SDKで読む設計になっている）

**これは最優先の指摘。**下位の観点をいくら潰しても意味が無くなる。

### B. 書き込みが04の制約を満たせるか（最も漏れが出る）

**04の3章の定義を1行ずつ指で追い、05の作成・更新インターフェースと突き合わせる。**

- 04で **NOT NULL** の列を、05の作成リクエストが**受け取るか**。
  受け取らないなら、**誰が値を入れるか**が書かれているか
  （サーバ側で生成 / DEFAULT / 認証情報から補う）。
  **どこにも書かれていないのが最も多い致命の指摘**
- 04の **DEFAULT** と、05のリクエストの「既定値」の記述が**一致するか**
- 04の **UNIQUE**（単独・複合）に対して、05に**重複エラーが定義されているか**
- 04の **FK** の参照先を、05はどう受け取るか。
  **パスから来るのか、ボディから来るのか**が読めるか
  （パスに `{property_id}` があるのにボディでも受け取る、は二重で危険）
- 05のリクエストが受け取るのに、**04に対応する列が無い**項目が無いか
- 04の**型・長さ・桁**の想定と、05の説明が矛盾していないか
  （04が `integer` なのに05が「小数を受け取る」と書いている）
- **DBなし（ファイル）の場合**: 05が書き込むと言っている場所が、
  04のファイルレイアウトで**書込を許した場所か**。
  **読取専用と宣言した場所へ書いていないか**（これは致命）

### C. 削除・状態遷移の一致（最も漏れが出る）

- 04の**削除方針（物理／論理）**と、05の削除インターフェースの説明が一致するか。
  04が論理削除なのに05が「レコードを削除する」と書いている、が典型
- 04の **`ON DELETE`（CASCADE / SET NULL / RESTRICT）** と、
  05の削除の説明・エラーが噛み合うか。
  **RESTRICTなのに05に「参照されている場合」のエラーが無い**なら、実装が本番で落ちる
- **CASCADEで消える範囲が、05の説明と一致するか。**
  「この問い合わせだけ消える」と書いてあるのに、04では回答も一緒に消える、など
- 04の**列挙値（status等）**と、05のリクエスト・レスポンス・IPOで使う値が**一致するか**。
  **05側にだけ現れる状態**が無いか（04の列挙に無い値へ遷移させている）
- **状態遷移の担当が決まっているか。**04が持つ状態を、05のどのインターフェースが
  どの値へ動かすか。**どのAPIからも遷移しない状態**があるなら、どちらかが余分
- 04に**保持期間・削除運用**があるなら、それを実行する手段が05にあるか
  （バッチ・サーバレス関数として1行立っているか）

### D. 読み取りが04の構造で解けるか

- 05の一覧系が受け取る**絞り込み・並び順・検索条件**が、
  04の**インデックス方針**（またはクエリ・ファイル構造）で解けるか。
  **04に無いインデックスを前提にしたクエリパラメータ**は指摘
- 05のレスポンスが返す項目が、**その器から1回で取れるか。**
  他の器をJOIN・追加取得しないと作れないなら、
  **05の「対応データ(④)」にその器も挙がっているか**
- **ドキュメントDBの場合**: 05のクエリが、そのDBの制約
  （複合クエリの可否・`array-contains` の個数制限・全文検索の不在）で**実現できるか。**
  04の4章にその制約が書かれているなら、05がそれを踏み越えていないか
- **非正規化した項目の扱いが、両文書で一致しているか**
  （04が「一覧表示用に名前を複製して持つ」としているのに、
  05は毎回参照先を引く前提で書かれている、など。
  **どちらの読み方を正とするかが決まらないと実装が割れる**）
- **ページネーション**の有無が噛み合うか。04が大量件数を想定しているのに、
  05に上限が無い（またはその逆）
- **DBなし（ファイル）の場合**: 05が読むと言っているファイルが、
  04のレイアウトに実在するか。**生成物の命名規則が両文書で一致するか**

### E. 型・識別子・SSOTの一致

- **型のSSOTがどちらかに宣言されているか。**
  05の冒頭に「型は04を参照」とあり、04が実際にその型を持っているか。
  **両方が別々に型を定義しているなら、その時点で食い違いの温床**
- **識別子の採番主体が一致するか。**
  04が「自動採番」なのに05の作成リクエストが `id` を受け取る、
  04が「業務キーを主キーにする」のに05は連番IDを返す、など。
  **ドキュメントDBなら、ドキュメントIDが何から来るか**が両文書で一致するか
- 05が返す **ID・トークンの形**が、04の定義（型・長さ・生成方法）と一致するか
- 実装キーと**利用者に見えるラベル**の対応表が04にあるなら、
  05のレスポンスが**どちらを返すか**が明示されているか
- **日時の扱い**（タイムゾーン・生成主体）が両文書で一致するか

### F. 認可の境界とデータの分離単位（最も漏れが出る）

**04の「データの分離単位」と、05の「権限の境界」は同じものを別の言葉で言っている。**
ここがずれていると、**横断で他人のデータが見える事故**になる。

- 04が持つ**分離キー**（テナントID・物件ID・ユーザーID）が、
  05の**パス・パラメータ・認可の説明**に現れているか
- 05の各インターフェースが、**分離キーで必ず絞れる形になっているか。**
  絞りようがない（分離キーを受け取らない一覧API）なら致命
- 04で分離キーを持たないテーブルがあるなら、**05側でどう守るか**が書かれているか
- **BaaS直アクセスの場合**: 04のパスの切り方が、
  05の0章で宣言した**セキュリティルールの境界と一致するか。**
  ルールで絞れない形の器を、05が「認可済み」として扱っていないか
- 05の**必要権限**の記述と、04が持つ**権限・所属の器**（中間テーブル・ロール列）が対応するか。
  05が「対象物件の管理権限」と言うなら、それを判定する器が04にあるか

### G. 秘密情報・個人情報の受け渡し

- 04が**ハッシュで持つ**と決めた項目を、05が平文で受け取る／返すことになっていないか
- 05のレスポンスに、**04では内部用と位置づけた項目**が漏れていないか
  （内部ID・他人の個人情報・監査用の列）
- 04が**保持期間**を決めているなら、05にそれを実行する手段があるか（観点Cと繋がる）
- 04が置き場を決めた**秘密情報**（APIキー・トークン）の扱いが、05の0章と一致するか

### H. トランザクション境界・整合性・冪等性

- 05の**1呼び出しが、04の複数の器をまたいで書くか。**
  またぐなら、04の5章（整合性の方針）に**その境界が書かれているか**
- 04が**非正規化**した項目について、**同期を誰が担うか**が両文書で一致するか。
  04が「書込時にまとめて書く」としているなら、05のどのインターフェースがそれをするか
- 04が集計値・カウンタを持つなら、**それを更新するインターフェースが05にあるか**
- **副作用のあるインターフェース**（送信・課金・削除）について、
  05の冪等性の記述と、04の器（重複防止のUNIQUE・処理済みフラグ）が噛み合うか。
  **05が「再実行しても二重にならない」と言うなら、それを担保する器が04にあるか**
- **CLI・バッチの場合**: 途中で落ちたときの再実行が、
  04の中間ファイル・状態の持ち方で成立するか

### I. 片方だけ更新された痕跡（横断特有）

**どちらが新しいかを判定する。**これは横断レビューにしかできない。

- 04にだけ新しい器・列があり、05がそれに追随していないか（またはその逆）
- 05が**04でリネームされた古い名前**を使っていないか
- 04の制約（NOT NULL・UNIQUE）が後から足されたのに、05のエラー表が増えていない
- どちらかだけが02・03の新しい記述を反映している

判定材料: 名前の新旧、連番の並び、ファイルの更新時刻、gitのログ
（`git log -1 --format=%ci -- <path>`）。
**更新時刻だけで断定しない。**内容の整合と合わせて判断する。

### J. 照合そのものができない箇所

観点を当てようとして**突き合わせる材料が無かった**ものは、
「食い違い」ではなく**照合不能**として別枠で出す。原因の文書と振り先を書く。

- 04の制約欄が空 → 観点Bが当てられない
- 04の `ON DELETE` が未定義 → 観点Cが当てられない
- 05の「対応データ(④)」欄が空欄だらけ → 観点A・マトリクスが組めない
- 05の2章のProcessが「処理する」で終わっている → 観点B・C・Hが当てられない
- どちらかに「未定」「TBD」「`ASK:`」が残っている → その項目は照合できない

**照合不能を「問題なし」に混ぜない。**見ていないものを見たことにしない。

## どちらを直すべきかの判定

大原則4で判定そのものを成果物にすると決めている以上、**「直す先」列を空にしない。**
下を出発点にする。

| 食い違いの型 | 直す先 | 根拠 |
|---|---|---|
| 04にあって05に無い（誰も使わない器・列） | **04 or 05** | 器が余分なのか、操作を書き忘れたのか。**03の画面に出るなら05の抜け**、出ないなら04が余分 |
| 05にあって04に無い（根拠の無い読み書き・返す項目） | **04** | 05が必要としている以上、器が要る。ただし**03に根拠が無いなら05が余分** |
| 04のNOT NULL・UNIQUE・FKを05が満たせない | **05** | 制約は器の側の決定。05が受け取り方・エラーを足す |
| 04の削除方針・`ON DELETE` と05の説明が矛盾 | **04** | 消えたものは戻らない。**運用の判断であって契約の判断ではない**ので04で決めて05を従わせる |
| 列挙値が05にだけある | **04** | 状態を持つのは器の側。04の列挙に足す（05が誤っているなら05） |
| 05のクエリを04のインデックス・構造が解けない | **04** | 画面が要求する読み方が正。04にインデックス・構造を足す |
| 分離キーと認可の境界のずれ | **04 or 05** | **どちらの側が漏れているかで変わる。**器に分離キーが無いなら04、絞っていないなら05 |
| 秘密情報の扱いの矛盾 | **04** | 安全側（持ち方の決定）が正。05を従わせる |
| 型・採番主体の二重定義 | **05** | 型のSSOTは04。05は参照に寄せる |
| 片方が古い痕跡（観点I） | **古いほう** | 新しいほうが実態を映している |

**「上流が正」を機械的に当てない。**この表の2行目と6行目が示すとおり、
**05のほうが正しい場面は普通にある。**契約を書いて初めて分かったこと
（05が必要とするのに04に器が無い項目・04の構造では解けないクエリ・
権限を判定する器が無い）は、**04を直す根拠になる。**

判定に迷ったら `04 or 05` と書き、**どちらに倒すと何が起きるかを1行ずつ**添える。
「決められなかった」で流さない。
**04を直す指摘は、データ移行が要るかどうかも一言添える**（重さが変わる）。

## レポートの形式

### 冒頭

- 突き合わせた**ファイルのパス**と、**判定した両方の形態**
- **CRUDマトリクス**（データストア × インターフェース）。手順3で組んだものをそのまま
- 当てた観点と、**照合不能だった観点**

### 指摘一覧

**重大度の高い順**に並べる。

| 重大度 | 意味 |
|---|---|
| **致命** | 実装できない / 本番で壊れる / データが漏れる（前提の矛盾・NOT NULLを埋められない・分離キーで絞れない・読取専用へ書く） |
| **重要** | 実装は進むが、後で手戻りになる（使われない器・解けないクエリ・足りないエラー・同期の担当が不明） |
| **軽微** | 意味は通るが読み違えを誘う（名前のゆれ・注記の不足・二重定義） |

```
| # | 重大度 | 観点 | 04側 | 05側 | 何が噛み合っていないか | 直す先 |
|---|-------|------|------|------|---------------------|-------|
| 1 | 致命 | B | inquiries.property_id (NOT NULL) | POST /api/properties/{token}/inquiries | 05のリクエストが property_id を受け取らず、tokenからの解決も書かれていない。挿入できない | 05（tokenから解決する旨を明記） |
| 2 | 重要 | A | ai_chat_logs | — | どのインターフェースからも書かれない。誰が記録するか両文書に無い | 05（記録の担当を明記。不要なら04から落とす） |
```

**「直す先」は必ず埋める**（判定は「どちらを直すべきかの判定」に従う）。
判定できないものは `04 or 05（判断材料: …）` と書く。

### 照合不能の一覧

指摘一覧とは**分けて出す。**何が足りなくて照合できなかったか、振り先はどこか。

### 締め

- 指摘の件数を重大度別に
- **次にどのスキルを、どの順で走らせるべきか**（04が先、05が後）
- **データ移行が必要になる指摘があれば、それだけ別立てで**注意を促す

## やらないこと

- **文書を書き換える。**1文字も直さない。直すなら該当のレビュースキルへ切り替える
- **04の内部の点検**（章の欠落・ER図の破損・命名の揺れ・制約の空欄そのもの）
  → `db-doc-review`
- **05の内部の点検**（エラー表の欠け・IPOの空欄・1章と3章の数の不一致）
  → `api-ipo-doc-review`
- **新規に書き起こす** → `db-doc` / `api-ipo-doc`
- **02・03を対象に含める。**04・05の2本だけ（判定の根拠として引くのはよい）
- **06以降（テストケース）・Buildの内容が無いことを不足として出す**
- **実装コード・既存スキーマとの突き合わせ** → 単体レビューの観点Iの仕事
- **DBエンジン・API方式の選び直し、設計の作り替え提案**

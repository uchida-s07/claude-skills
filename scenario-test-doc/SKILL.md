# シナリオテスト仕様書づくり（システムテスト）

Vモデルの **システムテスト**（左側の対応は ② 要件定義）にあたる文書を1本作る。
やることは1つ — **②の受入基準を、Build後の実アプリに対して人が手で実行できる手順に翻訳する。**

01〜05は「何を作るか」を決める文書。06は**「作ったものが②を満たしているか」を人が判定する文書**。
成果物は実行される。**読んで分かる文書ではなく、そのとおり操作できる文書**を作る。

骨組みは同ディレクトリの `template.md`。章立てと表の列を見るための参考であって、
埋め方の指示書ではない。分量はそこに合わせにいかなくてよい。

**前提条件**: **01〜05の5文書が揃っていること。**欠けた状態でこのスキルを始めない。
（欠けていれば `request-doc` / `requirement-doc` / `spec-doc` / `db-doc` / `api-ipo-doc` へ回す）
**使う場面**: 05まで固まり、Buildに入る前後。実アプリの受入判定の物差しを作るとき。
**やり方**: **Claudeが01〜05から自律的に全シナリオを書き切る。**ユーザーは**成果物をレビューする役**。

## このスキルの進め方（他の文書スキルと違うところ）

**人間に判断を仰ぐのは、原則として最後の1回だけ。着手時の質問もしない。**
テスト対象・実行形態・テストデータは**01〜05とリポジトリから判定できる**ので、
聞かずに決めて宣言する。

1. **着手時**: 聞かない。01〜05とリポジトリを読み、**前提環境を判定して宣言してから**書き始める。
2. **途中**: 02の受入基準を正典として**全シナリオを最後まで自律的に書き切る。**
   機能ごとに「これでいいですか」と伺いを立てない。判断が要る箇所は決めて書き、
   **決めた事実を記録しておく。**
3. **完了前**: 書く過程で**重大な確認事項**（テスト実行そのものが危険・不可逆／上流の矛盾で
   テストが成立しない）が出ていたら、**完了させる前にまとめて確認する**（手順6）。

> **作業の段取りの確認（手順0）は、いつ聞いてもよい。**

1機能ずつ見せて赤入れを受ける進め方は**しない。**
シナリオは前提環境と初期データを共有していて（TEST-06の送信結果がTEST-13のGivenになる、など）、
**途中で1つ変えると初期データとカバレッジ表に波及する。**通しで書き切ってから直す方が速い。

## 大原則

1. **入力は 01〜05。揃っていなければ着手しない。**
   （05は04を、04は03を、03は02を、02は01を前提に作られるので、**05があれば下流も揃っている**。
   まず05の有無を見る）
   **正典は02の受入基準。**そこに書かれた「〜すると、〜であること」が、そのまま Then になる。
   03（画面・エラー表示）は**操作と期待文言の根拠**、04（データ）と05（インターフェース・
   エラー意味論）は**画面から見えないものを確かめる根拠**、01は**なぜそれを確かめるか**の確認用。
   欠けている文書があれば探し、無ければ**この文書を書き始めず**該当スキルへ案内する。
   02〜05に穴があるだけなら、06の中で補わず
   **`requirement-doc-review` / `spec-doc-review` / `db-doc-review` / `api-ipo-doc-review` で
   上流を直してから**戻ってくる。
2. **Then は受入基準と1対1に対応させる。**02の受入基準の文を、**観測できる形に落とす**だけ。
   受入基準に無いことを勝手に期待結果にしない。各 Then の末尾に
   **どの基準に対応するか**を `（②の受入基準に対応）` `（③のエラー表示に対応）` の形で添える。
   **どこから来たか分からない Then を1行も作らない。**
3. **全機能に、正常系と異常系のシナリオを最低1つずつ割り当てる。**
   カバレッジ表（1章）でそれを保証する。**空欄はテスト漏れそのもの。**
   異常系が思いつかないなら、02の例外・バリデーションと03のエラー・例外表示を読み直す。
   **そこに書いてあるものは全部テストになる。**
   **ただし、02にも03にも例外の定義が1つも無い機能に、異常系をでっち上げない**
   （大原則2と正面から衝突する。実装が正しくてもFailする Then を作ることになる）。
   その場合はカバレッジ表の異常系欄に **`（②に例外の定義なし）`** と書き、
   **02側の不足として手順9で報告する**（→ `requirement-doc-review`）。
   **無言の空欄と、根拠を示した「定義なし」は別物。**前者だけが不足。
   **1機能に1本ずつ別のシナリオを立てる必要はない。**同じTESTを両方の列に入れてもよい
   （`種別` を `正常系＋異常系` にして、表の中で行を分ける）。
4. **人が手で実行できることだけ書く。**
   - **操作は具体値で書く。**「適切なキーワードを入力する」ではなく「`駐輪場` と入力する」。
     「不正な値」ではなく「本文を空欄のまま送信する」。
   - **期待結果は観測できる形で書く。**表示される**文言まで**書く。
     「正しく処理される」で終わらせない。
   - **画面から見えないもの**（DBの値・ログ・生成ファイル・中間状態）を確かめるなら、
     **その手段を前提環境の「検証補助」に先に書く。**書かずに手順へ出さない。
5. **1行1判定。**Given / When / Then の1行に判定が2つ混ざると、Fail の原因が特定できない。
   判定が分かれるなら**行を分ける。**
6. **テストデータは先に確定させる。**シナリオ本文に初めて出てくるデータを作らない。
   Given が参照する値は**すべて「初期データ」表に実在する**こと。
   前のシナリオの結果を Given にするなら、**どのTESTで作られるかを明記する。**
7. **トレーサビリティを各シナリオの見出し下に置く。**
   `対応機能(②)` / `対応フロー(⑤)` / `画面(③)` / `対応要求(①)` / `種別`。
   **②は必須、③⑤は該当があれば必須。**空欄を作らない。
8. **②の受入基準に対応する画面・インターフェースが③〜⑤に無いなら、★設計未対応として残す。**
   これを黙って落とすと、**要件と設計の不整合が発見されないままBuildへ流れる。**
   該当ステップに `★設計未対応` と書き、**「仕様上Failする想定」であること**と
   **Failの原因が実装ではなく要件(②)と設計(③〜⑤)の不整合であること**を明記する。
   冒頭の「注記（対象範囲について）」にも同じ内容を1件として載せる。
9. **Scope 2 以降・Out of Scope はテストしない。**02のスコープに従う。
   対象外にした機能は、**カバレッジ表から消すのではなく、冒頭の注記に理由付きで書く。**
   無言で消えているのは、テスト漏れと区別が付かない。
10. **自動テストコードを書かない。**単体テスト・E2Eスクリプト・テストランナーの設定は
    Build フェーズの成果物。**06は人が読んで手で実行する文書**であることを冒頭で宣言する。
11. **「未定」「TBD」「要確認」を本文に残さない。**
    決め切れないものも**暫定で決めて書き、決めた箇所として手順9で申告する。**
    保留を残すと、実施者がそこで止まる。
    **ただし「重大な確認事項」だけは暫定で押し切らず、完了前に聞く**（手順6）。
    聞くと決めた項目も、**本文には暫定案を書き込んだうえで**印を付けておく。
    （`★設計未対応` は保留ではなく**確定した記述**なので、この原則の対象外）
12. **表を主体にする。**散文は章冒頭の「目的」と、表にすると死ぬ補足だけ。
13. 日本語で書く。ただし**識別子（画面ID・機能ID・コマンド・パス・パラメータ名・
    実際に入力する値）は実装で使う表記のまま**書く。

## 手順

### 0. 既存の設計書があるか確認する

`docs/requirements/` などに `06-scenario-test.md` が既にあるか探す。
**候補が複数見つかったら、どれのことかユーザーに聞く**（事実確認なので聞いてよい）。

- **ある** → このスキルの出番ではない。**`scenario-test-doc-review` へ回す**（点検して不足を埋める）。
  全面書き換えは、ユーザーがそう言った場合だけ。
- **ない** → 1へ進む

**あわせて01〜05が揃っているか確かめる。**欠けていれば、その時点で該当スキルへ案内して終える。
出力先の既定は、05と同じディレクトリの `06-scenario-test.md`。既存の連番規則があればそちらに合わせる。

### 1. 01〜05 を読む

- **02（要件定義書）を全文読む。ここが正典。**
  **受入基準を1つ残らず抜き出して手元に並べる**（機能IDと対で、あとでカバレッジ表になる）。
  **1つの機能に受入基準が複数あるなら、文単位に割って番号を振る**
  （`FUNC-03-a` `FUNC-03-b`）。**1つだけ拾って残りが消えるのが最も多い漏れ**で、
  番号を振っておけば手順7でそのまま突き合わせられる。
  **例外・バリデーション**も同じように全部抜き出す — **異常系シナリオの種はここにしかない。**
  **スコープ**（Scope 1 / 2 / 3 / Out of Scope）で**テスト対象の線を引く。**
  非機能要件に測れる基準（処理時間・精度・件数）があれば、それも判定できる形にする。
- **03（仕様書）を全文読む。**画面ごとのUI要素・操作・**エラー表示の文言まで。**
  **Given（どの画面を開いているか）と When（どの要素をどう操作するか）の根拠**であり、
  **エラー表示の文言が異常系の Then になる。**画面遷移図は複数画面をまたぐシナリオの順序の根拠。
- **04（データ構造設計書）を読む。**画面から見えない結果（保存された値・状態遷移・
  列挙値）を確かめるときの根拠。**検証補助でDBを見るなら、見る先はここで決まる。**
- **05（API/IPO一覧）を読む。**2章のフロー（FLOW-xx）が**シナリオの骨格**になる。
  3章のエラー意味論は**異常系の期待結果**の裏取り。
  **02の受入基準に対応するインターフェースが05に無いなら、それが原則8の★設計未対応。**
- **01（要求定義書）**は「なぜこれを確かめるのか」の確認用。課題・ジャーニーが
  各シナリオの `対応要求(①)` になる。

**読み終えたら、抜き出した受入基準を1つずつ指で追い、
その場で「これを確かめる画面が03にあるか・インターフェースが05にあるか」を確かめる。**
**無いものが★設計未対応**（大原則8）。ここで印を付けておけば、手順3でそのまま使える。
**書きながら気づくのでは遅い**（辻褄を合わせる方向に手が動いてしまう）。

読み終えた時点で、**全シナリオを最後まで書き切れる状態**にする。
足りない情報は02〜05から**導く**。導けないものは暫定で決める（大原則11）。

### 2. 前提環境を判定して宣言する（**聞かずに決める**）

**まず自分で調べる。**「どうやって起動しますか」と投げない。

調べる先（あるものだけ）:

- **05の冒頭・1章** — 実行形態（HTTP API / BaaS直アクセス / CLI・バッチ）と認証方式。ここが最大の手がかり
- **03の1章の「処理単位・前提」** — ログインの要否、アクセス経路（URL / QR / コマンド）
- **リポジトリの起動口** — `package.json` の `scripts`、`README`、`Makefile`、`docker-compose.yml`、
  CLIの引数定義（`argparse` / `commander` / `cobra`）、モバイルなら `flutter run` とビルド構成
- **04** — 初期データを投入する先（テーブル・コレクション・ファイル配置）。
  シード・マイグレーションのファイルがあれば、**そこに実在する値をテストデータに使う**
- **02の非機能要件・05の認証の節**（0章、またはCLI形態では1章の冒頭） — テスト用アカウントに要る権限

判定して書くのは次の6つ。**空欄を作らない。**

| 項目 | 決めること |
|---|---|
| 対象 | 何を起動した状態を指すか（URL・コマンド・端末とビルド構成） |
| 起動手順 | 依存の用意 → 設定 → 起動。**実施者がそのとおり打てる粒度**で |
| アクセス経路 | URL・QR・コマンド・ディープリンク |
| テストデータ | 初期データ表を指すか、投入するファイル群を列挙するか |
| 初期状態 | どの状態で開始するか。実行前にクリアするものがあるか |
| 検証補助 | 画面から見えないものを確かめる手段（無ければ行ごと省く） |

**実装依存で変わりうるもの**（ポート番号・URLのパス構造）は、
**「実際の値は起動環境に読み替える」と1行添える。**断定して外すより、読み替え先を示す。

**秘密情報は値を書かない。**在り処（環境変数名・鍵の管理場所）だけ書く。
**テスト用アカウントのIDとパスワードは値をそのまま書く**（実施者が打てないと意味がない）。
ただし**それが本番でも通る資格情報なら、手順6の重大な確認事項**として扱う。

判定結果と根拠を**1〜2行で宣言してから**3へ進む。

### 3. カバレッジ表を先に作る

**シナリオ本文より先に1章を作る。**ここが**テストの設計図**であり、
先に作らないと「書きやすい機能だけ厚くなる」。

1. 手順1で抜き出した**受入基準を、機能IDごとに1行**並べる
2. 各行に**正常系のTEST-IDを最低1つ**割り当てる
3. 各行に**異常系のTEST-IDを最低1つ**割り当てる。
   種は**02の例外・バリデーション**と**03のエラー・例外表示**。
   両方を舐めて、**落ちるものが無いように**割り当てる。
   **どちらにも種が無い機能だけ** `（②に例外の定義なし）` と書いて空ける（大原則3）
4. **Scope 2 以降・Out of Scope の機能は行を作らず**、冒頭の注記へ回す（大原則9）
5. **受入基準に対応する画面・インターフェースが③〜⑤に無いもの**を印付けし、
   ★設計未対応として載せるTESTを決める（大原則8）

この時点で**TEST-IDの総数と、各TESTが何を確かめるかが確定する。**そのまま4へ進む。

> **1機能1シナリオに割らなくてよい。**受入基準が複数あるなら分けてよいし、
> 1シナリオで複数機能をまたいでもよい（送信 → 管理側で確認、など）。
> **同じTESTを正常系と異常系の両方の列に入れてもよい**（そのTESTの `種別` は
> `正常系＋異常系` にし、表の中で正常系の行と異常系の行を分ける）。
> **カバレッジ表のマスが埋まることだけを守る。**

### 4. 全シナリオを自律的に書き切る

**その場では質問しない。**02〜05からシナリオを起こすのはClaudeの仕事。
重大な判断に当たっても、**書く手を止めずに印を付けて進む**（下記）。
空欄・`{}`・「TBD」を残したまま出さない。

書く順序:

1. **冒頭の引用ブロックと「使い方」** — Vモデル上の位置と、実施者が何をするか
2. **注記（対象範囲について）** — 該当があるときだけ。Scope外と★設計未対応
3. **前提環境と初期データ** — 手順2で決めたもの。**初期データはここで確定**（大原則6）
4. **1章 カバレッジ表** — 手順3のもの
5. **2章 シナリオ** — カバレッジ表の順に、TEST-01から。
   各TESTは「見出し → メタ情報 → Given/When/Then の表」の形を崩さない
6. **3章 判定の切り分けガイド** — Fail の症状 → 疑う層 → 確認先
7. **末尾** — 「次のステップ」

各シナリオを書くときに守ること:

- **Given は「今どうなっているか」だけ**書く。操作を混ぜない
- **When は1つの操作**。「入力して送信して確認する」は3行に割る
- **Then には観測できる結果と、対応する基準の出どころ**を書く
- **判定欄は全行に `☐Pass / ☐Fail`**、実施者メモ欄は空で置く
- 異常系には、**その異常系がどこから来たか**を見出し直下に引用で1行添える

**判断したことは、その場で作業メモに残す**（どこを02〜05から起こし、どこを自分で決めたか）。
手順9でそのまま使う。**重大な確認事項に当たったものは、メモ上で分けておく**（手順6で使う）。

**手を止めない。**重大な判断に行き当たっても、そこで質問して待たない。
**暫定案を書き込んで印を付け、残りを最後まで書き切ってから**手順6でまとめて聞く。

**印は `<!-- ASK: 何を確認したいか -->` のHTMLコメントで入れる。**
本文の表示には出ないので、途中で中断されても文書が壊れない。
**「要確認」「TBD」の語は本文に書かない**（大原則11のgrepに引っかかり、
本当の書き残しと区別できなくなる）。

**書いたらファイルへ。**まとめて最後に書かない（`/clear` や中断で消えるため）。

### 5. 上流の不足に気づいても、ここで埋めない

書いている途中で02〜05の不足に気づいたら（受入基準が曖昧で○×が付かない、
例外に対応するエラー表示が03に無い、受入基準に対応するインターフェースが05に無い）、
**手を止めず、06側では次のどちらかで処理して**手順9の報告に積む。

- **判定できる形に落とせるもの** → 06側で具体化して書き、**決めた箇所として申告する**
- **③〜⑤に対応する実体が無いもの** → **★設計未対応として本文に残す**（大原則8）。
  こじつけで別の手順に置き換えない

02・03・04・05そのものを書き換えるのは、それぞれのレビュースキルの仕事。

### 6. 重大な確認事項があれば、完了前に確認する

**該当が無ければこの手順は飛ばす。**（飛ばしたこと自体は報告しなくてよい）

#### 何が「重大」か

次の**どれかに当てはまるものだけ**が重大。**当てはまらないものは聞かずに決める。**

- **手順どおり実行すると、取り返しがつかないことが起きる**
- **実施者が用意できないものを前提にしている**
- **上流が矛盾していて、どちらを正とするか決めないとシナリオが書けない**

具体的には次のとおり。

| 重大（完了前に聞く） | なぜ |
|---|---|
| **本番環境・実データ・実アカウントに対してテストさせることになるとき** | 実行した瞬間に戻せない。テスト環境の在り処を確かめる必要がある |
| **課金・外部への送信（メール・通知・決済）を伴う手順を含めるとき** | 実行が外に出る。ダミー先・サンドボックスの有無を確かめる必要がある |
| **削除・初期化を含む手順で、戻し方が01〜05から分からないとき** | 一度流すと以降のシナリオが実行できなくなる |
| **02の受入基準と、03〜05の設計が正面から矛盾していて、どちらを期待結果にするか決まらないとき** | どちらを正とするかは上流の判断。★設計未対応で処理できる範囲を越えている |
| **★設計未対応が多すぎて、その機能のシナリオが1本も成立しないとき** | テストを書く段階ではなく、上流を直す段階 |
| **テスト用アカウントの資格情報が、本番でも通るものしか見当たらないとき** | 文書に平文で書くことになる。テスト専用の値を用意してもらう必要がある |
| **実施者・実行環境が特定できず、起動手順が書けないとき**（手順2で調べても分からない） | 誤ると全シナリオが実行不能になる |
| **02の非機能要件の測り方が、業務の事実を知らないと決められないとき**（許容時間・件数の水準） | 推測すると桁違いの基準になる |

| 重大でない（聞かずに決めて手順9で申告） | なぜ聞かなくてよいか |
|---|---|
| シナリオの切り方・本数、1本にまとめるか分けるか | 記述の整理であって判定の中身ではない |
| TEST-IDの採番順、カバレッジ表の並び順 | あとで直せる |
| 検索キーワード・入力文字列などのテストデータの中身 | 受入基準を判定できれば何でもよい |
| 初期データの件数・名称 | 同上 |
| Given をどこまで書くか、前提を何行に割るか | 実行できれば足りる |
| 「実施者」の呼び方（研修生・テスター等） | 文書内で一貫していれば足りる |
| 検証補助でDBを見るかログを見るか | 観測できれば足りる |

> 迷ったら**「この手順を実施者がそのまま実行したとき、戻せないことが起きるか」**
> を考える。起きるなら重大。**文書の書き方の問題なら聞かない。**

#### 聞き方

- **全シナリオを書き切ってから、まとめて聞く。**見つけた時点で止めない（手順4）。
- `AskUserQuestion` で、**一度に聞くのは2件まで。**3件以上あれば**影響の大きい順**に刻む。
- 選択肢は**そのシナリオの文脈に落とした具体案**にする。抽象語で聞かない。
  妥当な案を先頭に置き `（推奨）` を付け、**各案に「これを採ると何が変わるか」を一言添える。**
  暫定で本文に書き込んだ案がどれかも明示する。
- **なぜ聞くのかを1行で言う**（「実行すると実顧客へメールが飛ぶため」）。
- 「まだ決まっていない」と言われたら、**何が分かれば決まるのかを言語化して、その一点だけ聞く。**
  それでも決まらないなら、**持ち帰るか暫定で確定させるかをユーザーに選んでもらう。**
  暫定で確定させる場合は、**そう決めた事実を前提環境か該当シナリオに1行残す。**

#### 答えが返ったら

- **本文の暫定案を差し替え、印を消す。**
- **波及を必ず追う。**前提環境・初期データ・カバレッジ表・該当シナリオの Given —
  **この4箇所がそろって直っているか**を毎回確認する。ここが最も取りこぼす。
- 差し替えた内容は、手順9の一覧に**ユーザーが決めたもの**として載せる
  （Claudeが決めたものと混ぜない）。

### 7. 自己点検する

`scenario-test-doc-review` を走らせる前に、**機械的に潰せるものだけ**自分で潰す。

- [ ] **02の全機能ID**が、カバレッジ表に現れているか（Scope外は注記にあるか）
- [ ] カバレッジ表の**正常系・異常系の両方が全行で埋まっている**か
      （空けるなら `（②に例外の定義なし）` の断りがあるか。**無言の空欄が無いか**）
- [ ] **02の受入基準を文単位に割った番号**（手順1）が、**1つ残らずどれかの Then に落ちている**か
- [ ] カバレッジ表の**全TEST-IDが2章に実在する**か。**逆に2章のTESTが全部カバレッジ表にある**か
- [ ] 2章の**全TESTに `対応機能(②)` と `種別`** があるか。そのIDが02に実在するか
- [ ] 2章に出る**全 `SCR-xx` が03に、全 `FLOW-xx` が05に実在する**か
- [ ] **判定欄が全行に `☐Pass / ☐Fail`** で入っているか
- [ ] **Given が参照する値が、すべて初期データ表にある**か（または作られるTESTが明記されているか）
- [ ] **02の例外・バリデーション**が、どれかの異常系シナリオに落ちているか
- [ ] 「未定」「TBD」「要確認」「{」が本文に残っていないか（**grepで確認する**）
- [ ] **`ASK:` の印が1つ残らず消えているか**（grepする。暫定案が残っていないか）
- [ ] 自動テストコード・実装コードを書いていないか

引っかかったら**直してから**8へ進む。

### 8. `scenario-test-doc-review` で点検する（**省略しない**）

06が書き上がったら、**ユーザーへ出す前に必ず `scenario-test-doc-review` スキルを1回走らせる。**
点検の観点（章の揃い・カバレッジ・受入基準との対応・異常系の網羅・実行可能性・
前提環境と初期データ・トレーサビリティ・章をまたいだ整合・★設計未対応の扱い・
スコープ・混入・未確定の残り）は**そちらが正典**なので、
ここで独自のチェックリストを作らない。

**点検していない成果物をレビューに出さない。**
指摘はその場で直し、直した結果を手順9の報告に含める。

> レビュー側は「作成スキルから呼ばれたとき」の進め方を持っている。
> **点検結果をこちらへ返すところまでがレビューの仕事**で、そこで承認を取らせない。

### 9. ユーザーにレビューを依頼する

**ここが人間の出番。**成果物とあわせて、次の6つを必ず出す。

1. **作ったファイルのパス**と、**判定した前提環境とその根拠**（手順2）
2. **カバレッジ表のダイジェスト**（機能ID × 正常系 / 異常系のTEST-ID）。
   全文を読ませる前の見取り図
3. **★設計未対応の一覧** — どの受入基準が、③〜⑤のどこに対応を欠いているか。
   **これが06を書いて初めて見つかる最大の成果**なので、**最初に見せる**
4. **決めた箇所の一覧** — 「何を・どう決めたか・なぜそう決めたか」を表で。
   **手順6でユーザーが決めたもの / Claudeが決めたもの / 01〜05に根拠があるもの**の3つを
   区別して見せる。**レビューの時間はClaudeが決めたものに使ってもらう。根拠の弱い順に並べる。**
5. **02〜05に対して気づいた不足**（手順5）。
   **06の中で勝手に補わず、上流を直すべきものとして報告する**（振り先のスキル名も添える）
6. **手順8のレビュー結果** — 何を指摘され、どう直したか

**レビュー結果はその場でファイルに反映する。**指摘を溜めない。
反映後、変えた箇所を一覧で見せて**承認をもって完成**とする。自分の判断で締めない。

### 10. 上流の直しを勧めて終わる

**★設計未対応も上流の不足も1件も無かったなら、この手順は飛ばし、
「これでBuild／テスト実行へ進んでよいか」の確認だけで締める。**

1件でもあったなら、赤入れが片付いた後に**最後に必ず次を伝える。**言わずに締めない。

> 06を書く過程で、**②の受入基準に対して③〜⑤が対応を欠いている箇所**が見つかりました。
> このままBuildへ進むと、該当シナリオは**実装が正しくてもFailします。**
> **要件(②)側を実態に合わせるか、設計(③〜⑤)側に不足を足すか**を先に決めることをおすすめします。
> 02×03の食い違いは `requirement-spec-crossreview`、04×05は `db-api-crossreview` が、
> **文書を書き換えずにどちらを直すべきかの指摘だけ**を出します。

**走らせるかはユーザーが決める。**このスキルの中で勝手に起動しない。

そのうえで「これでBuild／テスト実行へ進んでよいか」を確認する。

## 各章に必要な項目

**必要なのは「どの項目があるか」まで。分量は問わない。**

| # | 章 | 中身 |
|---|---|---|
| 冒頭 | 引用ブロック | Vモデル上の位置（システムテスト / ②要件定義）・何をもとに作ったか・誰が手で実行するか |
| — | 使い方（実施者向け） | 起動 → 実行 → 判定記録 → 原因切り分け → 全Passの意味、の手順 |
| — | 注記（対象範囲について） | **該当があるときだけ。**Scope外にした機能と★設計未対応 |
| — | 前提環境 ＋ 初期データ | 手順2の6項目 ＋ Given が参照する値の一覧 |
| 1 | カバレッジ表 | 機能(②) × 受入基準（要約） × 正常系 × 異常系 |
| 2 | シナリオ | TEST-xx ごとに メタ情報 ＋ Given/When/Then の表 |
| 3 | 判定の切り分けガイド | Fail の症状 → 疑う層 → 確認先 |
| 末尾 | 次のステップ | 全Passを目指す旨。★設計未対応があるならその扱いも |

### 冒頭の引用ブロック

```
> Vモデル: システムテスト（右側）/ 対応する設計: ② 要件定義
> ①〜⑤の設計書が固まった段階で、② の受入基準をもとに生成する。
> 実施者は **Build した実アプリ** に対して手動でシナリオを実行し、判定を記録する。
```

**「Build した実アプリに対して手で実行する」ことを必ず明記する。**
ここが抜けると、自動テストの仕様書と読み違えられる。

### 注記（対象範囲について）

**該当が無ければ章ごと省く。**空の章を置かない。書くのは次の2種類だけ。

- **テスト対象外にした機能**と、その根拠（02のスコープのどこでそう決まっているか）
- **★設計未対応**（大原則8）。どの受入基準が、③〜⑤のどこに対応を欠いているか。
  **どのTESTのどのステップでFail想定として扱うか**まで書く

### 前提環境 ＋ 初期データ

手順2の6項目を表で。続けて**初期データ**の表を置く。

- 初期データは `種別 / 内容` の2列で足りる（アカウント・マスタ・登録済みデータ）
- **Given が参照する値は、すべてここに実在させる**（大原則6）
- **アカウントはIDとパスワードを値のまま書く。**秘密情報は在り処だけ書く
- 実装依存で変わりうる値は「実際の値は起動環境に読み替える」と添える

> **投入するデータがDBのレコードではなく「入力ファイル群」の形態**（CLI・バッチで
> `input/` にサンプルを置く、など）**では、初期データ表を別立てしなくてよい。**
> 前提環境の「テストデータ」行に、**どんな性質のファイルを何件置くか**を列挙すれば足りる
> （「明細が読み取れる日本語Excel 1件 / 一部項目が欠損したPDF 1件 / 破損PDF 1件」）。
> **どちらの形でも守ることは同じ** — **Given が参照するものが、シナリオの外で先に確定していること。**

### 1. カバレッジ表

表: `機能(②) / 受入基準（要約） / 正常系 / 異常系`

- **機能(②)** は `FUNC-01` の形で02を指す。02に無い呼び名を発明しない
- **受入基準（要約）**は、02の文を**判定の観点が分かる程度に**残す。「〜できること」だけに削らない
- **正常系・異常系の両方を埋める。空欄を作らない**（大原則3）
- 1つの機能に複数TESTが対応してよい（`TEST-03 / TEST-07` のように並べる）
- 横断的な観点（完了条件・停止条件・非機能）があるなら、**（横断）の行として立てる**

### 2. シナリオ

各TESTは次の形を崩さない。

**見出し**: `### TEST-01 {何を確かめるか}（正常系）`
— **見出しだけで何を確かめるか分かる**こと。「機能テスト1」のような名前を付けない。

**メタ情報**（箇条書き）:

- `**対応機能(②)**: FUNC-01 ／ **対応フロー(⑤)**: FLOW-01 ／ **画面(③)**: SCR-01`
- `**対応要求(①)**: 課題1、ジャーニー②`（01に対応があれば）
- `**種別**: 正常系` / `異常系` / `正常系＋異常系`

**表**: `# / 前提(Given) / 操作(When) / 期待結果(Then) / 判定 / 実施者メモ`

- **Given** = 今どうなっているか（開いている画面・存在するデータ・ログイン状態）。操作を混ぜない
- **When** = **1つの具体的な操作**（入力値まで書く）
- **Then** = **観測できる結果 ＋ 出どころ**（`（②の受入基準に対応）`）。表示文言まで書く
- **判定** = `☐Pass / ☐Fail`（全行）
- **実施者メモ** = 空欄で置く（Fail時に事象を書く欄）

異常系には、**見出し直下に引用で1行**、どこから来たかを書く
（`> ② の「例外・バリデーション」と ③ の「エラー・例外表示」から作成する`）。

★設計未対応のステップは、Then に**次の3つを全部書く**。

1. なぜ確認できないか（③〜⑤のどこに対応が無いか）
2. **「このステップは仕様上Failする想定」**
3. **Failの原因が実装ではなく要件(②)と設計(③〜⑤)の不整合であること**

### 3. 判定の切り分けガイド

表: `Fail の症状 / 疑う層 / 確認先`

**Vモデルの左側を上から下へ並べる**（②要件 → ③基本設計 → ④⑤詳細設計 → 実装）。
最後の行は必ず**「上記が正しいのに動かない → 実装(Build)バグ」**で締める。
プロジェクト固有の症状（エージェントの完了条件が効かない、など）があれば行を足す。

### 末尾

```
→ Fail を修正し、全 Pass を目指す。全 Pass ＝ 要件を満たした証明。
```

★設計未対応があるなら、**そこは原理的にFailするので上流を見直す**旨を続ける。

## やらないこと

- **自動テストコードを書くこと**（単体テスト・E2Eスクリプト・テストランナー設定） → Buildフェーズ。
  **06は人が手で実行する文書**
- **単体テスト・結合テストの設計** → 単体は⑤、結合は③に対応する検証。06はシステムテスト
- **要件定義書（02）の不足を埋めること** → `requirement-doc-review`。
  06の中で受入基準を足さない（気づいたら手順9で報告する）
- **仕様書（03）の画面・エラー文言を発明すること** → 03に無いものをThenに書かない。
  対応が無いなら★設計未対応（大原則8）
- **テーブル定義・API仕様の再掲** → 04・05の内容。参照するだけ
- **Scope 2 以降・Out of Scope のシナリオを書くこと** → 冒頭の注記に回す
- **実施者が用意できない前提を置くこと**（実データ・本番アカウント・外部システムの実接続）
  → 手順6で確認する
- **章ごとにユーザーの承認を取りながら進めること** → 手順9でだけ人間に渡す
  （重大な確認事項があるときだけ手順6を挟む）
- **テストを実行すること・実行結果を書き込むこと** → 判定欄は空で渡す。実行するのは人間
- **`scenario-test-doc-review` を走らせずに提出すること**（手順8は省略しない）
